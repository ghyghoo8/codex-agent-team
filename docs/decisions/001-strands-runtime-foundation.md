# ADR-001：采用 Strands SDK 作为受控执行架构基础

- 状态：Accepted（架构方向）；真实运行与验收另有阶段门。
- 决策日期：2026-09-30。
- 决策依据：用户要求“将《Codex Agent Team：基于 Strands SDK 的受控执行底层方案》作为新的架构基础”。
- 当前工作：开发指引、仓库工程初始化及 README。

## 背景

此前文档围绕 Codex App 执行宿主设计协作与交接。2026-09-25 的 [Strands 方案](../v3-0925/codex-agent-team-strands-runtime-proposal-2026-09-25/docs/strands-runtime-foundation-proposal.md) 提出项目自行拥有执行循环，将业务权威与模型运行分开。当前仓库已有 Git 历史及该方案交接包，初始化前没有工程代码、依赖锁文件或业务数据库。

## 决定

采用 Strands TypeScript SDK 路线作为新开发的架构基础：

1. Team Service 是任务、计划、授权、认领、证据、交接及人类验收的唯一业务权威，并是业务 SQLite 的唯一写入者。
2. 按需启动的 Runner 负责 Strands Agent 生命周期、Provider、会话及执行观察。SDK 类型限制在适配内部。
3. 工具在全部参数转换之后、实际动作之前核验权限、版本、资源与操作许可；业务记录与外部效果分别对账。
4. 项目脚本与测试属于不受信任代码，进入经过验证的隔离环境，不获得 Runner 或 Team Service 凭据。
5. 保留确定角色、精确能力锁、两阶段就绪、单写者、未知结果不重放、技术交付与人类验收分离等既有原则。

首版采用一个仓库、一个 npm 包、一个锁文件，Team Service 与 Runner 有独立入口；采用 Fastify、TypeScript strict，目标 Node.js 24。业务存储规划为 SQLite + better-sqlite3，界面规划为 React + Vite；按切片引入。Runner 通信选择本机父子进程 IPC，具体消息 schema 在首个使用切片落实。首版不并建 IPC/HTTP 两套运行框架。

不采用完整 `createHarness()` 的默认工具与后台行为，不 fork 框架，不提前建立多后端插件系统。Codex App 继续作为开发工具及质量比较基线。

## 与旧材料的关系

原交接包、ZIP、manifest 及旧文档保持原样。它们的“本轮只读”“未批准架构采纳”描述属于当时的历史范围；不否定这次已授权的初始化，也不扩张这次工作到完整产品开发。

| 旧内容 | 当前处理 |
|---|---|
| Codex App 为成品主要执行宿主、首版无自有 Runner | 被本 ADR 的 Strands Runner 路线取代 |
| 任务/计划/分工/Attempt/证据/决定、版本检查、显式授权 | 由 [开发指引](../development-guide.md) 明确继承 |
| 能力专项 v0.3 的精确版本与两阶段核验 | 继续适用；外部宿主探针替换为 Runner 实际构造与调用验证 |
| Wake/历史恢复、PowerContext、SkillBox | 按需参考，不作为 Strands 首个切片前置依赖 |
| 自动降档、旧全组 Hook、CodexBoard 底座 | 继续排除 |
| D01“是否接受自有运行责任” | 架构方向已决定，不能再次列为待采纳 |
| D09/R5“何时成为主路线” | 解释为真实运行准入与质量验收，不能凭本 ADR 标为通过 |

旧方案只按上表及开发指引明确引用的业务契约继承，不整份恢复 `docs/backup/` 的执行路线。当前权威顺序为：最新用户指示 → 本 ADR 的采纳与覆盖关系 → 原 Strands 方案的适用技术边界 → 开发指引的实现约定；能力专项只治理能力锁与就绪检查。

## 未决事项与后果

仍需在相应切片前确定 Provider/实际模型、参数与数据出站范围，审批身份入口，SDK/源码/Session 格式锁，真实隔离方式，保留策略，试点任务及预算。详见开发指引 §13。

项目需自行承担授权、工具安全、进程管理、操作对账、会话兼容及编码质量，SDK 不替代这些责任。任一硬门槛失败时停止相关执行；可以保留成果并明确交接，但不静默切换后端或重放未知写操作。

本次采纳不代表 SDK 已安装、源码审计完成、真实模型调用成功、隔离验证通过或 R1–R5 完成；也不迁移在途任务，不授权推送、合并、发布或部署。
