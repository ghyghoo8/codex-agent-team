## 1. 给接手者的摘要

本项目希望让一个需求方通过可配置的专业角色，围绕任务完成澄清、方案、实现、协作、评审和验收，并在会话中断或执行者变化后可靠续办。

本轮讨论的重点已经从“尽量省 token、动态选择运行档位”转向：

> **任务组织清晰，角色真实生效，协作结论可追溯，交接有证据，恢复不重复执行，所有有实质影响的变化有明确授权。**

用户明确允许降低 token 成本的优先级。不能据此推导出无限预算、自动换模型或扩大执行权限。

### 1.1 接手后首先做什么

**先核对，不先重建。**读取本地仓库的 `AGENTS.md`、README、现有设计文档、依赖锁文件和已有实现，记录实际分支、提交及未提交改动，再对照本文形成差异报告。原上传方案曾处于只有设计、运行探针未执行的状态；这不证明本地仓库现在仍没有代码。[B1, §10–11]

首个候选验证不是完整云端平台，而是一个小闭环：

```text
一个明确任务与已授权计划
  → 一个真实角色执行部分工作
  → 形成带版本与证据的交接
  → 另一个会话核对并记录接收结果
  → 在有效执行权下继续
  → 记录实际结果
  → 人类验收精确成果
```

这个闭环可先用人工触发和明确记录验证。它不要求恢复旧的动态调度、部署 Todos、接入全部 PowerContext 能力或安装一组 Hook。

### 1.2 三类不能混淆的记录

```text
上下文接收确认 ≠ 执行授权
执行结束／运行成功 ≠ 技术交付通过
技术交付通过 ≠ 人类业务验收
```

### 1.3 本文的证据标签

| 标签 | 含义 |
|---|---|
| 用户明确 | 当前可见对话中的直接要求或明确调整。 |
| 原方案基线 | 上传 v0.5 的设计约束；原文仍为 Proposed，不代表已实现。 |
| 候选设计 | 本轮整理出的建议，需与仓库现状及用户决策对齐。 |
| 文档可见 | 本轮可获取的官方文档说明；不是本机实测结论。 |
| 待验证 | 接口、运行行为、默认值或当前仓库状态尚无足够证据。 |
| 已归档 | 暂存备用，不因本文整理而重新生效。 |

未特别说明时，第 5–18 节的新增设计属于**候选设计**，其中标注 `[B1]` 的规则来自原方案基线。

## 2. 需求演变与当前约束

### 2.1 用户明确表达的内容

| 主题 | 当前可确认的要求 |
|---|---|
| 使用环境 | 围绕 Codex App 的工作方式设计，后续交给本地开发。 |
| 初始问题 | 长任务已经投入较多工作，资源或上下文可能不足时，希望能交接，而不是从头再来。 |
| 接续选择 | 当前 Agent 可以评估剩余工作、提出接续建议；不固定 Ultra → XHigh。 |
| 授权 | 调度和运行变化需要显式授权，避免隐式动态机制。 |
| 触发 | 可以有人工触发；不希望为了监控而不断调用分析 Agent。 |
| 归档 | 先前的运行控制、动态调度和 Hook 草案已暂存备用，未采纳。[B2] |
| 新参考 | 研究 Todos、PowerContext、Dashi，提炼可强化当前方案的内容。 |
| 成本 | token 成本优先级可以降低。 |
| 当前交付 | 整理为可供本地开发接手的文档；本轮不是执行开发或推送仓库。 |

### 2.2 继承自原 v0.5 的基线

原方案明确独立拥有任务板、Team Service 和业务数据；Dashi 仅供提炼，不作为运行底座或长期兼容对象。角色定义、专业分工、运行配置和执行实例分开，任务状态与执行观察分开，必须保留人类验收。[B1, §1、§4、§6–8]

原方案的本地服务、SQLite、TypeScript 技术方向可以作为评审起点，但具体依赖版本不能从旧文档直接复制为“当前已验证组合”。现有仓库若已有实现或后续决定，应先核对，不擅自回退到旧版。

### 2.3 仍不是已批准决定的内容

以下内容曾在助手建议中出现，不能自动升级为用户需求：

- 产品必须部署云端，或必须采用“云端控制、本地执行”。
- 用 Todos 替代自有任务板，或将 Todos 与 Team Service 双向同步。
- 正式引入 PowerContext 作为必需依赖。
- 建设本地常驻执行器、无人值守接单、自动唤醒 Codex。
- 自动升级或降级模型，自动调整 effort、预算、参与角色。
- 一次性接入六个或更多 Hook。
- 因 token 成本不再最高优先级而放弃范围、质量或权限边界。

**“交接到本地开发”描述的是下一步工作地点与接手方式，不等于用户已决定最终产品只能本地部署。**

### 2.4 本文建议的优先级

建议顺序为：正确交付与授权 → 可靠续办 → 协作清晰和使用体验 → 响应速度与维护成本 → token 优化。

这是根据“成本优先级降低”形成的设计建议，不是用户给出的量化排序。实际试点门槛由用户确认；继续记录用量，但不为节省用量省略必要核验。

## 3. 范围收敛与不做事项

### 3.1 候选最小产品范围

保留一个需求方、一个活动 Mission、一个当前 Coordinator。角色目录可以有多个角色，执行实例按工作创建。首个可写闭环采用单个隔离 worktree、同一时刻一个写入者；最多两个同时执行的 Specialist 是原方案试点建议，不是 Codex 的通用硬上限。[B1, §3、§8]

首版需要：任务及计划、角色版本、分工、执行记录、必要协作议题、证据、交接、接收核对、人类验收、可见阻塞与手动续办。

### 3.2 暂不列为首版依赖

不先做通用流程引擎、常驻角色群聊、自动模型路由、定时 LLM 评估、强化学习调度、跨项目任务网、无人值守远程执行、桌面客户端注入或完整聊天复制。

这些不是永久禁止的功能；新增时应有明确需求、授权、独立设计和验证，而不是作为“基础设施”一并带入。

### 3.3 归档方案如何使用

旧归档只用于解释探索历史和未决问题。[B2]

其中关于 Max / Ultra / XHigh / High 的固定能力排序、20%/30% 阈值、token 节省比例、自动降档、Hook 字段和触发保证，均不得直接进入配置或验收标准。

新文档若替代旧章节，应通过明确修订记录说明“保留／修改／不采纳”，不要修改归档的原始状态。

## 4. 三个参考项目：提炼内容与使用边界

### 4.1 参考分工

| 来源 | 文档或原材料支持的参考价值 | 对当前方案的候选补强 | 不据此认定 |
|---|---|---|---|
| Todos | Agent 具有职责、模型、工具、Skill 和 Memory；围绕任务规划、实现和评审。[T1] | 任务作为协作入口，角色配置与交付过程可见。 | Todos 缺少角色；它已解决全部授权问题；它能接管已有 Codex App 会话。 |
| PowerContext | 区分 Memory、Handoff 和版本化资料；提供工作约定、接续、接收及结果记录接口。[P1–P3] | 给上下文交接增加精确版本、来源与接手核验。 | 接收记录授予执行权；记忆就是当前任务真相；已有 Todos 联调方案。 |
| Dashi | README 描述本地任务板及统一 HTTP 操作入口；Skill 要求读取任务、使用版本并由用户确认完成。[D1–D2] | 执行前核对、任务与运行关联、操作效果明确、行为验证。 | Skill 提示词等于服务端硬门禁；应复用它的数据库或注入路线。 |

### 4.2 Dashi 应沉淀为本项目规则的内容

原 v0.5 已基于 Dashi 固定快照提炼任务状态、CAS、层级依赖、执行引用、证据和恢复。该快照 `2a6970a` 是原文记录，不是本轮重新获取的提交。[B1, §12]

本轮建议进一步落实为六项：

1. 开工／接续前核对任务、需求变化、输入版本、工作区与未决运行。
2. 不只保存任务的最近会话 ID，还要保存每次 Attempt 的实际运行引用。
3. 配置名称、计划请求、实际启动参数和行为验证分开记录。
4. 查看、分析、准备、提交、接收和执行是不同操作。
5. 请求停止、观察到停止、副作用核对是不同事实。
6. 每项可靠性保证对应行为测试，不用代码中出现某个字段证明隔离成功。

这些是本项目拟采用的工程契约，不是对 Dashi 当前实现逐项认证。

此前讨论提到的 `read-only` 参数转换、线程完成事件、进程所有权和特定测试实现，仅保留为本地源码复核线索。本轮未锁定一致源码提交，不把它们当作最新版缺陷或已成立的保证。

### 4.3 不搬入 Dashi 的部分

README 的嵌入路径涉及 CDP 和客户端界面注入。[D1] 它与官方 Hook 不是同一机制，不能证明旧 Hook 草案可用。

保留独立实现边界：不 fork 作为底座，不连接其数据库，不维护 API/schema 兼容，不跟踪全部版本变化，不复制桌面壳和安装器。若确有代码复用需求，先核验许可证、版本、适用范围和维护责任。

### 4.4 参考不等于依赖

候选组合不是“Todos + PowerContext + Dashi 全部装上”。本项目首先需要唯一任务权威和真实宿主；外部上下文服务与现成工作台的采用必须分别决定。

## 5. 候选产品模型：任务、阶段、角色、分工

### 5.1 概念映射

| 概念 | 含义 | 边界 |
|---|---|---|
| Project | 代码项目及实际工作区归属 | 标题相同不能证明同一项目。 |
| Mission | 一次目标交付；仍可采用 `kind=mission` 的根 Task | 不另建同义父议题。[B1] |
| Work item | 可检查的具体工作项 | 首版保留一层子任务，不扩展任意树。[B1] |
| Stage | 澄清、方案、实现、验证等阶段 | 是流程位置，不等于任务状态或能力档位。 |
| RoleProfile | 可复用专业职责、指令、输入输出要求 | 不等于永久 thread，不自带执行授权。 |
| RuntimeProfile | 本次模型、effort、宿主及工具权限请求 | 请求值需与实际生效证据分列。 |
| Assignment | 某角色在某工作／阶段的具体分工 | 可由原 ProcessAssignment 演进，不需另造重复模型。 |
| Attempt | 一次实际执行尝试 | 重新派发建新记录，不覆盖历史。 |

Stage 可先是计划快照内的有限枚举与分工属性。没有实际需要时，不急于建设独立阶段引擎或数据库表。

### 5.2 角色与阶段是多对多，不是自动入组规则

示例：后端角色可以参与方案、实现与评审；架构角色可以先设计方案，在实现遇到问题时再受邀咨询。适配某阶段不代表自动参加该阶段所有任务。

```text
Mission / Task
  └─ Plan revision
      └─ Stage + Work item
          └─ Assignment
              ├─ role_profile_revision
              ├─ responsibility: owner / contributor / reviewer
              ├─ input_contract + output_contract
              ├─ authorized_runtime_profile
              └─ Attempt(s)
```

每个工作项有明确主责，参与角色按当前需求选择。简单任务允许单角色完成，不为团队形式增加无意义分工。

### 5.3 角色配置面板

至少包括：职责与非职责、适用阶段、专属指令与 Skill、输入和输出标准、上下文需求、候选运行配置、版本、宿主验证结果。

角色修改产生新版本；正在执行的计划不随目录编辑自动变化。模型不可用时显示不可用和候选处理方式，不静默替换。继承宿主配置也应显式记录。[B1, §4]

官方 Subagents 文档说明子 Agent 有配置及父环境继承关系；因此云端或本地角色卡片上的“只读”不能直接证明实际只读。[O2]

## 6. 架构候选与部署决策

### 6.1 优先用于验证的最小形态

```text
人类需求方
  ├─ 自有任务板／决策入口
  └─ 本地 Codex App 中的当前 Coordinator
           │
           ├─ Team Skill：工作方法与交接指引
           ├─ Team MCP：受控业务命令
           │       ↓
           │   Team Service → 唯一业务数据库
           │       └─ Context Adapter → 可选 PowerContext
           │
           └─ 已验证的宿主工具 → Specialist Attempt
                                     ↓
                              本地工作区／Git／验证记录
```

这是便于试点的候选形态，不预先裁定最终是否云端部署。

### 6.2 组件边界

| 组件 | 负责 | 不负责 |
|---|---|---|
| Taskboard | 展示、计划预览、人类决策、证据入口 | 不绕过业务服务直接改数据库。 |
| Team Service | 任务、计划、认领、授权检查、版本、证据接纳、验收 | 不靠模型自述制造运行事实。 |
| Team MCP | 将工具请求映射为统一业务命令 | 不保存另一份任务状态，不假设能遥控 App。 |
| Coordinator | 在授权内组织角色、调用可用宿主工具、提交结果 | 不自授人类验收权，不默认控制其他根会话。 |
| Context Adapter | 将本项目身份、版本与外部上下文接口对接 | 不把外部结果直接映射为 `done`。 |
| PowerContext（可选） | 被选用后的记忆、交接与来源能力 | 不替代任务授权与工作区核对。 |
| Codex 宿主 | 实际模型和工具运行及权限实施 | 不以 turn 结束决定业务验收。 |
| Git / 文件系统 | 真实代码、文档和验证产物 | 不把路径字符串当作跨机器可访问证据。 |

MCP 文档提供工具与数据连接能力，包括本地 STDIO 和远程 HTTP 方式。[O1] 本方案不从该能力推导出云端能够唤醒已关闭的 App，或可以恢复崩溃前的执行。

### 6.3 保留但未定案的路线

| 路线 | 用途 | 进入条件 |
|---|---|---|
| 本地自有任务服务 + Codex | 验证 v0.5 的角色与交付闭环 | 与现有仓库实际情况对齐。 |
| Codex + PowerContext 小试验 | 先隔离验证跨会话交接质量 | 授权安装、数据范围、服务版本和宿主兼容性明确。 |
| 云端 Team Service + 本地 Codex | 远程准备任务、角色和协作资料 | 单独确定认证、可达性、数据上传、断线语义和执行入口。 |
| Todos 作为唯一任务工作台 | 评估现成产品能否替代自建 | 用户明确改变产品边界；不与自有任务服务双重持有状态。 |
| 自有本地执行服务 / App Server 路线 | 需要主动控制独立线程或无人值守运行时研究 | 另立运行方案，验证单一驱动者、审批和停止能力；不作为 App 不支持时的静默 fallback。 |

## 7. 唯一事实来源与上下文可信度

### 7.1 各类信息的权威来源

| 信息 | 权威来源 |
|---|---|
| 当前需求与范围 | 可信人类输入及其确认的任务／计划版本。 |
| 当前任务状态、分工与验收 | 唯一业务服务。 |
| 实际代码及未提交改动 | 指定工作区、Git 基线和受控快照。 |
| 测试结果 | 绑定输入／代码版本的实际执行记录。 |
| 运行是否在途或停止 | 可获取的宿主观察；不可获取时明确 unknown。 |
| 长期记忆、交接解释 | 指定来源和版本的上下文记录；仍需与现场核对。 |
| 执行权限 | 当前有效授权加宿主实际限制，不来自记忆中的文字。 |

### 7.2 记忆不是新的系统指令

召回的记忆、历史聊天、讨论消息、工具输出与外部交接均作为资料处理，不能覆盖当前用户指示、宿主安全边界和服务端授权。

长期原则也必须保留出处与状态。旧记忆说“允许发布”，不能代替本次发布授权；某角色在讨论中表示“同意”，不等于用户接受了范围变化。

### 7.3 上下文清单

每次执行建议记录一份有界清单，而不是复制全部聊天：

```text
任务与计划版本
角色及分工版本
所需规范／Skill 版本
必需需求与接口资料
已接受决策
精确交接及证据引用
本次召回的辅助记忆及来源
遗漏／不可访问／可能过期的内容
```

对敏感字段脱敏。记录来源不等于向所有角色开放全文；读取范围仍需权限检查。

### 7.4 两种上下文缺失的不同处理

辅助记忆不可用：在已授权策略下可继续，并标注上下文缺失。

必需交接、需求基线或验证证据不可用：不能把缺失当作不存在，也不能静默换用 `latest` 或重新开始；阻止依赖该资料的交付动作，记录解除条件。

---

## 8. 同一任务内的多角色协作

### 8.1 两种最小协作方式

**阶段交接：**方案 → 实现 → 指定成果评审 → 人类验收。

**阶段内咨询：**主责角色遇到具体问题 → 建立议题 → 获准角色回应 → 形成决定或显式分歧 → 主责继续。

多角色不等于并行写代码。初期可串行咨询、并行只读检查，写入仍单一负责。[B1, §8]

### 8.2 议题记录

候选字段：`topic_id`、任务／计划版本、问题、发起分工、受邀角色、相关证据、消息、决策引用、状态、结束条件。

候选议题状态为 `open / awaiting_input / resolved / deferred`；只描述讨论，不改变 Attempt 状态。

评论、建议、异议和已接受决定分开。决策至少写明问题、结论、依据、影响范围、决定者的可信来源及版本；摘要不能自行把多数意见变为批准结果。

### 8.3 协作的授权边界

发出问题不自动启动所有相关角色。执行计划可以事先允许特定咨询、评审和有限修复；超出参与者、范围或轮次边界时提出建议并等待决定。

后台通知、页面刷新和模型响应是不同动作。刷新界面不应隐式调用模型，收到一条消息也不应自动唤醒接收者。

## 9. 显式授权与操作效果

### 9.1 授权不是每一步重复询问

一次具体授权可以覆盖一个有限流程。例如：指定任务与计划、允许的角色与运行配置、工作区和可写范围、一次评审及一次窄修复、停止条件，以及不允许推送／合并／发布。

但“系统认为更省成本”“模型自评风险低”“记忆里曾允许”都不能补出不存在的授权。

### 9.2 操作效果矩阵（拟议契约）

| 操作 | 允许产生的效果 | 不隐含授权 |
|---|---|---|
| 查看状态 | 读取任务、运行观察和证据索引 | 不启动 Agent、不改任务状态。 |
| 分析当前工作 | 调用被允许的模型形成建议；分析本身需在授权内 | 不换模型、不延长执行、不扩大范围。 |
| 只读预览交接 | 在当前回复中整理候选内容；不调用业务／上下文写工具 | 不正式保存、不启动接手者。 |
| 准备交接 | 保存被允许的边界材料或草稿，明确保存位置 | 不保证产生正式版本，不转移控制权。 |
| 提交交接 | 保存精确版本、来源及提交结果 | 不代表技术交付或用户验收。 |
| 核对并接收 | 保存接收结论、检查结果及精确版本 | 不授予文件、工具或发布权限。 |
| 启动／接续 | 创建有效 Attempt，调用指定宿主 | 不跳过旧执行核对，不自动换配置。 |
| 请求停止 | 记录停止意图并调用允许的中断能力 | 不代表执行已经停止。 |
| 人类验收 | 接受精确候选成果清单 | 不自动合并、发布或开启后续任务。 |

“只读”在这里指不执行额外业务写入；宿主正常保留聊天的行为不能被承诺为零持久化。

### 9.3 运行配置变更

模型、effort、角色、宿主、上下文服务、工具权限与预算发生实质变化时，检查是否被现有**精确授权**覆盖；否则先提出变更。升档和降档一视同仁。

默认候选策略是不自动改变配置。确需预授权转换时，列出精确来源和目标配置、适用任务、触发入口、限制与撤销方式，而不是只写“自动降级允许”。

不把 `max / ultra / xhigh / high` 当作已验证的统一模型 ID 或等级体系；本地选择器与宿主 schema 才决定合法配置。

### 9.4 可信来源

`role_name`、`actor`、`approved_by` 字符串和内容哈希都不授予权限。服务端从认证连接或人类入口解析身份，绑定计划版本和操作范围。[B1, §7.5]

子 Agent 如果继承父 Agent 的全部业务凭据，就不能宣称它只能读取或不能提交。必须实际验证，必要时缩小 Pilot 范围，并由用户决定是否接受降低的保证。

## 10. 四种“交接”必须分开

| 类型 | 解决的问题 | 关键记录 |
|---|---|---|
| 技术成果交接 | 下游是否可以使用上游的某一版本成果？ | `technical_handoff`、输入和成果版本、必需验证／评审。[B1] |
| 上下文接续 | 新会话是否理解当前工作并能核对现场？ | Continuation Package、精确版本、接收回执。 |
| Coordinator 控制权接管 | 谁可以认领、登记或接纳本 Mission 的结果？ | 可信控制绑定、控制代、人类接管决定。[B1] |
| 人类业务验收 | 成果是否满足用户要求？ | 人类接受／退回，绑定精确候选成果。[B1] |

上下文接收之后，技术交付可能仍未完成；技术交付之后，业务验收可能仍在等待。

接手者核对资料不要求先拥有代码写权限；真正继续执行前才需满足完整的计划、认领、工作区和宿主授权条件。

## 11. 上下文交接协议

### 11.1 发起条件

可以由用户明确提出，或在已授权阶段交付／暂停流程中发起。当前 Agent 可建议交接，但建议本身不启动接手者。

预算、上下文或失败信号仅为观察资料。默认不进行定时模型巡检，不把低余额直接映射为换模型。确需自动信号时，在启用前声明采集、写入与模型调用效果。

### 11.2 建议的接续流程

```text
1. 核对任务、计划、授权和工作区基线
2. 读取当前事实，区分完成、未做、失败与未知
3. 生成交接内容和证据清单
4. 在授权内提交正式交接，获取精确版本
5. 核对提交结果；失败或未知则显式保留待对账状态
6. 接手方读取精确版本并核对证据、现场、能力与权限
7. 记录 accepted / needs_clarification / declined
8. 处理旧执行与控制权；满足条件后创建新 Attempt
9. 执行并保存 succeeded / partial / blocked 等实际结果
10. 通过独立的技术交付和人类验收流程收口
```

外部服务返回的状态要保留原值和来源，不能为了统一枚举丢失信息。上面的接收状态与 PowerContext 文档术语一致，但本项目是否直接采用其 schema 待适配验证。[P2–P3]

### 11.3 Continuation Package 内容

以下是**本项目候选内容契约**，不是可直接发送给 PowerContext 的 API 请求：

```yaml
schema_version: "proposal.v1"
identity:
  project_id: "<任务服务中的项目ID>"
  task_id: "<工作项ID>"
  plan_revision: "<不可变计划版本>"
  assignment_id: "<分工ID>"
  source_attempt_id: "<原执行ID>"
  context_scope_id: null  # 未绑定时为空，不能猜测

goal:
  objective: "<当前目标>"
  in_scope: []
  exclusions: []
  acceptance_criteria: []

authority:
  authorization_ref: "<实际授权记录引用>"
  unresolved_requests: []
  note: "这里只引用授权，不因出现该字段而获得授权"

workspace:
  identity: "<本机已核验工作区身份>"
  branch: null
  base_commit: null
  current_head: null
  dirty: null
  tracked_diff_ref: null
  untracked_artifacts: []
  active_execution_observation: "unknown"
  observed_at: null

progress:
  completed_with_evidence: []
  partial: []
  not_started: []
  blocked: []
  unknown: []

decisions:
  accepted: []
  rejected_options_with_reasons: []
  unresolved: []

validation:
  checks: []  # 每项保留命令、范围、代码基线、状态、时间、日志引用
  not_run: []
  unavailable_evidence: []

continuation:
  next_action: "<可执行的下一步>"
  required_capabilities: []
  known_side_effects: []
  risks: []
  stop_conditions: []

provenance:
  source_references: []
  created_at: "<实际生成时间>"
  declared_by: "<声明者；不自动视为可信执行身份>"
```

不得把 null 填成“无”，不得把未执行测试写成通过。未提交修改和 untracked 文件可能属于交接成果；不强制自动 commit，也不遗漏未跟踪文件。保存补丁或附件前检查秘密、路径和上传授权。

### 11.4 接手核验

接手者检查三类内容：

- **现场一致性：**任务、需求、工作区、输入和成果基线是否与交接相符。
- **实际能力：**能否读取证据、运行所需工具、取得所需环境。
- **授权有效性：**继续的行为是否有当前授权，是否存在待处理变化。

核对通过才能记录接收；不确定则需要澄清，不把接收做成默认动作。接收回执绑定精确版本，不只保存 `latest`。

PowerContext 的公开接口区分 Prepared Handoff 和正式提交的 Revision；接收回执与工作结果的链接也有精确选择约束。[P2] 本地接入时以锁定版本的真实工具 schema 为准。

### 11.5 接收检查不是授权事实的替代品

Agent 的“authorization confirmed”仍是一次观察／声明。服务端在启动新 Attempt 时重新执行授权检查；不能仅凭回执字符串决定用户已经同意。

同理，证据能读取仅证明身份与可访问性，不保证未过期。交接提交与接收之间发生的新变化仍需处理。

## 12. PowerContext 接入候选

### 12.1 第一阶段只验证显式路径

优先研究长期记忆读取、正式交接、精确版本读取、接收确认与结果记录。自动召回、提示词采集、画像、经验生成和 Skill 演进单独授权、单独验证。

PowerContext 的 Memory 用于可复用知识；Handoff 用于转移当前工作，两者不能互相替代。[P1]

文档可见的工作连续性接口包括：

```text
create_work_contract
handoff_current_work
commit_handoff
continue_handoff
acknowledge_handoff
record_task_outcome
```

这些名称来自参考项目，不是当前仓库已实现的工具。具体参数、读写效果、版本与可用性由本地锁定版本核验。[P2–P3]

### 12.2 本项目适配边界

候选方式：业务服务保存本项目身份与精确外部引用，通过一个窄适配模块调用选定的上下文服务。不需要为此建设多厂商平台。

另一种小试验可以让 Codex 直接使用 PowerContext MCP；此时必须承认其写入未经过 Team Service 的全部门禁。不能同时开放宽泛直接写工具，却声称所有上下文写入都受本项目规则控制。

两条路径需要明确选择，不要默认同时启用，也不自动 fallback。

### 12.3 Scope 映射

先验证选定版本的 Scope、Memory 和 Handoff 约束，再定映射：

- 本项目的项目身份不由模型猜测。
- 任务上下文 Scope 由明确映射选择；匹配失败时报错。
- 多个独立任务是否可安全共用同一个 Handoff Scope，需要检验并发和 head 语义，不能先假设可以。
- 项目共享知识与任务工作状态应可区分；跨 Scope 读取及证据引用是否支持，必须实测。
- 不默认通过工作目录或 Git remote 自动打开另一个项目的上下文。

Scope ID 在本项目中只作为资源定位，不作为访问凭据。多用户／云端部署的认证、跨项目访问控制和数据保留另行设计；本轮没有验证 PowerContext 的完整多租户适配。

### 12.4 跨服务写入与对账

Team Service 和 PowerContext 的写入不能视为同一数据库事务。

建议使用本地操作记录：`prepared / sent_unknown / external_committed / linked / failed`，并保留操作 ID、期望版本、外部精确引用和最后观察。这是联动操作状态，不是 Attempt 状态。

| 失败窗口 | 恢复契约 |
|---|---|
| 外部准备成功，正式提交失败 | 如实记录已有草稿／Source，不声称存在正式里程碑。 |
| 外部提交成功，业务登记失败 | 按精确引用核对后补登记，不直接重做外部写入。 |
| 外部请求响应丢失 | 标记结果未知；先查询，不盲目重试有副作用的调用。 |
| 任务已登记引用，外部证据不可读 | 显示证据不可用，阻止依赖该证据的动作。 |
| 旧引用对应的现场已变化 | 固定新基线、补验证或形成新版本，不改写旧回执。 |

本项目的 `command_id` 不会自动使第三方工具具备幂等性。对方若不能查询未知写入或接受幂等键，必须保留人工对账路径，不能承诺 exactly-once。

### 12.5 降级与退出

选用的上下文服务不可用时，已有任务记录仍应可读，页面显示独立健康状态。辅助记忆缺失与必需证据缺失按第 7 节分别处理。

停用外部服务时先停止新写入和依赖动作，保留版本、来源及必要的获准导出。不静默切换存储，也不让数据库里只剩永远无法读取的引用。

## 13. 运行关联、中断与控制权

### 13.1 完整关联链

```text
任务 → 计划 → 分工 → Attempt
  → 实际运行 ID → 工作区／代码基线
  → 使用的上下文版本 → 产物／验证 → 结果／交接
```

任务上显示的最近会话，不等于当前唯一有权控制的会话。

### 13.2 请求值、观察值、验证值

运行记录建议分别保存：

| 记录 | 内容 |
|---|---|
| Requested | 用户／计划请求的角色、模型、effort、工具和写入范围。 |
| Resolved | 实际送给宿主的可观察启动参数和配置来源。 |
| Observed | 宿主返回的执行 ID、状态与可获取字段。 |
| Verified | 具体行为探针结果；未知字段仍标未知。 |

不要求宿主一定提供全部字段，不通过模型自报填补缺失。

### 13.3 认领与启动

统一业务入口在短事务内检查计划、可信控制绑定、版本、依赖、容量和写入资源，并创建 `prepared` Attempt。事务提交后再调用宿主，不在事务里等待模型或网络。[B1, §6.5、§7.4]

启动已发出但结果未知时，不重复启动。任务服务的资源认领只能约束服务端操作；它不能停止仍持有实际写权限的外部进程。

### 13.4 中断与接管顺序

1. 暂停新派发，读取最新任务、计划和未决 Attempt。
2. 核对实际运行、工作区差异和已形成的证据。
3. 区分“确认未启动”“确认已停止”“仍在运行”“无法确认”。
4. 已停止的执行核对部分成果与副作用，再固定继续范围。
5. 更换 Coordinator 时，由可信人类入口确认接管，原子切换控制绑定和控制代。
6. 旧执行不能继续写当前共享范围后，才按新基线建立后续 Attempt。
7. 迟到结果保留为历史或待核对材料，不覆盖当前计划；有效旧证据可以经核对复用。

原方案明确 unknown 不因超时或服务重启就成为已停止。[B1, §8]

隔离 worktree 只隔离对应文件；共享数据库、外部服务、部署和其他副作用仍需单独核对。不能用“新建了 worktree”推断所有冲突已经消失。

## 14. Hook、自动化与用量观察

### 14.1 不恢复旧 Hook 选型

旧的六 Hook 建议仍是归档材料。[B2] 首个交接闭环不以 Hook 为前置条件，也不假定事件载荷含有准确 token 余额、全部执行 ID 或实际 effort。

### 14.2 本轮新增的文档依据

PowerContext 的 Codex 配置文档描述 `UserPromptSubmit` 路径用于上下文准备与用户输入采集，显式 MCP 工具用于操作记录。[P4] OpenAI 官方 Hook 文档区分配置、启用与对非托管 Hook 确切定义的信任；安装插件不能简单等同于完成全部信任与生效检查。[O3]

这只支持把该接入列为可验证候选，不能据此证明用户当前 App 支持同样入口、默认值或权限效果。文档中 `/hooks` 的 CLI 使用说明也不应原样改成 App 操作承诺。

### 14.3 建议的能力开关

以下是产品设计项，不是 Codex 或 PowerContext 的真实配置键：

| 能力 | 候选初始策略 |
|---|---|
| 人工查看、分析、交接与接收 | 一等入口；依各自读写和执行效果授权。 |
| 自动召回 | 后续项目级显式开启，展示来源和缺失。 |
| 提示词／对话采集 | 与召回分开授权，明确保存位置、保留期和敏感信息。 |
| 自动形成候选记忆 | 单独启用；候选不自动成为已接受规则。 |
| 自动发布长期规则或安装 Skill | 不默认开启。 |
| 定时调用模型评估 | 不默认引入。 |
| Stop 后强迫继续或自动标完成 | 不采用；Stop 不是业务验收。 |
| 自动模型／权限变化 | 不默认开启，包括所谓降档。 |

普通代码的状态刷新不等于模型调用。脚本若把内容注入上下文、生成语义摘要或触发新运行，仍会产生对应开销；不得承诺 Hook 一定零 token。

### 14.4 用量记录

仅记录可靠来源能提供的字段，并保留来源、时间、累计／增量口径。未知值不记成零。

输入、输出、缓存和 reasoning 字段是否重叠必须依据实际计量定义，不能直接相加。上下文窗口、单次生成上限、账号额度、任务预算不是同一概念。用量不能换算成任务完成百分比。

## 15. 最小数据与命令契约

### 15.1 在原模型上增补，不另起一套

保留原有 Project、Task、Plan snapshot、RoleProfile、RuntimeProfile、Assignment、Attempt、Evidence、Decision。[B1]

新增候选记录：

| 记录 | 关键内容 | 实现约束 |
|---|---|---|
| ContextBinding | 项目／任务／工作区与外部 Scope、服务实例的映射 | 版本化；不能把 scope_id 当认证。 |
| ContextReference | family、ID、精确 revision、服务实例、可读性 | 不只存 latest；引用不代表授权。 |
| HandoffRecord | 原 Attempt、计划基线、精确版本、提交／联动状态 | 正式交接和草稿分开。 |
| HandoffReceipt | 接收身份来源、精确选择、结论、检查与时间 | 只代表核对记录，不代替认领。 |
| DiscussionTopic | 问题、参与分工、消息与决定引用 | 评论不能直接写审批状态。 |
| IntegrationOperation | 幂等键、外部结果与对账进度 | 不假设外部系统有相同事务语义。 |

先只建立所选切片需要的表；流程词汇不必全部变成独立实体。

### 15.2 状态保持分离

- Task：保留原 `backlog / todo / in_progress / in_review / blocked / done / canceled` 作为候选基线。
- Attempt：保留原 `prepared / running / succeeded / failed / interrupted / unknown`。
- 交接准备、提交、接收与联动失败：单独记录，不塞进 Attempt 枚举。
- 阶段位置、模型消耗、人类验收：不混成一个“进度”字段。

一次运行成功可以只完成约定子步骤；任务结果可能仍为 partial。记录语义必须明确。

### 15.3 命令意图

以下是本项目候选业务命令，不是宣称现有 MCP 工具已实现：

| 命令意图 | 最小检查 |
|---|---|
| 读取执行上下文 | 当前需求变化、计划、输入引用、未知运行与可访问范围。 |
| 提交计划候选 | 保留来源版本；不自动授予计划执行权。 |
| claim_work | 可信控制绑定、有效计划、CAS、依赖、容量和写入范围。 |
| record_runtime / submit_result | 当前 Attempt、真实运行引用、版本与控制代。 |
| register_handoff | 写入效果已授权，精确外部引用与本地基线可核对。 |
| record_handoff_receipt | 精确交接版本及检查；不由此更改任务为 done。 |
| record_review / record_technical_handoff | 对指定成果和输入版本检验交付条件。 |
| approve_plan / accept_delivery / take_control | 可信人类入口及所见版本。 |
| request_cancel / reconcile | 分开记录意图与观察，未知副作用不重放。 |

写命令带 `command_id`、`expected_version` 和相关任务／计划／Attempt 标识。同键同内容返回原结果，同键不同内容冲突。按任务或相关实体做 CAS，不因普通活动日志变更而无差别重跑全部工作。[B1, §7.4]

新增错误可包含 `CONTEXT_UNAVAILABLE`、`BASELINE_MISMATCH`、`HANDOFF_NOT_COMMITTED`、`RECEIPT_INVALID`、`EXTERNAL_WRITE_UNKNOWN`；字段与名称在实现前和现有错误体系合并。

### 15.4 服务端强制与提示词约定分开

Skill 负责怎样整理问题、解释证据和形成交接。服务端负责身份、版本、认领、输入有效性和人类决定来源；宿主负责实际工具与文件限制。

声明“Reviewer 只读”“不得递归委派”前，必须找到实际约束或行为证据；否则只标为协作约定，不宣传硬隔离。

## 16. 页面与使用体验

首版仍以任务板和任务详情为中心，不重建完整聊天客户端。

### 16.1 任务详情应可回答

当前目标和范围是什么？哪个计划版本有效？谁主责、谁参与、谁评审？实际运行在哪里？哪些证据已通过、哪些未做？下一步应由谁处理？

### 16.2 建议的信息区

- 目标／验收、阶段／分工、当前计划与授权。
- 运行记录：请求配置、可观察配置、工作区、状态来源及时间。
- 协作议题：待回应、未决分歧、已接受决定。
- 交付／交接：精确版本、验证结果、可读性、接收回执。
- 连接状态：页面、业务服务、上下文服务和宿主分别显示。

模型和权限未验证时显示“未验证”，不显示为已经生效。进度以成果和验收项为依据，不用 token、消息数或 Agent 自评百分比代替。[B1, §9]

### 16.3 操作确认应展示实际效果

提交交接前显示保存对象与目标位置；启动前显示计划、角色、实际候选配置、写入范围和执行者；接管前显示旧运行及未决副作用。

“打开任务”“发起只读评审”“评审并修复”“启动执行”不能共用一个含混按钮。对已经明确授权的组合流程，不反复弹出无价值确认，但要能查看授权依据和撤销方式。

原方案 P0–P4 与本文 L0–L5 是不同编号体系；不要把本文切片覆盖成原计划已通过。

### 17.1 首个候选用例

为一个 Web 工具增加“任务筛选并保存视图”。来源为原方案示例，不代表已授权修改任一真实产品。[B1, §5.2]

建议验证：范围澄清、保存位置讨论、接口／前端实现、一次中断交接、独立评审和人类验收。真实项目、写入目录和验收清单在试点前明确。

### 17.2 必须覆盖的行为测试

| ID | 场景 | 通过标准 |
|---|---|---|
| V01 | 两个调用者竞争同一工作项 | 只有一个取得有效认领，不留下半条 Attempt。 |
| V02 | 旧版本或新需求尚未处理 | 拒绝按旧基线派发／提交，并给出原因。 |
| V03 | Agent 冒充人类验收 | 服务端拒绝，不依赖提示词服从。 |
| V04 | 模型／权限请求无法生效 | 明确未验证或不可用，不静默替换。 |
| V05 | 项目、工作区或 Scope 不匹配 | 拒绝依赖该绑定的读写，不回退到默认项目。 |
| V06 | 交接有失败、跳过、未执行或未知测试 | 状态在摘要、接收与结果中保持，不变成通过。 |
| V07 | 交接后代码或需求变化 | 接手者发现差异，旧接收不覆盖新版本。 |
| V08 | 必需证据无法读取 | 不记录无条件接受，说明缺失和解除条件。 |
| V09 | 外部提交成功但业务登记失败 | 可以核对精确引用并补登记，不重复制造正式交接。 |
| V10 | 外部请求结果未知 | 保留未知并查询／人工核对，不盲目重试写入。 |
| V11 | 宿主失联、服务重启 | 不把本地状态更新当成已停止，不在旧可写范围重派。 |
| V12 | 控制权更换后旧会话提交 | 旧绑定被拒，不能凭新控制代重新取得权限。 |
| V13 | turn 结束／进程退出零 | 不自动变为业务 done；按要求核验运行与成果。 |
| V14 | 只读预览交接 | 没有调用业务／上下文写工具，没有新执行。 |
| V15 | 同一任务内咨询 | 只启动获准角色，保留分歧，结论有来源与版本。 |
| V16 | 敏感信息和跨项目上下文 | 未授权内容不上传、不跨项目召回、不进入公共日志。 |

数据库规则用真实临时数据库与竞争请求验证；类型检查、mock 返回值、字符串匹配只证明对应层面，不替代运行证据。

### 17.3 试点结果与停止条件

评价质量、交接遗漏、重复工作、过期信息误用、恢复效果、人工干预和使用负担；耗时和用量为辅助指标，不编造节省率。

Go 至少要求：关键权限和版本规则有效，交接与旧执行处置可核对，无假验收、无未知执行重放，用户接受实际成果。

关键能力不可验证时，停止相关路线或提出降级实验；不能为了展示闭环把“不知道”改成“已完成”。

## 18. 工程组织与技术约束

### 18.1 先尊重仓库现状

本轮没有读取目标仓库当前文件、分支或实现，不知道已有测试是否通过。先检查 `AGENTS.md`、`package.json`、锁文件和迁移，再决定增量修改。

原 v0.5 的 TypeScript、React、Fastify、SQLite 和薄 MCP 可作为已有选型方向。[B1, §6] 本文不确认其旧版本号的当前可用性，不生成未经核验的新依赖组合，不要求为了文档统一而升级全部依赖。

### 18.2 候选目录职责

```text
web/                       任务、角色、证据与决策界面
server/                    统一业务命令、权限和存储
server/context/            可选上下文服务适配，先保持小模块
mcp/                       工具与业务命令之间的薄映射
shared/                    可传输契约与错误类型
migrations/                本项目数据库版本
skills/                    工作与交接方法
roles/                     内置角色定义
test/ 或仓库现有测试目录    单元、集成、行为和宿主探针
docs/                     设计、决策与探针结果
```

目录仅表示职责，实施时沿用真实布局，不为匹配此树搬迁代码。

### 18.3 本地与外部数据

业务数据库只由业务服务写入，Hook／MCP 不直连 SQL；大日志和成果放文件或 Git，数据库保存有界引用。[B1, §6]

采用外部上下文服务时，保持它自己的存储边界，不要求它与业务服务共用 SQLite。用户数据不进入前端静态资源目录，不把 localhost 视作充分身份认证。

默认不自动同步完整聊天、源码、终端日志、环境变量、令牌或未批准附件。是否允许联网推理、嵌入、自动加工与保留资料分别确认。
