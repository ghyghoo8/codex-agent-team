# Codex Team：角色驱动的软件交付方案

> 状态：**Proposed v0.5 — 独立实现与 SQLite 已明确，技术栈选型完成，运行能力待验证**  
> 日期：2026-09-05  
> 本文件是唯一方案入口。按用户要求，由 codex-agent-team 独立实现任务板、本地服务、存储、角色与协作能力；Dashi 只提供一次性的功能与实现参考，不是产品底座或后续维护对象。  
> 本轮完成技术栈选型与方案整理，未编写业务代码、启动产品试点、安装依赖/配置或启用自动化。仓库名保持 codex-agent-team。

## 1. 推荐结论与取舍

产品目标：**一个需求方可以配置专业角色，围绕一个需求完成澄清、选交付方式、组队、分工、执行、评审与验收；任务和成果在本项目自有任务板中可追踪、可续办。**

推荐组合：

- **自有 Taskboard + Team Service + SQLite**：任务板负责展示和人类操作，本地服务及其数据库持有任务、流程规则、执行记录、交付证据和验收的唯一业务状态。
- **Codex Coordinator + Team Skill**：讨论需求、提出计划、调用宿主执行工具、汇总结果。
- **专业角色**：长期保存定义，按任务生成执行实例；角色不等于永久 thread。
- **薄 MCP**：连接本项目 Team Service 的业务命令，不保存第二份任务状态，不承担后台调度。
- **流程预设**：先交付“连续流 + 增量交付 + 必要工程实践”，验证后增加“时间盒迭代”。其他方法有明确演进位置，首版不伪称全部支持。

| 维度 | 评估 |
|---|---|
| Value | 复用角色配置，降低每次解释职责和交付要求的成本；让任务接续依赖证据，减少漏项和上下文丢失。 |
| Cost | 高于接入现成任务板：需要自建基础 UI、数据持久化和业务接口；但首版可排除外部兼容与升级跟踪。主要成本是角色实际生效、原子认领、证据与验收、中断续办。 |
| Net result | 对多步骤、有专业分工的需求有条件正收益；简单修改应走单角色，避免团队协调成本。 |
| Recommendation | **PILOT**：先验证目标宿主能实际运行指定角色，再完成一个可写、可评审、可人工验收的闭环。长期多根与无人值守运行延后。 |

这里的“持续推进”指：Coordinator 执行期间推进已授权且可运行的任务；会话再次进入时按持久记录续办。关闭 App、父执行停止或机器休眠后的后台连续工作，暂不承诺。

**Dashi 的参考边界**：仅使用本次已检查快照中提炼出的能力与机制，结论收在 §12。产品可以在没有 Dashi 仓库、安装包、服务或数据库的机器上运行；不兼容其 API/CLI/schema，不建立 fork、同步、数据迁移或版本跟踪关系。后续取舍由本项目需求、验证与维护成本决定。

## 2. Review：原讨论还缺什么

| 优先级 | 不足及后果 | 本次修订 |
|---|---|---|
| P1 | v0.3 将参考项目误当成运行底座，带入了不需要的集成、兼容与维护关系。 | 本项目独立拥有 UI、服务与数据；Dashi 的价值止于一次性能力提炼。 |
| P1 | 把角色目录、@agent 或专属 Prompt 当作“指定模型的角色已运行”。 | 区分配置请求与运行证据；角色绑定是首个阻断性探针。 |
| P1 | “MCP + Skill 能实现”没有说明谁真正调用原生 spawn。 | Coordinator 调宿主工具；MCP 只返回派发材料和提交业务记录。 |
| P1 | 有任务状态和依赖，并不代表有可执行的流程门禁。 | 在自有 Team Service 实现少量固定业务规则；UI、HTTP 与 MCP 共用，不能只约束 MCP。 |
| P1 | 依赖必须等 done，而 done 必须用户验收，容易让内部交付链停住。 | 依赖引用版本化技术交接证据；人类验收是另一项决策。 |
| P1 | 角色只读、验收权、禁止递归委派被写成提示词要求，却被描述为硬保证。 | 区分宿主权限、服务端授权和协作约定；未证明的限制不得标为已强制。 |
| P1 | “重启后继续”没有覆盖已启动但未记下 ID、已写文件但结果未回报的窗口。 | 派发前记录 attempt；不确定执行先对账，不能盲目重派。 |
| P2 | 七种方法论被拆为多个正交维度后，仍可能演变为任意组合的通用引擎。 | 只发布有明确行为和验收样例的完整预设；不提供规则脚本、任意状态机或组合编辑器。 |
| P2 | 模型档位被当作专业能力/职级。 | 专业能力、流程责任和运行配置分开；按任务难度选算力，记录实际生效配置。 |
| P2 | 缺少可比较的首个场景、成功条件与停下来的依据。 | 使用同一需求推演两种流程，按闭环证据与试点收益决定是否扩展。 |

## 3. 产品范围与一次完整用户路径

首版建议默认：单人需求方、单机、本项目独立的本地试点数据、单个活动 Mission、一个 Coordinator；最多两个同时执行的 Specialist，且受宿主更低的有效上限约束。角色目录可以多于两个，并发席位与角色数量分开。

一次需求按以下顺序推进：

1. **发起**：在自有任务板的 Mission 卡片中记录目标、项目、输入和期望成果。
2. **澄清**：Product 角色协助形成 Brief：用户问题、范围、非目标、验收标准、风险与未决项。人类拥有价值、优先级和范围决策权。
3. **建议**：Coordinator 根据不确定性、依赖与风险，推荐单角色或团队、交付预设、角色及模型配置。
4. **预览与授权**：展示本次计划版本、任务依赖、必需证据、可写范围、预计并发和需要人类决定的节点。已有明确授权在相同范围内持续有效。
5. **执行**：服务端认领可运行任务；Coordinator 启动角色实例；产物、执行引用和阻塞回写 Team Service，在自有任务板展示。
6. **技术交接**：检查输入版本、成果与验证证据；必要评审通过后，下游可以消费指定成果。
7. **用户验收**：展示唯一候选成果和逐项验收清单；用户接受后才进入 done，退回则保留证据并安排返工。
8. **续办**：再次进入同一 Mission，先检查最新需求、已接受成果、未决执行与当前工作区，再继续剩余工作。

普通任务拆分、已授权范围内的重排和窄修复不反复要求确认。范围扩大、模型替换、权限扩大、流程规则变化以及发布/合并等未获授权效果，需要新的具体决策。

## 4. 角色模型：可复用定义，按任务实例化

| 概念 | 内容 | 存放与生效 |
|---|---|---|
| RoleProfile | 职责、边界、专属指令、所需 Skills、输入/输出标准 | 内置模板随本仓库分发；用户编辑的项目角色及不可变版本由 Team Service 保存。 |
| RuntimeProfile | model、effort、宿主、工具与权限要求 | Team Service 保存期望配置；启动时核对目标宿主，记录实际证据。 |
| ProcessAssignment | 本次负责澄清、实现、评审或集成 | 保存在 Mission 计划快照，不等于永久职级。 |
| TeamTemplate | 常用角色组合和默认交付预设 | 可选快捷方式，不是发起需求的前提。 |
| MissionPlan | 已确认 Brief、来源版本、流程版本、角色/运行配置、任务依赖和授权范围 | 一次不可变快照；历史执行不跟随目录编辑改变。 |
| AgentRun | 一个角色执行某项任务的一次 attempt | 持久保存引用；原生子 Agent 是运行实例，不是永久团队身份。 |

专业角色按需要选用：

| 角色 | 核心交付 | 责任边界 |
|---|---|---|
| Product | Brief、验收标准、范围变化建议 | 协助需求方；不能替人类决定业务验收。 |
| UI Designer | 交互方案、视觉规范、可检查的设计成果 | 有独立设计选择时启用；简单样式改动可由前端承担。 |
| Frontend | 界面实现、状态与交互、浏览器验证证据 | 对应 UI 交付范围。 |
| Backend / Business | 接口与业务逻辑、错误路径、直接验证 | 对应业务范围，不默认接管数据迁移。 |
| Data | 数据模型、查询或数据处理及验证 | 存在真实数据职责时启用。 |
| Reviewer | 对指定成果版本的缺陷与评审结论 | 有实质风险时与实现分开；不用“换一个角色名”冒充独立评审。 |
| Coordinator | 组队、分派、交接、整合与状态汇总 | 不默认获得用户验收或外部发布权限。 |

“日常实现 → gpt-5.6-sol medium，复杂工作 → 更高 effort”可作为用户配置示例；不写死可用模型，也不假定更高 effort 必然更好。模型/effort 不可用时保留请求并报告，不静默替换。默认未指定模型时可继承宿主设置，但启动快照必须记录这一选择。

跨任务复用角色定义与经过核准的项目资料，不默认复用无限增长的角色对话。每次输入只带 Brief、已确认接口、当前任务和直接依赖产物；成员间协作经过 Coordinator，首版不做消息总线。

### 4.1 从角色卡到实际执行的闭合路径

推荐生效流程：

~~~text
本项目角色版本
  → 为已选宿主生成不可变配置/派发材料
  → 验证宿主能识别该版本
  → 冻结 MissionPlan
  → 认领 attempt
  → Coordinator 调宿主执行工具
  → 保存 runtime ID 与实际可观察的配置证据
~~~

官方支持 Custom Agent 文件，不等于当前 Desktop 工具支持按角色名动态启动。本轮可见 spawn 工具没有 agent_type、配置路径或 developer_instructions 参数；task_name 只是子任务名。把角色说明放入 message 仅证明传入了工作指令。

目标宿主必须在试点前固定，优先验证用户使用的 Desktop。新建/编辑角色何时被识别、模型配置优先级、权限继承都要实测。配置导出是单向生成物；手改导出文件视为漂移，需要显式导入新版本，不做双向同步。目标工程的 .codex 配置只能在实施获准后安装，本轮不写入。

## 5. 软件开发流程：把选择变成可观察行为

本产品可以借鉴不同方法论，但不宣称简化预设等于完整方法认证。尤其“时间盒 + 回顾”只能叫时间盒迭代；完整 Scrum 还包含其规定的责任、事件和工件。[Scrum Guide](https://scrumguides.org/scrum-guide.html)

| 方法/思路 | 在产品中保留的行为 | 上线安排 |
|---|---|---|
| 看板 | 显式开始/完成定义、容量限制、按容量拉取、显示阻塞与等待 | 首版连续流预设 |
| 迭代/增量 | 将目标切成能独立检查的成果；逐增量交接与验收 | 首版共同基础 |
| Scrum | 迭代目标、时间盒、选入工作、范围调整记录、增量检查与改进 | 后续先做时间盒迭代预设；不直接标为完整 Scrum |
| XP | 根据改动需要启用测试先行、持续集成、评审和重构；证据可检查 | 作为工程实践；不用形式化结对聊天替代验证 |
| 瀑布 | 固定阶段及退出产物；阶段变更需重新检查下游输入 | 有明确阶段交付需求后增加 |
| V 模型 | 需求/设计与相应验证活动的追踪，按当前版本检查覆盖 | 有追踪需求后增加；仅画 V 不算支持 |
| 螺旋 | 风险、实验、证据、继续/调整/停止决定组成一轮 | 有高风险探索需求后增加 |

上述是本产品的取舍映射。看板强调流程定义与 WIP 控制；XP 的贡献集中在互相支持的工程实践；风险驱动和验证追踪也各有不同用途。[Kanban Guide](https://kanbanguides.org/the-kanban-guide/)、[Agile Alliance XP](https://agilealliance.org/glossary/xp/)、[SEI Spiral Development](https://www.sei.cmu.edu/library/spiral-development-experience-principles-and-refinements-spiral-development-workshop-february-9-2000/)、[NASA V&V 与追踪指导](https://www.nasa.gov/reference/system-engineering-handbook-appendix/)

### 5.1 首版只提供一个可执行预设

**连续流交付**：Brief 就绪 → 按优先级与依赖拉取 → 实现/验证 → 必要评审 → 技术交接 → 人类验收。

仅把以下少量内容做成结构化规则：

- 开始条件：授权计划有效、依赖证据有效、没有未处理的需求变化、任务可认领。
- 容量条件：Mission 的派发容量，以及工作区/集成资源占用。
- 提交条件：要求的产物引用、输入版本、验证结果齐全。
- 交接条件：该成果满足当前交接标准，必需评审已通过。
- 验收条件：来自人类入口的接受决定，绑定精确候选成果版本。

需求访谈、拆分技巧、会议提示、回顾方式放在 Skill。规则检查只证明结构、权限与已有证据满足条件；不能从“测试通过”自动推断产品质量或业务价值。

**并发与 WIP 分开**：同时运行的 Specialist 首版最多两个；技术交付 WIP 从首次开始到有效技术交接，已开始的 blocked、验证中和待技术评审项都计入，父议题不重复计数。已技术交接但待用户验收的项单独显示为验收队列。端到端未验收数量另报，不能把技术 WIP 下降当成用户价值已交付。

WIP 数值在试点计划中固定，不等于线程数量。返工重新计入后可能暂时超限，此时允许修复存量、禁止拉取新项；不得通过改成 blocked 规避限制。

### 5.2 用同一需求比较两种流程

讨论用例：为一个 Web 工具增加“任务筛选并保存视图”。这是方案推演，不表示已授权修改某个产品。

共同验收：条件组合正确；刷新后可恢复保存视图；空结果与错误状态清楚；已有任务操作不回归。共同任务为 Brief/接口约定 → 保存能力 → UI 交互 → 集成验证。

| 决策点 | 连续流 | 时间盒迭代（后续试点） |
|---|---|---|
| 选任务 | 有容量且依赖满足就拉取 | 先选定本轮目标与工作集合 |
| 新增“共享视图”要求 | 入 backlog，由需求方调整优先级，不抢占在途写任务 | 检查是否影响本轮目标；记录范围调整，或放下一轮 |
| 角色使用 | Product 按需澄清；实现与评审随任务进入 | 围绕本轮目标一次组队，运行实例仍按任务创建 |
| 交付 | 基础筛选可先形成一个增量 | 检查本轮选定增量与目标完成情况 |
| 超时/未完成 | 暴露阻塞和工作项年龄 | 到时间盒结束记录未完成项，重新排入后续；绝不自动标 done |
| 新增持久内容 | 无额外迭代实体 | iteration ID、目标、起止时间、选入任务、变更记录与复盘决定 |

若第二种流程只是换列名或标签，没有改变选择、变更和交付行为，就不进入实现。运行中的 Mission 不热切换流程；下一 Mission/迭代采用新版本，在途成果沿用原契约。

## 6. 组件边界与唯一数据来源

~~~mermaid
flowchart TB
    U["人类需求方"] --> B["自有 Taskboard / 人类决策入口"]
    U --> C["Codex Coordinator + Team Skill"]
    C --> M["Team MCP 薄适配"]
    M --> D["Team Service 统一业务命令"]
    B --> D
    D --> S["本项目 SQLite 数据库"]
    C --> H["宿主原生执行工具"]
    H --> W["按任务启动的专业角色"]
    W --> C
    W --> A["隔离工作区 / Git / 文档成果"]

~~~

| 所属 | 责任与数据 | 不承担 |
|---|---|---|
| 自有 Taskboard | 角色配置、Mission/子任务、依赖与证据展示、人类确认/验收入口 | 不直接写数据库，不在前端单独判定业务完成 |
| Team Service | 角色版本、任务、计划、认领、运行记录、交接和验收的唯一业务写入者；用 SQLite 持久化 | 不复制完整 Codex 对话，不由聊天结束推断任务完成 |
| Team MCP | 把工具调用转为 Team Service 的结构化命令，返回结果与版本 | 不另存业务状态，不直接执行 SQL 或管理独立根会话 |
| 本仓库的角色模板与 Skills | 提供角色默认定义、需求澄清/分工/交付方法和目标宿主使用约定 | 不代替服务端门禁和运行时权限 |
| Codex 宿主 | 实际模型执行、工具权限、原生子 Agent 生命周期与审批 | 业务任务的最终验收 |
| Coordinator | 对已授权计划作调度选择，调用宿主，提交候选结果 | 自报人类身份、绕过门禁、默认控制其他会话 |
| 文件系统/Git | 代码、文档、提交及测试输出本体 | 用任务库副本替代成果 |

以上产品组件全部在 codex-agent-team 内实现并由本项目发布。Dashi 不出现在运行依赖图中；删除其源码目录或停止其服务不应影响本产品。

薄 MCP 可以是本地 STDIO 进程，通过本项目 loopback HTTP 服务调用同一业务命令。不能反向调用一个假定存在的“宿主 spawn API”；若后端改用 App Server 自行创建独立 threads，则属于 §13 的另一条运行路线。[Plugin architecture](https://developers.openai.com/plugins/concepts/plugins)

### 6.1 技术栈选型

**采用 TypeScript 全栈、React 单页应用、Fastify 本地服务、SQLite + better-sqlite3，以及官方 MCP TypeScript SDK v2。** 一个仓库、一个 npm package、一个长期运行的业务服务；MCP 是宿主按需启动的独立 STDIO 入口。浏览器访问本地页面，业务服务同时负责 HTTP、静态资源与数据库。

以下是 **2026-09-05 的选型基线**，版本已按官方文档和 npm 发布元数据核对；尚未安装或生成锁文件，不代表整套组合已运行通过。实施时固定直接依赖及 package-lock.json，使用 npm ci 复现，不在启动时自动追随 latest。

### 6.2 从参考实现提炼的内部模式

- **统一入口**：UI/HTTP/MCP → 命令校验 → 业务事务 → SQLite。传输层只转换参数；状态规则只有一份。
- **并发写入**：更新使用读取时的 version 作为条件，受影响行数不为 1 即冲突。claim 在同一事务内检查归属、授权、依赖与容量；不能只做一次普通状态移动。
- **交付追踪**：任务 → attempt → 已知执行 ID → 产物/验证/评审引用；重试增加 attempt，历史不覆盖。
- **状态展示**：业务状态、运行观察与人类决定分开，界面明确显示待谁处理。首版按需刷新和读取有界历史，增量 cursor 在确有读取成本时再加。

接口名称、数据表和目录结构由本项目定义；这些模式不要求沿用参考项目的 taskctl、HTTP 路径、字段名或迁移历史。详细提炼与不采纳项见 §12。

**数据边界**：本产品独立数据库是唯一业务来源，Git/文件系统保存产物。首版不连接 Dashi 的本地库或云库，不导入其任务历史；云部署、跨项目任务编排、跨主机和多人协作均后置。

### 6.4 接口、页面数据与代码组织

保持一个 package.json 和锁文件，按 `web/`、`server/`、`mcp/`、`shared/`、`migrations/`、角色模板与 Skills 分责；这些是拟定目录，尚未创建。服务内部将命令处理与 SQL 访问分开即可，不拆独立 Process Kernel、npm 工作区或多宿主适配平台。

HTTP 使用普通 JSON 请求/响应，Zod schema 放在 shared，仅含可传输的数据。HTTP 边界显式 safeParse，MCP 工具复用相同 schema，之后都调用同一业务命令。Fastify 原生采用 JSON Schema/Ajv，**不会自动识别 Zod**；首版不再手写一套重复校验 schema，也不为此添加 OpenAPI/type-provider 插件。SQL 参数化、业务权限检查和数据库约束各负其责，不能用输入合法替代业务合法。[Fastify 校验机制](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)

页面动作成功后 revalidate；MCP/Agent 引起的后台变化通过当前可见 Mission 页面的一条有界刷新循环读取：建议初值 3 秒、一次只允许一个请求；隐藏页面暂停，重新可见时立即刷新，失败时延长间隔。展示最近更新时间与连接错误，低频页面保留手动刷新。不先加 WebSocket/SSE；claim、交接和验收等待服务端确认，冲突明确展示，效果未知的命令不自动重试。

开发时 Vite 将 API 代理到 loopback 服务；交付时由 Fastify 同源提供页面与 API。静态根目录只包含页面构建产物，SPA 回退不能吞掉 API 错误；数据库与项目文件不放在静态目录。人类入口、MCP 凭据和控制会话继续遵循 §7.5，不能把“运行在 localhost”当作可信身份的证明。

### 6.5 SQLite 的具体使用规则

- **单一写入服务**：UI 与 MCP 不打开数据库。数据库放本机数据目录；只保存任务、角色/计划版本、attempt、证据引用和决定，不吞入完整对话或大体积日志。
- **短同步事务**：claim 采用立即写事务，在同一事务内校验并记录 attempt；更新同时检查 expected_version，受影响行数不为 1 则回滚。事务回调不 await，不启动 Agent、不等待网络，也不做长文件扫描。模型执行在提交之后发生。[驱动事务语义](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#transactionfunction---function)
- **显式连接设置**：启用并读回 WAL、foreign_keys=ON、synchronous=FULL，设置有限 busy timeout。WAL 允许读写并行但仍只有一个同时写入者；同步驱动会占用 Node 事件循环，所以只处理有界 metadata 查询。实际测到延迟问题后才考虑数据库 worker。[SQLite WAL](https://sqlite.org/wal.html)、[同步设置](https://sqlite.org/pragma.html#pragma_synchronous)
- **迁移与恢复**：服务启动时按编号事务执行本项目迁移并记录版本，失败不接收业务请求。使用 SQLite/驱动 backup API 备份并验证恢复；不能只复制正在使用的单个 .db 文件，也不能把 WAL 当备份。[在线备份](https://sqlite.org/backup.html)

这只能保证业务记录的事务性，不能把跨数据库、宿主执行和文件写入包装成一个事务；prepared/unknown 与对账规则仍按 §7–§8 执行。

## 7. 最小数据与命令契约

本节描述本项目需要自行实现的业务能力，不是现有 API 清单。数据从空库开始设计，只建立首个闭环需要的记录、索引和本项目迁移；不承担参考项目的 schema 兼容。

### 7.1 自有任务模型与必要记录

- **Project**：项目身份与本机工作目录。首版每个 Mission 只绑定一个明确项目，不引入远程主机映射。
- **Task**：统一的业务任务记录，保存项目、类型、父任务、标题、状态、version 与交付要求。首版只有 Mission 根任务及其一层工作子任务。
- **Mission**：kind=mission 的 Task，加上目标、活动计划、当前可信控制绑定、候选成果与运行控制信息；不再创建一条同义父 issue，不另存一套相互同步的任务状态。
- **Work item**：kind=work 的 Task，parent_id 指向同项目的 Mission。依赖边只连接当前 Mission 的工作项，按 §7.3 的条件检查；不先实现任意任务关系网络。
- **Plan snapshot**：Brief 与需求来源清单、流程/角色/运行配置版本、任务 DAG、交付标准、授权范围。计划 ID 指向不可变内容。
- **Attempt**：attempt_id、task_id、plan_revision、control_generation、可信控制会话绑定、认领版本、已解析的输入产物版本、派发意图、运行引用、工作区范围、观测状态、证据引用。
- **Evidence / Decision**：输入与产物版本、验证方式/结果、评审者及结论、技术交接决定、用户接受/退回决定。任务评论是展示和讨论，不能靠解析任意评论制造已批准状态。

任务 version 保护并发更新，需求来源版本说明“依据什么做”，活动记录用于展示发生了什么，三者不混用。计划保存明确的需求来源及版本；开始前把新增/修改的需求输入纳入检查。新的人类指示尚未处理时阻止新派发，Coordinator 明确归类为原范围内澄清、重大变更或无需调整；普通执行日志不会自动撤销计划。评论与活动独立留痕，不照搬参考项目的 activityKey 作为授权凭证。

### 7.2 任务状态、执行状态和交付状态分开

本项目暂采用七个足够表达当前流程的状态：backlog / todo / in_progress / in_review / blocked / done / canceled。名称采用常见任务语义，转换规则由以下契约定义，不受参考项目状态变化约束。

- backlog：尚未授权执行的需求或候选工作。
- todo：已纳入可执行范围，等待依赖和资源。
- in_progress：实现、验证或必要评审正在进行。
- blocked：有明确阻塞或运行状态待核对，必须记录原因与解除条件。
- in_review：完整候选成果已具备交接所需证据，等待相应检查/用户验收；状态本身不是依赖通过凭证。
- done：人类接受的具体成果版本。
- canceled：停止继续该业务项；不自动证明运行中的进程已经停止。

Attempt 的观测状态可为 prepared / running / succeeded / failed / interrupted / unknown。原生 turn completed 只能影响运行记录；不能直接使任务 done。业务取消仍有未知执行时必须显示“已要求停止，执行待核对”，不能显示“全部已停止”。

### 7.3 依赖与验收：避免人为死锁

计划中的依赖声明上游任务、交付物类型/位置与交接条件，不预填尚未产生的版本。下游 claim_work 在同一事务中选择满足条件的有效交接，将精确产物与证据版本锁入该 attempt；之后的执行、提交与验收都检查这一输入基线。首版只支持两类条件：

1. **technical_handoff**：上游指定版本已有有效交接记录、验证结果和要求的评审结论，下游即可使用；不要求上游先 done。
2. **human_acceptance**：只有需要业务确认后才能继续的节点使用，如需求基线、关键设计或发布范围。

取消、失败和裸 in_review 都不满足依赖。某产物被修订或交接被撤销后，直接消费者标记“输入已过期”；禁止用旧证据继续提交或验收，按影响范围补验证，不笼统重跑所有任务。计划 DAG 要拒绝依赖环。

最终用户可一次接受“父议题 + 列出的必需子项成果版本”。服务端在一次事务中检查清单仍有效并记录决定；任何候选版本变化都拒绝使用旧接受请求。被豁免、取消或失败的项不被顺手标 done。已验收后新增需求建后续任务，保留原验收记录。

### 7.4 少量意图命令

| 调用者 | 命令意图 | 必须保证 |
|---|---|---|
| Coordinator | 读取上下文、提交候选计划 | 返回当前版本与需求变化，不产生授权 |
| 人类入口 | 接受计划、扩大范围、接受/退回成果、确认接管 | 来源可核验，并绑定所见版本 |
| Coordinator | claim_work | 单事务检查计划授权、可信控制会话及控制代、任务版本、依赖、容量及资源；锁定输入版本并建立唯一活动 attempt |
| Coordinator | record_runtime / submit_result | 更新自己的当前 attempt；记录真实 ID；迟到、跨代或旧版本不能覆盖 |
| 评审流程 | record_review / record_handoff | 指定成果和输入版本，检查本任务要求；不能自称人类验收 |
| Coordinator/人类入口 | pause / request_cancel / reconcile | 分别记录期望动作与观察事实，不把请求成功当作执行已停止 |

变更请求携带 command_id、expected_version 和相关计划/attempt 标识；同一 command_id 同一内容返回原结果，同键不同内容报冲突。至少区分 VERSION_CONFLICT、PLAN_CHANGED、DEPENDENCY_UNSATISFIED、CAPACITY_UNAVAILABLE、FORBIDDEN、RUN_UNKNOWN、UNSUPPORTED_RUNTIME，并给出明确可处理原因。

claim_work 先持久化 prepared attempt，再启动宿主。已发出启动而响应未知时不可再 spawn；对这类未知派发，只有明确未启动才可直接关闭该 attempt 并重新派发。已确认停止的失败/中断执行另走恢复路径：核对部分成果与副作用，确定下一次执行基线和剩余范围后，可以在原授权内创建新 attempt；保留旧记录，不把它改成“从未执行”。

这些规则从首版就落到 Team Service 统一命令入口。UI 拖拽、HTTP 和 MCP 不提供绕过 claim/验收的任意状态写入路径；首版也没有需要兼容的旧 CLI、旧接口或自动认领入口。以后新增客户端继续调用相同业务命令，不另建状态规则。

### 7.5 身份与实际权限

人类决策入口与 Agent 命令入口必须区分可信调用来源；role_name、actor 字符串、模型自述或内容 hash 都不是授权证明。首版面向同一可信本机用户，不宣称抵御持有操作系统全部权限的攻击者；应用命令层仍须阻止 Agent 凭据调用人类验收。

派发、运行登记和结果提交还必须核验 Mission 的当前控制会话绑定。绑定由 Team Service 从已授权连接的凭据解析，不能由请求自报；control_generation 只是期望版本，不授予控制权。人类确认接管时，服务端原子更换当前绑定并废止旧绑定：旧会话即使读到了新控制代，也不能重新认领或提交。

期望 Specialist 只取得完成工作需要的工具，任务写入经 Coordinator。但子 Agent 若继承相同 MCP 凭据，这条隔离就没有成立，必须在试点前验证。Codex 沙箱决定实际文件权限，服务端 claim 只约束任务状态，不能停止一个仍有写权限的旧进程。

未能验证人类决策来源或子 Agent 权限隔离时，自动写任务的 Pilot 不通过；可另行选择由人类提交状态的演示，但那是降低保证的实验方案，需要明确同意，不能静默替代。

## 8. 文件协作、中断与恢复

首个可写切片：一个隔离 Mission worktree，同一时刻一个实现者写入；Product、设计建议和 Reviewer 读取固定输入/成果。不能只在 Prompt 写“只读”便视为隔离通过。复杂共享运行环境仍按项目原有规则串行验证。

产品/评审可以并行，涉及同一文件或共享状态的写任务先串行。独立 worktree 并行开发只有在测到必要性后再加。合并、发布、外部通知和生产写入遵循用户实际授权；提交技术成果本身不新增这些权限。

### 8.1 检查点的最小内容

每次计划确认、派发、技术交接、阻塞和暂停形成结构化检查点：计划版本、任务与 attempt、控制会话绑定、工作区/基线、输入和产物引用、已完成证据、未知执行、剩余任务。全量对话留在 Codex，不复制到任务库。

### 8.2 再次进入的判断顺序

新会话可以先做只读核对；任何成果接纳或新 attempt 都要求当前可信控制绑定。若需要换 Coordinator，先完成步骤 5 的接管，再提交步骤 3 的续办决定。

1. 读取最新需求变化、计划和检查点，核对代码/成果引用是否仍存在。
2. 对每个未终结 attempt 核对已知运行 ID、宿主状态、文件差异和证据。
3. 确认已完成：已有且仍符合输入基线的有效证据继续使用；成果已产生但未登记时，由当前控制会话核对来源、版本与验证结果，形成接纳记录后才用于交接。确认未执行时可创建新 attempt；失败/中断且确定已停止时，核对部分改动和副作用，固定新基线与剩余范围后再创建新 attempt。
4. 存在在途或未知执行：保留 blocked/unknown，不因失联或时间过长自动认领。
5. 需要换 Coordinator 时先暂停新派发，处理旧执行；确认旧执行停止或工作区隔离后，由人类明确接管，原子更换可信控制会话绑定并增加 control_generation。旧控制者的迟到提交被拒；这不会废弃换代前已登记的有效证据。未登记成果只能由新控制会话依步骤 3 重新核对接纳，接纳记录保留原 attempt 与当前复核的来源。
6. 若无法证明旧执行已停止，禁止在其可写工作区重派；人类处置并记录成果差异后再决定继续。

暂停只停止新派发，在途可完成；取消先停止新派发并使旧代提交失效，再请求宿主中断，最后核对真实效果。宿主无法枚举/停止的执行保持显式未决。

服务重启后的数据库标记不能作为“旧执行确定停止”或“Mission 已恢复”的证据；本项目必须区分本地记录与运行观察。App Server 的历史 resume 也不承诺恢复崩溃前的在途执行。[App Server](https://learn.chatgpt.com/docs/app-server)

## 9. Taskboard 上需要展示什么

本项目自行实现一个浏览器任务板。首版只需项目/Mission 列表、任务板与详情、角色配置三个基本入口，验收放在 Mission 详情内：

- Mission 根任务：Brief、交付预设、当前计划与授权范围、团队快照、总成果和用户决定。
- 工作子任务：负责人角色、当前运行配置、依赖、工作区、验证/评审证据和待处理问题。
- 运行摘要：正在执行、等待依赖、等待评审、等待用户、运行未知；每项给出下一步责任人。
- 角色配置：先覆盖新增/编辑/版本/验证结果；不先做复杂的角色市场。
- 验收：按标准逐项查看证据，接受当前候选清单或退回具体意见。

模型“请求值”和“已验证值”分列；没有证据时显示未验证。进度使用已交付/总工作项及阻塞情况，不从 token 消耗或聊天长度伪造完成百分比。

设计时只借鉴“任务板 + 详情 + 活动/证据”的有效信息组织，不复刻参考产品的页面全集。甘特图、复杂富文本、完整聊天窗口、外部议题同步和多种展示模式均不作为首版要求。

试点价值评估使用一个小需求和一个有专业分工的需求，与“单会话 + 常规 subagent + 手工任务记录”比较。观察准备成本、人工干预、返工、结果质量、耗时和能实际获取的模型消耗；缺少计费证据时不编造金额。

**Go 的必要条件**：上述核心探针通过，用户接受交付质量，没有重复执行或假验收，并且重复使用的收益值得配置与维护成本。具体可接受耗时/消耗门槛在试点开始前由需求方确定，不在没有样本时声称提效百分比。

**停止或缩减范围的条件**：

- 指定角色/模型只能显示在 UI，实际运行无法确认。
- 核心调用需依赖 UI 注入、私有协议或 Dashi 的安装/服务/数据。
- 任一写入口、继承凭据或自报身份可以绕过必需规则。
- 不明执行被自动重派、用户未验收却标 done，或旧成果可覆盖新计划。
- 团队协调、配置或恢复成本持续高于单会话基线。

任何宿主、模型、工具、数据来源或保证级别的替换都要明确展示，由用户选择，不能自动 fallback。

当前没有可迁移的 Team 运行数据，也不安排从 Dashi 迁入数据。未来本项目升级只维护自己的 schema 与记录；缩减自动执行能力时，先停止新派发并处置在途 attempt，保留任务、证据与角色快照，回到自有任务板可人工续办的状态，不删除历史或接回外部任务板。

本方案已确定独立实现、自有数据与界面、SQLite、一次性提炼参考能力、不跟踪 Dashi 迭代；技术栈按 §6 的选型基线实施。建议默认值为单人、本地隔离试点、连续流、一个 Coordinator、按任务角色、最多两个 Specialist、单写 worktree、人工最终验收、无后台无人值守。

真正需要在实施入口决定的只有：

1. 第一个真实需求与其项目、可写边界和验收标准。
2. P0 验证的目标宿主；若 Desktop 不支持所需配置，是否愿意明确改选 CLI/App Server 或降低保证。
3. 试点可接受的人工干预、时间与模型消耗范围。

这些选择不阻碍本轮方案审查。本文仍为 Proposed；接受方案不等于已执行探针、完成安装或具备生产能力。
