## 1. 总体结论

本项目是**任务驱动、角色参与、证据可追溯、可中断续办的软件交付工作台**，不是插件商店、会话收藏器或自动模型调度系统。

```text
需求与验收标准
  → 任务／计划／角色分工
  → 确定能力版本、明确授权、检查实际就绪
  → 执行、咨询、验证和评审
  → 有证据的交付或上下文交接
  → 新会话核对并在有效控制权下继续
  → 人类验收精确成果
```

Wake 带来的新增能力是：**没有提前整理好交接时，也能从获准的原始工作资料中找回依据，再核对现场、形成恢复材料。**它是正常交接的补救路径，不替代主动记录结果，也不构成自动恢复执行。

技术栈建议保持 **TypeScript + React/Vite + Fastify + SQLite**。新增历史解析按需放到 Node 工作线程，搜索采用 SQLite FTS5；Rust core 是后续有明确收益时的局部选择，不整体改写为 GPUI。

## 2. 决策状态与范围

### 2.1 保持有效的边界

| 议题 | 处理 |
|---|---|
| 主要宿主 | Codex App；本机版本、实际能力和接入路径需验证 |
| 成本优先级 | token 成本降低优先级，不牺牲质量、授权或可靠性；仍如实记录用量 |
| 角色能力管理 | 声明依赖、确定版本、就绪检查、Attempt 快照；不做通用插件管理中心 |
| 业务权威 | Team Service 管任务、计划、认领、证据接纳、控制绑定与验收 |
| 运行变化 | 模型、effort、权限、角色、来源和宿主变化须在明确授权内；所谓降档也不例外 |
| 已归档 | 旧动态调度、自动降档、整组 Hook 草案不恢复 |
| 明确排除 | 不引入 RocYan98/CodexBoard 的远程路线 |
| 外部参考 | Todos、Dashi 供提炼；SkillBox、PowerContext 是可选来源，不是已决定安装的依赖 |
| 本轮新增 | 历史资料与证据重建的候选能力；不默认引入 Wake 全产品 |

最终云端或本地部署仍未因本专项而定案。建议先在一个本地项目、一个活动 Mission 上验证，不把“交给本地开发”误解成永久只能本地部署。

### 2.2 首版不增加的产品线

不建设全平台会话扫描器、原生桌面壳、通用插件市场、自动依赖安装器、全量聊天同步、常驻角色群聊、模型路由器、无人值守执行服务、跨主机同步或通用工作流编排器。

历史模块不提供删除第三方会话、不自动 resume、不直接打开外部深链。未来确有需求时另立效果、授权与宿主验证。

## 3. 五个参考方向如何组合

| 来源 | 提炼的能力 | 本项目保留的额外边界 |
|---|---|---|
| Todos | 任务承载规划、执行、评审与多次运行 | 不把现成工作台自动改为产品底座 |
| Dashi | 统一业务命令、CAS、执行关联、故障与恢复 | 提示词约定不能代替服务端和宿主门禁 |
| PowerContext | 记忆、精确交接、来源与接收回执 | 不成为任务授权或业务状态的第二权威 |
| SkillBox | Skill 资产、精确版本、完整包、提案与发布 | 当前 ACL 与任务选择分开；可变 Bundle 不替代能力锁 |
| Wake | 会话发现、共享解析、FTS、无界面读取与更新 | 阅读视图不等于原始证据；过滤不等于任务 ACL |

这是职责分工，不是安装清单。源码依据编号 `WK01–WK18` 见 [Wake 源码审阅](wake-source-review.md) 和 [原始行号摘录](wake-source-evidence.md)。其他参考沿用已有交接及能力 v0.3，本轮未重新认证这些产品。

## 4. 推荐架构与事实来源

```text
人类入口：任务板／当前 Codex 会话
               │
       计划、范围、参与角色、决策
               ▼
          Team Service
       统一业务规则与身份检查
          ├─ 任务／计划／Assignment／Attempt／Evidence／Decision
          ├─ 能力解析与检查 → 仓库固定 Skill；可选 SkillBox
          ├─ 上下文适配 → 精确交接；可选 PowerContext
          ├─ 历史资料模块 → 获准来源、快照、解析、派生索引
          └─ 已验证的宿主路径 → Codex 角色执行 → 工作区／Git
               ▲
       Team MCP：窄业务工具，不另存状态
```

历史模块可以先是 `server/history/` 内几个文件，不是独立平台。耗时解析与索引在有界工作线程运行；它不能写验收、启动模型或抢占控制权。

| 事实 | 主要权威 |
|---|---|
| 当前任务与批准范围 | Team Service 中的可信人类决定和精确计划 |
| 原始文件当时捕获的字节 | 获准保存的 SourceSnapshot，不是可变路径 |
| 历史内容的解释／排序／搜索 | 派生视图与索引；可重建、可不完整 |
| Skill 内容版本 | 明确选定的维护源；本项目保存精确引用与获准副本 |
| 当前实际代码与测试 | 指定工作区、Git 基线和对应验证记录 |
| 当前执行是否停止 | 宿主可观察事实；无法确认即 unknown |
| 历史记录是否适用于当前任务 | 当前控制方在授权内完成的核对与接纳 |
| 用户是否接受成果 | 可信人类入口的精确成果验收 |

原始日志也是可修改资料：内容 hash 证明所存字节一致，不证明该日志由谁真实执行生成。来源可信度、内容完整性、现场一致性和执行权限分别检查。

## 5. 任务、角色和执行模型

继续使用现有概念，不因每次研究新项目就重命名一套实体。

```text
Mission（根 Task）
  └─ Plan revision
       └─ Work item + Stage
            └─ Assignment
                 ├─ RoleProfile revision
                 ├─ RuntimeProfile / authorization_ref
                 ├─ CapabilityLock
                 └─ Attempt(s)
                      ├─ Requested / Resolved / Observed / Verified
                      ├─ 工作区／输入基线
                      ├─ 核验及成果 Evidence
                      └─ Handoff／历史来源引用
```

Stage 是有限阶段属性，不急于做可编辑流程引擎。RoleProfile 说明专业责任，Assignment 说明本次主责／协作／评审，Attempt 说明一次真实执行；角色不是常驻线程。

多个角色可以串行协作或并行只读。首个写入闭环采用单一工作区写入者。一次明确授权可以覆盖有限咨询、评审和窄修复；增加参与者、范围、运行配置或发布效果时再检查授权。

业务状态、运行观察、资料采集状态分别保存。不会因为消息出现 `done`、进程退出零、历史有“已经完成”，就改变任务的业务验收状态。

## 6. 能力专项 v0.3 继续作为执行前提

本次不重写已有专项，保留以下链路：

**角色声明 → 计划固定选择 → 启动前静态检查 → 受控启动 → 业务动作前会话核验 → 实际交付快照 → 接手重新核验。**

Skill 正文、引用文件、脚本和模板应覆盖完整选定清单；资产 ID 或稳定 URI 不等于不可变版本。Bundle 选择展开为具体叶子版本，当前权限撤销仍独立生效。

读取指引、下载文件、原生加载和执行脚本是不同效果。通过 Wake 找到历史中的 Skill 名称，只能作为使用线索，不能替代当时 CapabilityLock，更不能证明当前会话已获得同一内容。

历史解析会过滤一些系统／配置元信息，因此它尤其不能替代实际宿主配置与权限探针。[WK04]

## 7. 历史模块：先解决一项具体问题

### 7.1 目标与非目标

目标是支持：寻找旧工作、定位相关片段、核对当时记录、在异常中断后重建恢复依据。

非目标是：自动把历史整理成事实、自动写长期记忆、自动生成 Skill、自动给任务匹配“最近会话”、自动继续旧执行。

### 7.2 两条恢复路径并存

| 场景 | 流程 |
|---|---|
| 已有正式交接 | 读精确版本 → 核对资料与现场 → 接收记录 → 处理执行权 → 创建后续 Attempt |
| 没有正式交接 | 明确来源范围 → 捕获／读取历史 → 提出证据候选 → 核对现场 → 形成恢复材料 → 处理执行权 → 创建后续 Attempt |

历史补救不是正常交付的替代品。已完成的验证和决定仍应及时登记，不能设计成“最后扫描聊天就能自动还原一切”。

### 7.3 来源授权先于扫描

首版由人类选择一个具体 JSONL 文件、一个获准导出，或已有任务绑定的明确来源。Agent 只能使用已登记的 `source_ref`，不能传任意绝对路径让服务以自身权限读取。

目录发现与内容读取分别授权。即便只读取元数据，也可能暴露其他项目名称与路径。不要从一个项目目录自动提升到整个 CODEX_HOME，不按日志中的 project 字段自动授权，不在匹配失败时退到全库。

如果未来使用 Wake 原生全库索引，只能作为已明确批准的个人探索路线；不能同时宣称具有任务级最小访问隔离。[WK03、WK10]

## 8. 来源快照：把“可找到”升级为“可核对”

### 8.1 三种对象分开

| 对象 | 职责 | 能否随时重建 |
|---|---|---|
| SourceSnapshot | 本次允许保存的原始字节、范围、来源观察、摘要 | 来源仍存在时可重新捕获，但产生新版本，不覆盖旧版 |
| TranscriptView / SearchIndex | 解析、折叠、排序、搜索和显示 | 可以；必须保留 parser/index revision 与诊断 |
| EvidenceReference / Adoption | 某个任务为何采用某片段、核对了什么、谁接纳 | 业务历史，不随索引清空而丢失 |

没有获准保存完整文件时，可以只保存选定范围及必要上下文；必须如实标注范围，不能称为“整个会话快照”。原始敏感内容和可共享脱敏派生物分别有 digest 与访问策略。

### 8.2 对追加中 JSONL 的捕获约束

1. 服务端解析已授权 source_ref，核对实际路径、文件类型、允许根和链接策略；拒绝未批准的路径扩张。
2. 打开后记录文件身份、大小及观察时间。按批准范围捕获字节，不无限追赶持续增长文件。
3. 对追加日志，以完整换行边界形成本次范围；末尾不完整行标记 `partial_tail`，不默默丢弃后称完整。
4. 对实际捕获字节计算摘要，写入隔离暂存，再按目标文件系统已验证方式提交；文件与业务记录跨介质不是原子事务。
5. 前后发现截短、替换或可观察的修改时中止或生成需复核版本，不能依赖 mtime/size 判定完全相同。
6. 即便前后 stat 相同，也不证明与并发写者形成了一个瞬时一致快照。记录捕获策略；对需要强现场一致性的证据，须结合停止后复核或源提供的可靠快照能力。

`sha256` 是对捕获字节的完整性标识，不是全局时刻、身份认证或运行停止证明。不能宣称文件 hash 检查等于文件系统锁定。

### 8.3 正式锚点

内部候选结构如下，不是 Wake 原生接口：

```json
{
  "source_ref": "<受控来源身份>",
  "snapshot_ref": "<不可变捕获版本>",
  "snapshot_sha256": "<捕获字节摘要>",
  "source_kind": "codex_rollout_jsonl",
  "spans": [
    {"byte_start": "<范围内偏移>", "byte_end_exclusive": "<范围内终点>", "event_id": null}
  ],
  "parser_revision": "<解析规则版本>",
  "view_seq": null,
  "claim_ref": "<拟支撑的具体说法>",
  "availability": "available",
  "verification_ref": "<现场核对记录或null>"
}
```

示例使用占位符；实现中偏移使用经过范围校验的非负整数，禁止精度损失。一次工具调用和返回可能分属多个不连续 span；同一任务也可以关联多个会话。不要只存 `native_id + seq`。[WK02、WK04、WK11]

## 9. 解析契约：宁可展示不完整，不把未知变成成功

### 9.1 建议输出

解析只处理指定 snapshot，产出统一事件视图和独立 ParseReport。建议事件至少保留原始 kind、角色／来源、原始定位、时间及是否推断、工具 call_id、可观察退出结果、正文／输出类别、截断与过滤标记。

ParseReport 至少区分：

| 维度 | 例子 |
|---|---|
| 来源读取 | 成功、权限拒绝、缺失、读取中变化 |
| 格式解析 | 已识别、坏行、未知顶层、未知嵌套类型、schema 不支持 |
| 内容转换 | 包装清理、继承历史折叠、重复消息合并、Meta 过滤 |
| 完整性 | 完整到指定边界、partial_tail、大小限制造成的截断 |
| 工具结果 | 成功／失败／未知／未报告；不能把 false 默认值当成功 |
| 覆盖率 | 针对捕获范围的计数与缺口，而非整个机器／整个任务的完成率 |

机器计数可用于发现缺口，不自动等于“语义理解完整”。特别是一个未知类型被 `_ => {}` 忽略时，不能用坏行计数为零证明无遗漏。[WK04–WK06]

### 9.2 检索视图与证据视图

为阅读折叠 Meta、父历史和重复消息是合理优化，但应能回到获准原始 span。首次可只支持正文、工具调用与输出、压缩标记；已记录的可见思考摘要默认不检索、不注入，绝不尝试还原加密或未公开内部思考。

解析状态必须贯穿 worker → 索引 → 服务响应 → UI → 交接。原 Wake 的 `unknown_line_count` 到索引列的传播缺口正说明只在 parser 中维护计数不够。[WK05]

### 9.3 多会话和子 Agent

父子关系、继承历史、同名副本都标来源及观察可信度。关系不足时标未知，不靠“最近时间”强行拼接。不自动把子会话映射成某个 RoleProfile；只有实际 Assignment／运行记录或经过核对的关联才算业务联系。

## 10. 检索：先用关系型索引，不引入新的 AI 系统

### 10.1 首版查询范围

可以先对选定 snapshot 的小集合检索；多会话查询需要时加入独立派生索引。结果必须带：scope、snapshot、parser_revision、searched_fields、truncated/partial、next_cursor 和诊断摘要。

正文、工具输入、工具输出、配置材料分别分类。Wake 当前派生 FTS 没有工具输出，所以“搜不到 error”不能推出“测试没有失败”。我们的错误恢复场景可以索引获准的结果文本，或提供对指定原片段的有界查找，不默认全量索引所有输出。[WK07]

### 10.2 建议检索实现

采用 SQLite FTS5 trigram，适用于代码子串和至少三个 Unicode 码点的字面量。短词另用受项目、时间及工作量限制的 LIKE 路径；必须转义 `%`、`_`、反斜线及 MATCH 引号。实际 SQLite 编译配置须做探针，不能因为安装了某驱动就认为 trigram 可用。[O2]

搜索结果只作候选来源。相关性排序、时间新近或出现次数不等于证据权重；不能选取“通过”片段而忽略稍后的失败。

### 10.3 一致性与分页

搜索绑定索引 generation 与 snapshot。读取结果时沿用同一 snapshot，不现场读取最新版后声称是同一命中。查看更新版需要明确新来源引用。

消息分页与长消息内部字节分页分开；紧凑输出中被截断的单条工具结果，不能靠 next_seq 假装能完整续读。游标须绑定授权范围和 snapshot，拒绝被篡改、过期或跨项目使用。[WK11–WK12]

### 10.4 新鲜度

不使用单一 `fresh=true`。至少记录 `last_scan_started_at`、`last_scan_finished_at`、`scan_status`、`source_results`、`captured_boundary`、`parser_revision` 和 `latest_source_activity_at`。

`completed` 只能表示此次声明范围内的扫描工作结束。源离线、解析失败、扫描超时或未覆盖的目录要分别列出。不能用 `MAX(updated_at)` 证明全量覆盖。[WK08]

## 11. 历史片段如何成为可用恢复依据

### 11.1 接纳流程

```text
历史命中／人工选片
  → 建立候选说法与精确 span
  → 核对资料是否完整、是否在当前任务范围
  → 对照实际代码、需求、验证结果和运行观察
  → 当前可信控制方在授权内接纳为 Evidence
  → 编制恢复材料／Continuation Package
  → 接手者再次核验能力与现场
  → 处理旧执行和控制绑定
  → 新 Attempt
```

接纳者可以是计划授权的当前 Coordinator，也可以是人类；不能把每条证据都强制变成人工最终验收。但 Agent 自报的 `accepted_by` 字符串不是可信身份，服务端仍需校验来源及版本。

### 11.2 恢复材料内容

在现有交接包基础上增加历史来源清单、捕获／解析版本、支撑每条关键说法的片段、损坏／截断／不可读项、已补验证和未补验证。

现有 goal、scope、决定、完成/部分/未开始、Git 基线、未提交及未跟踪文件、测试、风险、下一步和停止条件继续保留。不要把正式交接包做成原始对话全集。

### 11.3 四种结果分开

```text
历史资料找到 ≠ 说法正确
说法被接纳为当前依据 ≠ 原运行已停止
接手确认 ≠ 获得执行权
技术交付通过 ≠ 人类验收
```

历史里有“Stop”或“完成”不能解决 unknown execution。若不能证明旧写入者停止或隔离，继续阻塞相同可写资源；新 worktree 也不能自动隔离共享数据库或远端服务。

### 11.4 PowerContext 与 SkillBox 的位置

恢复材料可经授权提交到 PowerContext，并记录外部精确 revision；外部提交和 Team Service 登记分别对账。当前范围内的合法本地方案无需先部署外部服务。

历史经验可以成为 Skill 提案依据；不自动写长期规则，不自动发布 SkillBox 新版本，也不让新版本改变在途 CapabilityLock。

## 12. 存储、权限和操作效果

### 12.1 建议的最小存储边界

| 存储 | 内容 | 写入者／恢复规则 |
|---|---|---|
| `team.db` | 任务、角色、计划、授权、Attempt、Evidence、接纳及引用元数据 | Team Service 唯一业务写入者；备份与迁移，不自动清空重建 |
| `history-index.db`（搜索切片启用时） | 派生消息、FTS、解析／索引版本与扫描覆盖 | 一个逻辑索引写者；可重建，不保存唯一业务决定 |
| `artifacts/` | 获准原始快照、验证日志、脱敏导出 | 服务控制的有界存储；引用和完整性可核对 |

首个单文件场景可以没有独立索引库。已有实现若用单库，也可先严格区分可重建表与权威表；不能为照搬目录树而迁移数据。选择分库后不做跨库原子事务承诺。

索引失败不删除已接纳 Evidence。源丢失先标 unavailable；源删除、索引删除、获准副本清理和业务记录保留是不同操作。[WK14]

### 12.2 文件与数据库联动

捕获采取 prepared → staged → committed/linked 等有限记录，故障时只对账本项目拥有的产物，不扫描并清理整个磁盘。正式引用前核对文件存在、digest 与授权。持久化失败不声称已有完整证据。

外部 SQLite 正常 readonly 查询与“复制三个文件”不同；后者不自动一致。对需要一致备份的来源优先使用适用 Backup API，或获准停止后捕获；无法建立条件时降为不可用观察，而不改写源库。[WK13、O3]

### 12.3 权限必须作用于每条读取路径

列表、搜索、取正文、读工具输出、遍历子会话、读记忆、导出都检查真实身份与项目／来源范围。MCP 参数 project_id 不授予权限。响应不返回未授权候选项目、私人绝对路径或完整凭据。

独立 Worker 是性能边界，不是 OS 安全沙箱；源访问仍须使用可信适配代码与受控凭据，不能把任意脚本或模型提供的路径交给 worker 执行。[O4]

### 12.4 操作效果矩阵

| 操作 | 可能效果 | 不附带发生 |
|---|---|---|
| 查看既有任务／扫描状态 | 读本项目记录，正常访问审计 | 不扫描源、不运行模型 |
| 一次来源捕获 | 读取指定内容、写获准快照和诊断 | 不扩大目录、不上传外部服务 |
| 更新索引 | 写派生数据库、有界文件读取 | 不改任务状态、不自动继续 Agent |
| 读取精确片段 | 读受控快照、返回有限内容 | 不调用外部推荐模型 |
| 提议／接纳证据 | 记录候选及可信决定 | 不授予执行权、不人类验收 |
| 生成恢复材料 | 在已授权范围内整理、必要模型分析、保存草稿 | 不默认发布记忆或 Skill |
| 继续工作 | 另经计划、就绪、认领和旧执行核对 | 不因历史找到就启动 |
| 清理派生索引 | 仅重建/删除本项目派生数据 | 不删除第三方会话、原始证据或验收历史 |

安装、认证、目录扫描、自动监听、跨服务上传分别授权。索引更新不调用 LLM；若未来使用语义检索或摘要，必须独立声明内容去向、预算和返回证据方式。

## 13. 技术栈建议

### 13.1 推荐组合

| 层次 | 建议 | 理由与验证要求 |
|---|---|---|
| 运行环境 | **Node.js 24 LTS + TypeScript strict/ESM** | 沿用项目方向；官方发布页所示 24 为 LTS。补丁、TypeScript 版本在本地锁定，不从旧方案抄具体数字。[O1] |
| 前端 | **React + Vite**；沿用现有路由、样式与组件 | 页面仍是任务、角色、证据；无需 GPUI/SSR/全新聊天客户端。构建与插件版本以实际锁文件为准。[O9] |
| 业务服务 | **Fastify**，复用单服务结构 | 同一命令层供 UI/HTTP/MCP；不因参考项目使用不同框架而迁移。[O5] |
| 传输校验 | **Zod 或仓库现有 schema 方案** | 明确边界校验与版本；不要维护互相漂移的多套业务规则 |
| 持久化 | **SQLite + better-sqlite3（优先沿用已有）**，参数化 SQL、编号迁移 | 有同步事务、readonly、backup 能力；事务不 await、不等模型或外部 I/O。需验证目标架构原生驱动、SQLite 编译选项。[O6] |
| 历史搜索 | **SQLite FTS5 trigram + 有界 LIKE** | 首阶段不引入 Elasticsearch、独立向量服务；短词和索引同步须实测。[O2] |
| 采集与解析 | **Node fs 字节流 + 有界 worker_threads** | 保留原始 span；较大的解析、hash、FTS 写入移出服务事件循环。不是每次请求新起线程。[O4] |
| 文件完整性 | **node:crypto 的 SHA-256 + 明确 manifest 格式** | 与 Skill 资产共用完整性思想，不共用语义身份或授权 |
| MCP | **官方 TypeScript SDK**，窄工具映射 | 复用既有 Team MCP；不复制 Wake 自写 JSON-RPC、不混淆协议版本和能力保证。[O7–O8] |
| 测试 | **现有 Vitest + 真实临时 SQLite；Playwright 关键闭环** | 源码 fixture、故障注入、权限拒绝、跨会话恢复；mock 不能证明真实事务／宿主行为 |
| 格式与质量 | 沿用仓库 lint/formatter/typecheck | 不为统一文档升级整个工具链 |

本轮未安装此组合，不能写成已联调通过。技术栈建议是模块级选择，不提供未经验证的“最新版本全家桶”。官方 MCP SDK 页面本次显示 v1 文档；与旧方案硬写的 v2 基线不同，实施时必须以实际发布包、宿主兼容和锁文件核对，不从旧文本推导已安装版本。

### 13.2 为什么不整体采用 Wake 的 Rust + GPUI

Wake 的选择服务于原生多平台会话浏览器；我们的主产品是现有任务业务、角色配置和证据工作流。全部重写会增加 UI、打包、IPC、数据库和测试链路迁移，但不会自动解决任务 ACL、证据快照和控制权。

**建议不是“Rust 不适合”，而是当前没有证据表明整体重写能抵消迁移成本。**如果真实历史负载不大，一个 Codex 格式适配和 SQLite 足以完成第一轮价值验证。

### 13.3 Rust 的合理进入条件

| 方案 | 适用条件 | 当前态度 |
|---|---|---|
| TypeScript 实现一个选定格式 | 当前主要 Codex，首先验证业务契约 | 推荐首个切片 |
| TS 业务＋Rust 解析子进程 | 多 Agent 格式适配确有需求，或性能／复用收益已测得 | 可选后续；明确源码版本、稳定输出 schema 和进程权限 |
| 直接接 Wake CLI/MCP | 只需要个人资料探索，能接受其范围和视图限制 | 仅独立试验，不当成正式证据或角色 ACL |
| 整体 Rust + GPUI | 产品改成原生多平台资料浏览器且团队愿意承担 | 不属于当前路线 |

若选择 Rust 子进程，优先 stdio JSONL 请求／响应，固定二进制和协议版本，传已批准来源引用或受控句柄，不传任意 shell 文本。输出严格 schema、请求 ID、snapshot、diagnostics、limits，stderr 只放脱敏诊断。初期不做 N-API／FFI、通用插件加载器或网络微服务。

Wake 原 CLI 输出格式化文本，不能不加版本契约就解析其自然语言响应当稳定 API。wake-core 虽与 GUI 分开，仍含清理和平台功能，复用前须有针对性裁剪／包装及回归验证。[WK01、WK17]

### 13.4 何时才换数据库或加消息基础设施

云端、多用户、多写实例成为明确需求时，再比较 PostgreSQL、对象存储和认证方案；不要因为一个历史索引就上数据库集群。首版有界后台任务可用现有服务内队列与持久操作记录，不需 Redis／消息总线。

持续监听与增量索引需要时再增加，明确唯一索引写者、取消、背压和失败状态。SQLite SQL写锁不替代逻辑扫描锁。[WK09]

## 14. 建议的代码职责与接口

以下是候选职责，实施时映射到真实仓库，不为匹配目录搬迁已有实现。

```text
web/                         任务、角色、历史片段、证据与决定
server/commands/             统一业务命令、授权、CAS
server/capabilities/         既有能力锁与就绪检查
server/history/
  sources                    受控来源登记和访问范围
  snapshots                  原始字节、span、完整性与清理策略
  parsers/codex               选定 Codex 格式；逐版本 fixtures
  projection                 统一阅读视图＋ParseReport
  index                      派生索引、覆盖、新鲜度、查询
  worker                     有界任务执行，不控制模型
server/evidence/             候选、接纳、现场核对与失效
server/context/              可选 PowerContext
shared/                      传输 schema、原因码、版本
mcp/                         现有窄工具面
migrations/                  业务与可选派生索引各自版本
skills/ / roles/             已审阅指引和角色定义
```

### 14.1 最小数据扩展

优先复用 Evidence、ContextReference、IntegrationOperation、Plan 和 Attempt。候选新增类型为 `HistorySource`、`SourceSnapshot`、`SourceAnchor`、`ParseReport`、`ScanReport`；类型不代表必须五张独立表。

- `HistorySource`：来源身份、允许范围、归属、数据保留和内容访问策略。
- `SourceSnapshot`：获准捕获范围、文件观察、字节摘要、产物引用、状态。
- `SourceAnchor`：精确原始片段与派生视图位置。
- `ParseReport`：parser版本、识别、过滤、失败与截断。
- `ScanReport`：此次范围、各源结果、截止边界与未覆盖项。

任务验收和控制权不存入这些派生对象。零值表示真实观察到零；未知为 null/unknown，并附原因。

### 14.2 候选业务命令

| 意图 | 最小检查 |
|---|---|
| 登记一个历史来源 | 可信用户、路径与项目、捕获和保留范围；不是直接扫码全机 |
| 捕获指定来源版本 | 来源授权、大小／类型／路径、原始内容效果、幂等和故障对账 |
| 搜索任务允许的资料 | 服务端 scope、字段覆盖、snapshot/index代次、有界扫描 |
| 读精确片段 | 每次 ACL、完整性、范围、游标与脱敏策略 |
| 提议／接纳历史证据 | 当前控制绑定、任务基线、所支撑的说法与核对依据 |
| 形成恢复材料 | 精确证据、未决项、现有授权、保存效果 |

这些不是已经存在的 API 名称。是否拆新 MCP 工具由现有接口决定；不要为了每个业务名词增加工具。UI/HTTP/MCP 共用规则；写入继续采用 command_id、expected_version、关联任务和 Attempt。

可映射的原因码：`SOURCE_SCOPE_DENIED`、`SOURCE_CHANGED`、`SNAPSHOT_UNAVAILABLE`、`PARSE_PARTIAL`、`FORMAT_UNSUPPORTED`、`INDEX_PARTIAL`、`ANCHOR_STALE`、`EVIDENCE_CONFLICT`。沿用现有错误体系也可以，但不能统一报“没有找到历史”。

## 15. 页面及使用体验

不新增历史管理中心，先在任务详情增加“相关工作资料”。用户能看到来源、精确片段、前后文、截断和解析警告、当前采用状态。

显示顺序建议：任务结论／待处理问题 → 支撑证据 → 可展开原片段；不是先倾倒全部聊天。用户应能区分“来自旧记录的说法”“当前现场已验证”“仍未验证”。

搜索无结果时提示查询字段、范围和未覆盖项。明确按钮“查看历史”“捕获资料”“作为候选依据”“接纳依据”“请求接续”的不同效果。“打开旧会话”不是恢复成功，不混入当前首版按钮。

## 16. 实施顺序：把新增能力嵌入旧路线图

| 切片 | 对原规划的关系 | 最小交付 | 不带入的工作 |
|---|---|---|---|
| I0 现状对齐 | 总体 L0／能力 C0 | 真实仓库、模型、锁文件、宿主与授权核对 | 不假设空库，不重新创建已有系统 |
| I1 原有任务交付闭环 | 总体 L1–L2／能力 C1–C2 | 一个角色、固定 Skill、认领、真实运行、证据和验收 | 不要求先做历史扫描或外部 Provider |
| I2 指定历史恢复 | 总体 L3 的异常路径补充 | 一个获准 Codex JSONL、不可变范围、ParseReport、片段接纳、一次新会话续办 | 不要求全库搜索、监听、状态库或 Wake安装 |
| I3 有界历史搜索 | I2 真实有用之后 | FTS5、短词回退、明确覆盖、snapshot锚点、权限及索引重建 | 不加向量库、外部摘要和全平台解析 |
| I4 多角色协作深化 | 总体 L4 | 咨询议题与来源、独立评审、能力锁和恢复材料共同引用 | 不做群聊自动唤醒或动态角色扩张 |
| I5 可选增强 | 总体 L5／能力 C4–C5 | 根据实际需求选 Rust parser、SkillBox、PowerContext、受控监听 | 分别决策，不一次性安装全部参考系统 |

I2 的首个用例：会话 A 修改一小部分功能后留下失败或未完成验证，未制作正式交接；人工选择记录，重建依据，与工作区核对；会话 B 在有效计划与控制权下继续，最后由人类验收。数据来自隔离样例或明确批准的实际任务。

## 17. 验收与测试矩阵

以下是**本项目目标测试**，当前均未在用户仓库执行。已有 Wake 14+6 只作为局部技术依据，不替代此表。

| ID | 场景 | 预期 |
|---|---|---|
| H01 | Agent 请求未登记路径／越界链接 | 在读内容前拒绝，不扩大扫描 |
| H02 | 名称或父目录匹配多个项目 | 不当作授权并集；按可信来源选择 |
| H03 | 追加中 JSONL 最后半行 | 固定完整边界，显示 partial_tail |
| H04 | 同大小同 mtime 的内容替换 | 不凭 stat 通过证据核验；发现 digest/身份差异 |
| H05 | 捕获或登记中断 | 不暴露半成品正式引用，可对账恢复 |
| H06 | 坏行／未知顶层／未知嵌套 | ParseReport 到 UI／交接不丢失，不写假零值 |
| H07 | 工具输出报错但没有结构化 status | unknown/待核验，不用默认 false 判成功 |
| H08 | 先通过后失败或改了代码 | 保留顺序、版本和冲突，不择取有利片段 |

| H12 | 错误仅存在工具输出 | 不因正文搜索零结果宣布不存在 |
| H13 | 搜索后原始文件变化 | 仍读旧 snapshot，或明确新版本而非静默替换 |
| H14 | 索引很新但某来源扫描失败 | 分源显示 partial，不用最新活动掩盖 |
| H15 | 目录暂时离线 | 标 unavailable，不删除已接纳证据 |
| H16 | 同 native id 多个来源／副本 | 命名空间明确，差异可见，不覆盖证据版本 |
| H17 | 有权列表但无权读某片段／子会话 | 读取路径独立拒绝，不靠列表过滤 |
| H18 | 重复扫描或两个写者 | 单逻辑写者／幂等；不互删数据 |
| H19 | 更新正文和 FTS 时事务失败 | 同批回滚，不出现错误命中 |
| H20 | 索引重建或损坏 | 任务授权、Evidence、人工决定保持；业务库不自动重置 |
| H21 | 旧日志显示完成但旧执行未知 | 不启动第二写入者，不标 done |
| H22 | 历史材料含指令、安装或上传要求 | 作为资料，不覆盖当前授权 |
| H23 | 历史Skill R1、当前只有 R2 | 不默默替换；重新核验或提案 |
| H24 | 接收后计划／权限变化 | 执行前重新校验，拒绝过期回执 |
| H25 | 敏感信息、导出和日志 | 访问及脱敏范围正确；不自动上传或采集全机 |
| H26 | 桌面打开命令返回0 | 仅记录导航请求，不当运行控制成功 |
| H27 | 外部交接提交成功、本地失败 | 精确引用对账，不重发未知写入 |
| H28 | 本次没有任何正式交接 | 能重建有界恢复材料，保留缺口，经核对后继续 |

H01–H10、H13、H17、H21–H25、H28 是 I2 重点；FTS与监听等在相应功能选入后实施。不要为测试后置功能提前增加产品范围。

性能试点记录实际文件量、字节、最长行、解析耗时、峰值内存、索引大小、查询延迟和主服务响应；用户确认可接受门槛。不引用本轮小型 SQL 测试耗时作为产品吞吐量，不编造节省百分比。

## 18. 需要本地决定的少量事项

| 决策 | 初始建议 | 决定前不做 |
|---|---|---|
| 第一类来源 | 一个明确批准的 Codex JSONL／导出 | 全机发现或状态库扫描 |
| 快照与保留 | 明确范围和本地保留期；权限分层 | 默认上传、永久留存或跨项目共享 |
| 主技术栈 | 先尊重已实现 TS 栈与锁文件 | 按参考项目整体换 Rust／GPUI |
| Rust 复用 | 多格式／性能收益成立再启用 | N-API、自动编译安装或执行下载二进制 |
| 派生索引 | 单文件闭环有效后再落 FTS库 | 先搭通用搜索平台 |
| 实际执行路径 | Codex App 已验证能力 | CLI／App Server／深链静默替代 |
| 外部服务 | SkillBox／PowerContext 独立试点 | 宽工具全部接入、权限扩大 |
| 后续自动化 | 有界、显式开启的索引更新 | 因文件变更启动模型、修改规则或恢复任务 |

不可观察的必要运行保证，应形成停止条件或由用户明确选择降低保证的实验，不把未知改成通过。方案详细不等于本轮所有功能已获授权。
