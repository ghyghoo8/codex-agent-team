## 1. 决策摘要

**当前建设“任务所需能力的声明、版本引用、就绪核验与运行记录”，不建设通用 Skill / MCP / Plugin / Marketplace 管理中心。**这一范围来自已确认的 v0.1。[B1, §1、§4]

本次新增的核心建议是：

> 将 Skill 当作具有明确来源、完整文件范围和确定版本的工作资产；角色声明需求，计划固定本次选择，宿主与服务实际实施权限，Attempt 保存运行证据，新会话重新核验。

### 1.1 四个直接结论

| 议题 | 本版处理 |
|---|---|
| 要不要管理整个插件生态？ | 不需要。继续以任务、角色、协作、交接和验收为主线。 |
| 要不要有 Skill 资产概念？ | 需要一个可引用的内容版本概念；首版可以由仓库文件和 Git 提交承载，不必新增资产服务。 |
| 要不要立即采用 SkillBox？ | 不设为前置依赖。本次补齐关键源码；正式采用前仍需数据库/接口/目标宿主验证。 |
| 要不要保留 MCP / Plugin / Marketplace？ | MCP 是业务或内容连接接口；Plugin 与目录按实际分发需要使用，不形成另一套管理后台。 |

### 1.2 当前约束与本次未决定事项

| 级别 | 内容 |
|---|---|
| 用户明确 | Codex App 场景；变化需要显式授权；可以人工触发；token 成本优先级降低；忽略 `RocYan98/CodexBoard`；希望进一步结合源码形成细致方案。 |
| 已确认范围 | 先做角色能力配置与就绪检查，暂缓完整插件管理中心。[B1] |
| 原项目基线 | 独立任务业务权威；角色、运行配置、分工、Attempt 分离；未知运行不重派；人类验收独立。[B2、B3] |
| 本次候选增量 | 在 v0.2 基础上明确稳定 URI 与精确内容的区别、当前 Bundle/ACL 与任务锁分离、完整包协议、检查副作用、最小只读适配及审阅证据。 |
| 仍待决定 | 产品最终部署方式、PowerContext / SkillBox 是否采用、目标宿主的实际适配方式、具体数据结构与安装分发方案。 |
| 不恢复 | 已归档的动态模型调度、自动降档和整组 Hook 方案；不引入 CodexBoard 的远程运行路线。[B4] |

降低 token 成本优先级，不意味着无限预算或自动扩权。优先用必要的核验提高交付和接续质量，用量仍如实记录。

### 1.3 本次读源码后，真正需要修改的地方

| 源码发现 | 对方案的修订 | 依据 |
|---|---|---|
| 稳定 Skill URI 读取当前版本 | 不把 URI 当 revision；历史接续走已选定的精确读取路径 | SB05 |
| 旧 Bundle revision 仍解析当前子版本和访问范围 | 固定叶子 Skill 清单，记录必要组合/引用关系；旧锁不绕过撤销 | SB03–SB04 |
| 原生兼容校验比传统存储更严格 | 区分资产有效、格式兼容、当前宿主可用；不静默修复正文 | SB06 |
| 完整包已有文件级与包级校验 | 可借鉴实现，但外部 checksum 与内部清单算法分开 | SB02、SB08 |
| 部分读取写审计、连接检查调用远端工具 | 检查入口展示效果，不用 GET/readOnlyHint 推断无副作用 | SB10–SB11 |
| 原安装器写全局配置且有权限组合计数假设 | 不默认安装；后续检查按必需能力名/schema 而不是工具总数 | SB12 |
| 提案审核有事务与旧基线冲突处理 | 借鉴 CAS，不把提案发布扩展成任务自动采用 | SB01、SB07 |

这些是**本项目的候选修订**，不是因为上传源码就已经授权部署参考产品。SB 编号均能在 §4 和配套《SkillBox 源码审阅与方案影响报告》中找到原文件行号。

## 2. 为什么这样收敛

完全不管理依赖，会让角色只剩名称和提示词：不能解释它缺少哪些能力，也不能让接手者复现工作前提。完整管理中心则会引入来源审核、全局扫描、安装升级、凭据托管、多设备分发、兼容性与运营等另一条产品主线。[B1, §2]

本项目应回答的是：

> **这个角色在这个任务、这个实际环境中，能否按约定工作？如果不能，缺什么、影响什么、由谁处理？**

而不是优先回答“所有平台有哪些插件，如何统一安装”。SkillBox 的研究不改变这一目标。

### 2.1 沿用 v0.2 相对 v0.1 的有效增量（本轮增量见 §1.3）

| v0.1 已有内容 | v0.2 细化 |
|---|---|
| Skill 来源与修订要求 | 区分可变选择器、不可变内容引用、文件清单与完整包指纹。 |
| 按角色检查能力 | 将声明、解析、授权、环境观察和实际交付分开，避免只看 `installed`。 |
| 启动前检查 | 拆成启动前静态核对和启动后、业务动作前的会话核验，避免循环依赖。 |
| Attempt 保存依赖 | 计划保存选择基线，Attempt 保存实际取得和观察结果；差异不可静默抹平。 |
| 缺失时提示 | 明确必需项、可选项、未知、失效及撤销的处理，不自动修复。 |
| 不建插件中心 | 增加轻量资产引用，但不自建完整 Registry、安装器或推荐服务。 |
| 版本变化需复核 | 增加组合展开、提案基线冲突、配套文件漂移和接续时复核。 |

这些增量是本项目的设计建议，不应标注成 SkillBox 已验证实现。

## 3. 在整个项目中的位置

### 3.1 产品主线保持不变

```text
需求与验收标准
    → 任务 / 工作项
    → 计划、阶段与角色分工
    → 能力选择、授权与就绪核验（本专项）
    → 实际执行、必要咨询与评审
    → 版本化成果 / 上下文交接
    → 接手核对与继续执行
    → 人类验收
```

RoleProfile 可适配多个阶段，Assignment 是一次具体分工，Attempt 是一次真实执行。角色适合某阶段不意味着自动参与；角色引用某能力不意味着已经安装或授权。[B2, §5、§8]

本专项不决定业务目标，不自动增加角色，不调度模型，不创建独立执行控制器。

### 3.2 组件分工

```text
RoleProfile：专业职责与能力要求
          ↓
Plan / Assignment：本次角色版本、能力选择和授权引用
          ↓
Team Service：统一业务规则、核验记录、认领与证据
          ├─ 内容解析模块 → 已选仓库 / 已审阅本地资产
          │               → 可选 SkillBox
          ├─ 上下文适配模块 → 可选 PowerContext
          └─ 已验证的宿主接入 → Codex / Specialist Attempt
                                      ↓
                                 工作区、Git、验证结果
```

“模块”首先指现有服务内的代码职责，不要求拆微服务、独立数据库或管理后台。

### 3.3 每类信息只有一个主要权威

| 信息 | 主要权威 | 本项目保存什么 |
|---|---|---|
| 任务、计划、分工、授权、验收 | Team Service | 业务记录及不可变计划引用 |
| 某一 Skill 的正文与文件版本 | 该资产选定的唯一维护源 | 精确引用、清单及获准保留的验证快照 |
| 工作经验与上下文交接 | 选定的上下文记录系统 | 版本、来源、接收结果及业务关联 |
| 宿主实际配置与工具暴露 | Codex / 执行环境 | 带时间、对象和来源的观察 |
| 外部服务权限 | 服务端实际访问控制 | 非敏感身份引用和访问检查结果 |
| 当前代码与产物 | Git / 指定工作区 | 基线、差异和产物引用 |

一个 Skill 可从仓库迁移到外部资产服务，但切换维护源必须明确。不能同时在两边编辑，再默认做双向同步；本地快照也不是第二个可编辑主源。

## 5. 对象模型：不要把所有东西都叫插件

| 对象 | 含义 | 主要约束 |
|---|---|---|
| SkillAsset | 一份可维护的工作指引资产 | 名称只是标签；要有明确来源和稳定身份。 |
| SkillRevision | 该资产某一确定版本 | 包含完整选定文件集合，不只正文。 |
| CapabilityRequirement | 角色对 Skill 或具体工具的要求 | 说明用途、必需性和使用方式，不授予权限。 |
| CapabilitySet | 可选的常用组合 | 只是选择便利；进入计划时必须展开。 |
| MCP Service / Tool | 服务连接及具体操作 | 服务可达不等于工具可用，更不等于任务已授权。 |
| Plugin | 打包与分发单元 | 一个包可含多个组件；检查实际所需组件。 |
| Marketplace | 发现与分发目录 | 首版不发展为应用商店或运营平台。 |
| RoleProfile / Assignment | 专业定义与一次具体分工 | 与资产访问 Profile、服务身份、任务授权分离。 |

官方将 Skill 描述为指引与配套资源，可含脚本；Plugin 用于组合分发相关能力；MCP 提供服务端工具和连接。[O1–O3] 本表中的业务实体名称是本项目建议，不是官方原生 API。

### 5.1 三类“允许”分别检查

```text
允许读取某份 Skill
    ≠ 允许把它交付给当前会话
    ≠ 允许执行其中提到的脚本、安装、迁移或发布
```

RoleProfile、外部资产访问 Profile 和任务授权互不代替。技能正文中写了“先安装依赖”或“调用某服务”，只能提出工作需求，不能替用户授予对应动作。

## 6. Skill 资产与完整版本引用

### 6.1 首版可以不建 Skill Registry

推荐先复用项目仓库或明确指定的内容仓库：内容维护在 Git，计划记录具体提交、资产目录及文件清单。允许已审阅本地目录作为来源，但它必须能形成可重读的确定快照；仅记录一个可变路径不够。

SkillBox 作为以后可替换的内容来源，不是角色、任务和就绪模块的前置条件。

### 6.2 可变选择器与不可变引用分开

| 类型 | 例子 | 允许使用的位置 |
|---|---|---|
| 可变选择器 | 名称、分支、标签、latest、Bundle 名称 | 浏览或提出计划时 |
| 内容引用 | 服务实例 + 资产 ID + 精确 revision；或仓库 + 完整提交 + 路径 | 已确认计划、Attempt、交接 |
| 完整性清单 | 相对路径、文件摘要、字节数、必要文件模式 | 下载、读取、接续时核对 |

提交 SHA 及内容指纹不能单独证明来源可信、安全、合法或仍可访问。只有可变来源、无法固定版本时，报告应明确说明限制，不伪造 revision。

### 6.3 版本覆盖的文件范围

最少应覆盖 `SKILL.md` 以及本次使用的参考资料、模板、资源、脚本、依赖声明和相关调用元数据。官方 Skill 目录也包含此类可选配套资源。[O3]

若只固定正文，却读取到变化后的 `references/checklist.md` 或 `scripts/check.py`，本次使用的工作方法已经发生变化。

建议的内部完整性规则：

- 使用规范化的包内相对路径；拒绝越界路径、重复路径、大小写碰撞和含糊编码。
- 对原始字节计算文件摘要，不能先修改换行或文本编码再假装与源文件相同。
- 清单至少记录路径、文件字节数、摘要和是否可执行；包含稳定的算法/格式版本。
- 包级摘要覆盖排序后的完整清单；新增或删除文件同样改变包级摘要。
- 首个下载实现拒绝符号链接、硬链接逃逸及无法完整验证的特殊文件；已有本地宿主符号链接不能因此被宣称安全，须按明确授权核对真实目标。
- 配套文件的外链不自动纳入受信依赖；需要使用时独立声明来源、版本及网络效果。

这些是本项目拟定的验证规则，不宣称与 SkillBox 的 checksum 算法兼容。二进制编辑器、通用压缩包导入器不属于首版。

### 6.4 已固定版本不等于环境被冻结

Git 目录可被工作区修改，外部服务可能撤销访问，宿主也可能加载其他同名或隐式匹配的 Skill。官方支持隐式 Skill 匹配，并存在多作用域发现。[O3]

因此，CapabilityLock 只表示**本次选择的依赖基线**，不是对全部环境能力的枚举或安全封锁。检测到相关漂移时，停止依赖该条件的业务动作，核对差异后再决定继续；不能未经验证宣称“整个 Agent 只会使用锁定内容”。

### 6.5 三种身份必须分别保存

1. **资产身份**：SkillBox `referenceId` UUID 或仓库内稳定标识，回答“是哪份资产”。
2. **内容身份**：SkillBox revision UUID + 完整包 checksum，或 Git commit + 路径 + 文件清单，回答“哪一份内容”。
3. **本次采用身份**：Plan/Assignment 中的 CapabilityLock，回答“这个任务批准使用什么”。

正文里的 `skill://UUID`、原生 `skill://skillbox/.../SKILL.md` 都不能代替内容身份。`referenceDetails` 和 `resolveSkillReference` 会提供当前目标版本，属于候选解析资料，不得自动扩充已确认计划。[SB05；`src/server/library.ts:844–905`]

同理，存储层声明 `requirements: Record<string, unknown>` 和 `executorIntegrations: string[]` 只提供需求元数据，不包含我们需要的具体工具契约、当前任务授权与宿主验证。不能直接把它们映射为 `ready=true`。[SB11；`src/shared.ts:34–47`]

## 7. 计划内能力锁定与组合展开

### 7.1 CapabilityLock 的定位

在已有 Plan snapshot 中增加一个有限的能力选择快照即可，不另建包管理器。它回答：本次选用了哪些内容和工具、为什么需要、选择依据是什么。

快照至少绑定计划版本、角色版本、Assignment、资产精确引用、必要性、交付方式、工具服务身份及授权引用。内容选择与权限选择使用关联，不复制两份互相冲突的授权表。

### 7.2 组合不是动态入组或扩权规则

如以后提供“后端实现能力组合”，在确认计划前展开成具体成员并固定版本。展开过程需要明确：

1. 检查组合引用是否成环、超出允许深度或规模；失败时不取一个静默截断的子集。
2. 按完整来源、资产身份和 revision 去重，不按显示名称合并。
3. 同一要求解析出互相冲突的版本或权限，交由计划处理，不采用最后写入者覆盖。
4. 记录展开后的清单与组合当时的版本，不能仅保存组合名称。
5. 组合新增成员不改变旧计划；已知的当前访问撤销仍影响相关操作，不能靠旧快照绕过撤销。

首版可以直接使用显式列表，不实现组合编辑、嵌套或解析服务。

### 7.3 Skill 隐含的工具需求

Skill 若需要某个 MCP 工具、运行库或额外资料，应形成可审阅要求。不能因为内容里出现工具名，就自动安装、登录或允许访问。

依赖冲突的处理应是：显示缺失或差异 → 提出计划/环境变更 → 取得适用授权 → 在支持的方式下处理 → 重新核验。

### 7.4 Bundle 与跨 Skill 引用的落地策略

SkillBox 的 Bundle 既便于组合，也参与当前访问授权；它不是历史依赖锁文件。[SB03] 只固定根 R1 时，嵌套 Bundle 的结构、子 Skill 当前 revision、当前 disabled/archived 状态都可能改变。

首版继续用**显式依赖列表**。需要 Bundle 时，在计划准备阶段解析选定成员，把实际需要的每个叶子固定成 `(provider_instance, asset_id, revision, checksum)`；记录根版本和选择理由。没有必要自动加载所有叶子的正文。

对于正文引用，先记录 `declared / selected / unresolved / out_of_scope`，只把当前任务确需的目标纳入锁定。不能宣称解析 Markdown 就知道全部运行期依赖；遇到新必需引用，提出计划变更再读取/执行。

Provider 非 strict 读取若返回子集，对探索可以展示；对本项目的必需要求必须逐项比对，缺失要报错。动态 ACL 收缩时拒绝新访问，动态 Bundle 扩张时不扩大旧任务；这两项并不矛盾。

## 8. 读取、交付、安装与执行四条边界

| 操作方式 | 合理使用场景 | 所需核对 | 不代表 |
|---|---|---|---|
| 指引读取 | 当前角色需要工作方法或检查表 | 确定版本、内容范围、当前接收身份 | 原生 Skill 已加载、脚本可执行 |
| 配套文件获取 | 当前任务需要模板、附件或脚本文件 | 目标目录、完整性、写入效果与授权 | 自动注册插件或安装依赖 |
| 宿主原生 Skill / Plugin 加载 | 明确需要宿主发现、调用或相关集成 | 目标版本支持、加载路径、附带行为、实际配置 | Task 已认领或权限已授予 |
| 脚本或工具执行 | 已授权业务步骤 | 对应工具、文件/网络/数据效果、运行时权限 | 一次批准覆盖未来全部脚本 |

首个切片宜先验证“确定版本的指引读取”。若任务明确要求原生加载，则读取文本不能当作替代；换交付方式必须经过明确计划修订。

### 8.1 最小内容来源接口（概念，不是现有 API）

内容适配模块最多先承担以下能力：

```text
resolve_reference(selector, approved_source_scope)
    → exact_revision + manifest + provenance
read_revision(exact_reference)
    → 内容或精确文件引用 + 可观察完整性信息
read_file(exact_reference, relative_path)
    → 指定文件 + 验证材料
```

现有任务授权由 Team Service 检查，服务访问权限由真实请求身份承担。凭据使用宿主或受保护配置，不进入公开引用和运行导出。

未实现的 GitHub 导入、发布、推荐、安装接口不要先放进首版。若采用 SkillBox，应以其锁定版本的真实 schema 做适配，不照抄本节名称。

### 8.2 下载与落盘的限定

获取文件本身是写操作；仅在已授权位置进行。若实现下载，先在目标文件系统的隔离暂存区校验，全部通过后才提交为完整产物；拒绝覆盖非本项目拥有的文件，不自动执行其中内容。

实现必须针对目标操作系统验证最终切换、失败清理及中断恢复，不能仅写了 rename 就声称跨目录、跨磁盘操作均原子。检查/下载可能联网或启动进程，应提前展示效果。

### 8.3 SkillBox 可选接入：固定读取路径，不混用语义

下表是对**上传快照**的源码描述，不是本项目已经上线的接口。

| 源码接口 | 是否支持精确历史内容 | 接入限制 |
|---|---|---|
| `load_skill({id, revision})` / `GET /api/skills/:id?revision=R` | 是；参数可省略 | 我们必须强制 R；返回的动态引用不能自动采用 |
| `read_skill_file({id, revision, path})` | 是；版本必需 | 只适用于内联文本，超过 160,000 字节或 NUL 二进制要另选已授权包路径 |
| `GET /api/skills/:id/bundle?revision=R` | 是 | 返回 `skillbox/v1` JSON 文件包，并非 Bundle 子图的内容合集 |
| CLI `fetch id@R` | 是，但 CLI 本身允许不传 R | 校验响应 id/revision；下载不是安装 |
| `skills/get` / `resources/read` 的稳定 URI | 取当前 active revision | 不能只靠地址恢复 R1；资源 digest 与读取字节要核对 |

证据：SB05–SB08；`src/server/app.ts:277–318`；`src/server/mcp.ts:209–249`。

**建议首个 SkillBox 适配优先选择精确工具/HTTP 读取，不依赖原生 Skills 扩展。**若用户选择原生加载，必须额外验证客户端的 manifest、digest、版本漂移处理和宿主加载；不能为满足演示静默降为普通文本。

**逐字节校验的补充限制：**`load_skill` 返回正文文本及文件元数据，`read_skill_file` 对 NUL 和长度做检查后以 UTF-8 解码，但不使用严格解码器。它返回的 SHA-256 是原文件字节摘要，不能保证所有返回文本重新编码后仍与原字节一致。需要确认完整原始内容时，使用已授权的 `skillbox/v1` 包读取并解码 base64 校验；文本路径若摘要不符，应报告不匹配，不偷偷修复编码或自行切换接口。[SB02、SB08；`src/server/library.ts:426–477`]

建议的窄调用链：

```text
Team Service 校验任务、所选来源与访问范围
  → 读取 id+revision（不能只传 latest/名称）
  → 验证响应 asset/revision、完整文件集合和外部 checksum
  → 按独立内部格式生成 manifest_digest
  → 检查声明依赖与当前访问状态，动态参考仅作为候选
  → 生成交付凭据，保存到现有 Evidence
  → 将批准内容交给当前会话；Attempt 记录实际交付
```

这只是一个窄内容适配模块，不构建多 Provider 管理后台。第一版可以只有 Git 读取，SkillBox 实现按单独选择加入。

### 8.4 检查与读取的效果类别

| 类别（内部候选） | 例子 | 应展示的效果 |
|---|---|---|
| `local_read` | 读取已批准目录与文件 | 本地范围、内容，不执行脚本 |
| `provider_read_with_audit` | SkillBox load/read/search | 联网读取，Provider 会写访问事件；可含版本/请求上下文 |
| `materialize` | 获取完整包 | 联网和本地落盘，目标目录、大小、权限模式 |
| `active_probe` | 初始化 MCP、认证刷新、外部连接检查 | 可启动进程、联网、远端工具调用、写检查记录 |
| `environment_change` | install-client.py 一类安装器 | 写全局/项目配置、凭据、Bootstrap，可能随后运行校验 |
| `external_analysis` | Skill 推荐 | 发送任务/描述给选定模型，可能写事件及缓存 |

SkillBox 的读取登记在 `events`，`readOnlyHint` 不等于零持久化。[SB10] Executor 设置页已配置凭据时会触发库存查询，服务端还会调用远端 `execute` 执行固定的连接列表查询。[SB11] 本项目页面默认只读已有报告，主动检查必须在效果明确的入口执行。

## 9. 就绪检查：静态核对与会话核验分开

### 9.1 为什么需要两阶段

v0.1 要求启动前检查当前会话是否可获得 Skill、是否暴露工具。但尚未创建的子 Agent 没有可检查的实际会话，容易产生“必须先验证才能启动、必须先启动才能验证”的循环。

本版建议区分：

- **启动前静态核对**：计划、身份、来源、版本、环境要求、授权与必需证据。
- **启动后、业务动作前的会话核验**：实际运行身份、配置、Skill 交付、工具暴露和限制。

实际宿主必须支持所需的受控启动或等效验证方式。不能把“先不要干活”的提示词单独当作硬隔离。若目标 App 无法提供必要控制或可核验证据，该自动执行路线不能通过探针；可由用户选择降低保证的人工实验，但不能静默替代。

### 9.2 推荐启动流程

| 步骤 | 执行内容 | 关键边界 |
|---|---|---|
| A. 形成计划 | 角色需求解析为确定能力清单，展示所需效果 | 不自动安装或扩权 |
| B. 批准计划 | 可信人类入口确认任务范围和版本 | 批准绑定精确选择，不是批准任意 latest |
| C. 静态核对 | 检查来源/版本/身份/工作区与旧执行、可用历史探针 | 未观察到的会话事实仍未知 |
| D. 认领 | 短事务校验计划、控制绑定、输入、容量，创建 prepared Attempt | 不在数据库事务内执行外部检查或启动模型 |
| E. 受控启动 | 通过已验证宿主路径创建并登记运行引用 | 只进行已授权初始化与核验；不盲目重试未知启动 |
| F. 会话核验 | 记录实际取得内容和运行时条件，与要求比对 | 必需条件不符时阻止依赖它的业务动作 |
| G. 执行业务 | 使用现有受控工具和工作区流程 | 权限仍由宿主/服务实时实施 |
| H. 交付/接续 | 保存结果、依赖快照、未决条件与证据 | 不将就绪或运行成功当作验收 |

“阻止”只能在本项目拥有控制权的入口实施。若存在可绕过 Team Service 的直接写通路，不能声称服务端检查控制了全部操作。[B2, §9、§13]

### 9.3 报告的独立维度

```text
需求已声明 / 来源已解析 / 内容版本已核对
交付方式满足 / 当前身份具备访问范围
具体工具可获得 / 任务授权有效 / 运行限制有依据
```

纯指引无需 OAuth。配置存在不等于当前会话已加载。读取成功能证明交付，不证明模型一定遵循；是否正确工作需要成果和测试验证。

每项使用 `satisfied / unsatisfied / unknown / stale / not_applicable`。报告总览可显示“静态核对通过、会话待核验”“已具备本次条件”“阻塞”“需复核”，不伪造单一 installed 状态。

必需保证未知时不放行依赖它的动作。可选项缺失只在计划原本允许、且不影响必需验证与安全要求时继续，并明确记录未使用。不要把所有不可观察的内部推理都列为必需证据，应只定义实际可验证且对任务有意义的条件。

### 9.4 时间、漂移与竞态

报告绑定计划、Assignment、角色版本、执行环境、会话/Attempt、内容和非敏感身份引用。`checked_at` 只是时间，不是持续有效保证。

检查后认领前重新校验计划和相关业务版本；运行时出现关键配置、资产、授权或身份变化后，对受影响项复核。普通活动日志或无关 Skill 更新不应让所有任务反复重跑。

外部权限可能在检查后撤销，因此内容服务和业务服务仍须在实际操作时校验。不承诺实时发现外部服务未暴露的后台变化；需要强保证的操作必须依靠真实执行边界的授权检查。不能把一次预检描述为跨数据库、宿主和外部服务的原子事务。

### 9.5 触发方式

人工检查、已授权任务启动、新会话接续，以及明确发现的相关变化是入口。没有定时 LLM 巡检、每次工具调用全环境扫描，或因警报自动启动另一个 Agent。

自动化允许在具体预授权内工作；“无隐式机制”不等于禁止全部自动化。观察、联网、落盘、模型分析、发布与执行的效果必须分别可见。

### 9.6 增加“来源格式兼容”但不等于原生能力就绪

SkillBox 的普通存储可接受某些缺省字段或旧 YAML，而原生 manifest 校验会拒绝；源码没有把旧文件自动修复后冒称原始内容。[SB06] 我们保留这种区分：

```text
文件完整性通过
  ≠ 该交付协议格式兼容
  ≠ Codex App 当前版本支持该协议
  ≠ 该会话真正获得内容
  ≠ 角色按指引完成了工作
```

原生列表可能因兼容过滤出现空页但仍返回 nextCursor。实现读取器时，只在游标明确终止后判定完成；页失败或不兼容报告不能当“没有任何 Skill”。大二进制或文件边界问题应遵循已选择交付方式，不偷偷尝试其他权限更大的接口。

## 10. 权限与可信边界

### 10.1 四层控制分别承担责任

| 层次 | 负责的控制 | 不能替代 |
|---|---|---|
| 资产服务 ACL | 谁能读/提议/修改某项资产 | 业务任务授权、文件系统限制 |
| Team Service | 计划、认领、提交、验收、控制会话 | 宿主的全部工具隔离 |
| Codex / 执行环境 | 工具暴露、沙箱、审批、实际启动 | 用户是否接受业务成果 |
| 人类入口 | 内容发布、计划、安装与范围变化等决定 | 外部服务的实时访问控制 |

官方 MCP 文档提供工具允许/禁止列表和审批配置，并区分认证与服务连接。[O4] 本项目应验证可用的原生控制，不把角色勾选框当作沙箱。

### 10.2 身份和凭据

RoleProfile 与资产访问 Profile 是不同对象。多个角色共用同一宽泛凭据时，不能宣传角色级资产隔离。

`actor`、`role_name`、`approved_by`、SHA 或模型自述不是可信身份。服务端从认证连接和当前控制绑定解析身份；快照只记录非敏感引用，不复制令牌、认证头或全局配置。[B2, §9]

若外部服务以一个共享服务身份访问，必须明确其权限边界与代理检查；同时开放绕过代理的宽泛工具，会使统一门禁承诺不成立。

### 10.3 撤销、禁用与缓存

内容锁定不能绕过当前的访问撤销。禁止继续访问和受影响操作后，需要标记相关报告失效、识别已有运行和副本，再按现有取消/接续流程处理。

已下载内容和已经进入会话的信息不能假设能够远程收回。缓存策略必须明确保留权限、离线使用条件与来源；不得在撤销后偷偷用缓存继续执行被禁止的工作。是否允许继续使用已合法获得的副本，依据明确政策和本次授权决定，不由实现自行推断。

### 10.4 内容安全与调用约定

外部 Skill、资源内容和 MCP server instructions 都可能影响 Agent。读取内容不提升其指令权威；其中的上传、安装、转发和执行请求仍受当前用户范围约束。

本项目不要求照搬 SkillBox 的任务开始全库检索约定；该约定已在 Bootstrap 与 MCP server instructions 中读到。[SB12] 不自动启用推荐、提示词采集、规则更新、Skill 发布或自动调用策略。对官方允许配置的隐式 Skill 调用行为，应在目标宿主验证具体效果；不靠文档开关名就宣称全环境已禁止隐式调用。[O3]

### 10.5 当前权限与版本化内容并存

SkillBox 当前请求将 client token 解析到最新 Profile，读取历史 revision 仍检查当前可读性。`disabled` 对非管理员阻断读取，`archived` 主要影响发现；精确旧内容工具路径与原生资源路径对归档的处理并不完全相同。[SB03–SB06]

因此，本项目至少分别记录：`selected_revision`、`current_lifecycle_observation`、`access_observed_at` 和本次操作返回结果。读取失败不借助管理员 Token 绕过，不因为历史 metadata 写着 disabled=false 就认定当前仍可用。

新增 `create` 权限在 SkillBox 中可能让新资产自动加入创建者 Profile。[SB04] MVP 不给执行角色 create/update/delete/propose，也不把 `allSkills` 当便利默认。正式提案功能以后单独授权。

**reader 不等于只有无副作用的读取工具。**本快照对 reader 也注册 `recommend_skills` 和 `report_skill_use`，前者可触发外部分析、后者写使用申报。仅关闭 create/update/delete/propose，不能证明这些工具已被隐藏。首个接入应通过自有窄 MCP 工具面或已验证的宿主工具限制，只开放所选读取能力；不照搬原 Bootstrap 的全库检索，也不只靠提示词禁止额外调用。[SB10、SB12；`src/server/mcp.ts:156–273`]

Provider 为避免暴露资源存在性可能返回 404。适配层应映射为“未找到或不可访问”，不能凭错误字符串推断资产不存在、凭据无效或再次越权探测。

## 11. 资产变更与发布：先轻量，后平台

### 11.1 首版使用已有版本管理

首版可以由人工通过已有仓库评审流程维护 Skill；本项目只读取明确版本、保存变更影响和执行记录。不立即建设网页编辑器、资产发布后台或提案数据库。

### 11.2 后续提案流程（候选）

```text
任务中发现问题
    → 提交变更建议、依据及 base_revision
    → 人类审查正文和配套文件差异
    → 检查适用范围、权限效果与验证结果
    → 对当前资产基线做冲突检查
    → 发布新 revision
    → 后续计划明确选择新版本
```

Agent 可以在获准时提出建议，不默认拥有直接发布权。批准某个提案不等于批准基线后来变化后的内容；发生冲突应重新评审，不能自动合并再发布。

发布 R2 不修改已确认的 R1 计划；发现 R1 存在安全问题时，走撤销/影响核对，不以“锁定旧版”继续绕过限制。需要恢复旧内容时，应通过可追踪的新发布或明确版本选择，不改写历史。

### 11.3 经验、记忆、Skill 与规则不混用

PowerContext 中的任务经验或交接可以成为 Skill 提案的依据；只有经过明确审查的变更才进入正式维护源。[B2, §7、§12]

```text
一次工作经验 ≠ 已确认项目规则
候选 Skill 改动 ≠ 正式发布
正式发布 ≠ 当前任务采用
当前任务采用 ≠ 工具执行授权
```

### 11.4 导入、发布、应用分别处理

未来提供导入时，应固定来源提交、目录和文件集合，审查完整内容再发布。导入预览不修改正式资产；发布不安装；安装不自动获得本次任务使用许可。

导入器应有明确的文件/大小/请求时间限制、路径与重定向策略，并验证最终内容与预览基线一致。具体限制由测试确定，不把参考项目数值直接写成我们的产品约束。启用 URL 下载还需单独验证网络访问边界，不能接受任意用户地址后直接以服务权限访问。

### 11.5 从源码借鉴的发布事务与审核范围

`reviewProposal` 的提案锁行、`publish` 的 expectedRevision 检查和提案状态落库位于同一外层事务；原测试包含旧基线和重复审批冲突断言。可以借鉴这种语义，但本轮未运行 PostgreSQL 验证。[SB01、SB07]

提案只禁止修改五类生命周期/组合字段，不保证正文、脚本或 `executorIntegrations` 没有行为变化。审核必须覆盖完整 diff、配套文件与效果，不限于 SKILL.md。对我们的项目，内容发布是资产决定，采用新版本另属于任务计划决定。

### 11.6 安装器不是就绪检查的前置条件

原安装器会下载并执行桥接客户端、写全局指引/凭据/宿主配置，然后验证工具集合；对于当前 writer 或 proposer 权限组合，固定工具总数 4/5 的断言与源码暴露数量不一致。本轮只做静态断言，未运行安装器。[SB12、P21]

这不是重写一个大型安装器的理由。首版不要调用原脚本。将来确需分发：先预检冲突与计划写集，用户确认后分步落盘，失败显示已产生的变化；校验所需工具名/schema/权限，不按总数判断兼容，不把备份文件等同于自动完整回滚。

## 12. 与交接、协作和恢复的整合

### 12.1 交接增加“能力依据”，不复制整个环境

在原 Continuation Package 中补充：

| 内容 | 用途 |
|---|---|
| 计划内能力清单引用 | 知道原执行被允许使用什么 |
| 实际取得的 Skill 版本与完整性结果 | 知道真正交付了什么 |
| 交付模式、宿主及相关配置来源 | 区分文本读取、文件获取和原生加载 |
| MCP 服务身份与工具契约的非敏感引用 | 核对接手方是否访问同一服务与范围 |
| 未知、失效、撤销与可选缺失 | 防止摘要把不确定写成成功 |
| 验证记录和仍未做的检查 | 支持后续按影响范围补证据 |

接手方核对自己的环境，不能沿用旧报告直接通过；同一任务可继续使用 R1，也可提出改用 R2，但不可只因最新版本可见就自行切换。

### 12.2 四个边界继续保留

```text
资料可读 / 接收确认 ≠ 取得执行权
执行开始 / 运行成功 ≠ 技术成果交付通过
技术交付通过 ≠ 人类验收
就绪检查通过 ≠ 全部代码、记忆或工具行为可信
```

更换 Coordinator 仍由可信人类入口处理控制绑定。旧执行未知时不在相同可写范围重派；新 worktree 也不自动隔离共享数据库和外部副作用。[B2, §10、§13]

### 12.3 多角色讨论不直接修改能力或规则

协作议题可以提出“需要另一个工具”“当前 Skill 遗漏检查”，但形成讨论消息不启动安装、发布或新角色。建议通过计划变更或资产提案路径处理。

阶段、角色、工具和 Skill 版本是不同维度。进入实现阶段不自动降档；Reviewer 读了某份 Skill 不等于已经具备只读权限。

### 12.4 外部服务联动

如采用 SkillBox / PowerContext，Team Service 与外部服务分别维护自己的数据。外部写入成功但本地登记失败时，按精确引用对账；结果未知时不盲目重复发布或提交。[B2, §12.4]

最初的 Skill 读取适配不必实现外部发布，能显著减少跨服务写事务。未来扩展写入时再复用 IntegrationOperation，不为每个 Provider 建立另一套任务状态。

### 13.4 源码审阅后的字段增量

在上面原有快照中补充即可，不新增一套 Registry 数据表：

| 字段/记录 | 作用 | 不可误用 |
|---|---|---|
| `asset_identity` | 服务实例 + referenceId + 当前可核对的 slug | 不是内容 revision |
| `exact_revision` | 原始 Provider 版本标识 | 不用 URI 或更新时间替代 |
| `provider_checksum` + `checksum_profile` | 原包摘要与算法/格式，例如 SkillBox 的 path/hash/executable 排序规则 | 不用自有算法覆盖外部值 |
| `manifest_digest` | 本项目规范化完整清单摘要 | 完整性不代表安全或授权 |
| `reference_bindings` | 此任务选中的跨 Skill 精确版本、依赖必要性、未决引用 | 不是发现一个引用就自动读取 |
| `composition_basis` | 使用组合时保存选择依据及叶子集合 | 不靠 Bundle root revision 锁全图 |
| `delivery_receipt` | 实际取得的 source/revision/checksum、交付模式、受信来源与时间 | 不证明模型一定遵循 |
| `current_access_observation` | 非敏感 principal/生命周期/时点与返回结果 | 历史快照不能授予当前访问 |
| `check_effects` | 本次检查的网络、落盘、服务审计和主动调用类别 | 不把“read”一律视为零效果 |

`delivery_receipt` 应由受控获取/校验路径生成，而不只是 Agent 填写“加载成功”。无法观察当前会话接收则保留 unknown。它与 HandoffReceipt 是不同记录：一个证明交付材料，一个记录接手核对。

## 14. 命令、错误与界面

### 14.1 命令是意图，不预设新工具面

| 意图 | 读写效果 | 约束 |
|---|---|---|
| 查看角色要求 | 读取已允许记录 | 不启动服务、不安装 |
| 解析选定来源 | 可能读文件/联网 | 限定来源与内容范围，不执行脚本 |
| 记录静态核验 | 写检查记录 | 绑定计划、身份与证据 |
| 记录会话核验 | 写 Attempt 相关观察 | 绑定真实运行，不伪造已加载 |
| 提出依赖变更 | 写候选计划或议题 | 不修改在途授权和正式资产 |
| 认领/启动 | 复用现有 claim 与宿主路径 | 版本、控制权、旧执行、就绪条件均检查 |
| 提交交接 | 关联能力快照与精确资料 | 不自动验收、切换模型或启动接手者 |

可以复用现有业务命令，避免新增同义 API。写命令继续使用 `command_id`、`expected_version` 和实体引用；幂等与授权语义一致作用于 UI / HTTP / MCP。[B2, §15]

### 14.2 可映射到现有错误体系的原因

`SOURCE_UNRESOLVED`、`REVISION_UNAVAILABLE`、`CONTENT_DRIFT`、`DEPENDENCY_CONFLICT`、`AUTHORIZATION_DENIED`、`READINESS_UNKNOWN`、`REPORT_STALE`、`UNSUPPORTED_HOST_CAPABILITY`。

这些是候选错误原因。沿用现有 code 体系也可以，但界面必须能区分缺失、权限被拒、未知和失效，不统一报“插件未安装”。

### 14.3 三个现有页面足够

| 位置 | 最小信息 |
|---|---|
| 角色详情 | 必需/可选能力、用途、来源选择、交付方式、版本策略 |
| 任务/启动预览 | 本次固定清单、静态核验、待会话验证项、阻塞与操作效果 |
| Attempt/交接 | 实际取得版本、证据来源和时间、配置差异、接手待核对项 |

不新增独立插件管理中心导航，不展示无关的全部账号、环境变量或系统插件。

一个面向用户的结果示例：

```text
任务：评审保存视图功能
角色：Reviewer / R3；计划：P5

本次选择：code-review / R7，正文与配套检查表
静态核对：内容来源和完整性已核对
会话核验：交付指引已登记；只读限制尚无证据
结果：暂不开始要求硬只读的评审业务动作

下一步：补做获准的隔离探针，或提出明确的方案变更。
不会自动发生：安装、登录、切换工具、降低要求、发布新 Skill。
```

## 15. 存储、技术栈与实施复杂度

### 15.1 不为参考项目换技术栈

先读取当前仓库。原文档的 TypeScript / React / Fastify / SQLite 方向仅是已有材料中的基线，不证明当前实现和旧版本组合仍可运行。[B2, §18]

本快照明确使用 Bun / Hono / Drizzle / PostgreSQL。[SB14] 不因参考项目采用这些技术，就改造本项目数据库。外部资产服务如被采用，通过小范围接口访问，不直连或复用其私有表结构。

### 15.2 需要什么才加什么

首个实现优先是：一组角色能力字段、计划内确定引用、两类报告、现有启动门禁与交接关联。

不先建设通用依赖求解、插件扫描守护进程、资产微服务、实时消息总线、自动推荐器或多 Provider 框架。来源解析先支持所选试点的一个实现；接口边界可以清楚，但不必提前实现所有适配器。

### 15.3 引用与内容副本

业务库保存有界元数据和引用；完整内容仍由维护源保存。若为离线交接保留副本，需有明确许可、保存位置、完整性和保留策略，不能静默将私有 Skill、源码或日志上传外部服务。

清理副本不抹掉已发生的历史使用记录。秘密、访问令牌和完整认证头不得进入报告、公开仓库或普通日志。

## 16. 合并到项目路线图的实施切片

以下是候选顺序，需在本地核对后取得具体实施授权。不替换旧计划的完成状态，也不认为仓库仍为空。

| 切片 | 与项目主线的关系 | 最小交付 | 通过/停止条件 |
|---|---|---|---|
| C0 现状和证据核对 | 对应总体 L0 | SkillBox 关键源码本轮已读；继续核对用户目标仓库与宿主 | 复用本包源码证据；仍不能把目标仓库和宿主假定已验证 |

| C2 实际会话核验 | 并入真实角色探针 | 受控启动、真实运行引用、必要工具/权限证据 | 不能证明关键限制则不放行相关自动业务动作 |
| C3 跨会话接续 | 并入总体 L3 | 新会话按原清单核对，处理差异和旧执行 | 不用 latest 替代；未知运行不重派 |
| C4 内容维护和有限分发 | 真实复用需求成立后 | 仓库提案流程、版本选择；可打包自有插件 | 新版本不影响旧计划；不必有资产管理后台 |
| C5 可选资产服务试点 | SkillBox 确有收益后 | 按本快照做最小只读精确版本适配、真实 ACL/历史读取测试 | 源码可读不是联调通过；不开放发布、推荐和 Executor |

C1–C3 可以在不部署 SkillBox、PowerContext、Todos 的情况下验证。若已有系统能力满足，复用现有实现，不重复搭建。

**下一步建议：**先在目标仓库做 C0，然后将 C1–C3 嵌入一个角色/一个 Skill/一个任务的闭环。若采用 SkillBox，不把 C5 膨胀为平台：只实现精确内容读取和副作用可见的核验。引用图、原生扩展、提案界面、导入器、推荐与安装分发不是同时开工的前置项。

### 16.1 首个纵向场景

使用一个获准测试项目中的 Reviewer 工作项：选定 Skill R1 → 确认计划 → 静态核对 → 会话核验 → 评审部分成果 → 保存交接 → 新会话核对并继续。
