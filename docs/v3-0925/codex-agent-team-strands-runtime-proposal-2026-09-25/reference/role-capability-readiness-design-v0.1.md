## 1. 决策摘要

**当前需要管理角色和任务对能力的依赖，但不建设通用的 Skill / MCP / Plugin / Marketplace 管理中心。**

当前模块定位为：

> **角色能力配置与就绪检查：声明角色所需的 Skill、MCP 工具及其来源要求；在执行前核对实际环境与任务授权；将检查结果和运行依赖关联到计划及 Attempt。**

首版不承担整个插件生态的搜索、安装、升级、分发、运营或集中凭据管理。按实际分发需要，可以打包本项目的 Team Skill 与 Team MCP，维护一个轻量插件目录；这不等于建设插件市场产品。

### 1.1 本次确认与尚未确认的边界

| 类别 | 本文处理 |
|---|---|
| 已确认的范围结论 | 先做角色能力配置与就绪检查，暂不做完整插件管理中心。 |
| 沿用的设计约束 | 角色与运行配置分离；来源、版本、实际执行证据可追踪；变化需在明确授权内。[B1, §5、§13–15] |
| 落地候选 | 本文的字段、报告状态、页面、流程和测试场景；实现前须与仓库现状对齐。 |
| 仍待决定 | 最终部署形态、是否正式接入 PowerContext、插件打包时机、目标宿主的具体适配方式。 |
| 本次没有授权 | 写业务代码、安装插件、更新依赖、修改 `.codex` 等宿主配置、启用 Hook、连接新服务、提交或推送仓库。 |

用户已降低 token 成本的优先级。因此，不应为省 token 省略必要核验；也不能以成本可接受为理由扩大产品范围或运行权限。[B1, §1–3]

## 2. 为什么现在需要最小管理，而不需要完整中心

### 2.1 完全不管理的不足

角色只有名称和提示词，不足以说明它能够完成工作。执行前仍需回答：所需指引是否可获得，服务是否可用，工具是否暴露给当前执行者，实际权限是否符合要求。

交接时也不能只交代码和摘要。接手者需要知道原执行使用了哪些指引、服务与约束，并核对自己的环境能否继续。原交接文档已经要求角色版本、运行配置与实际证据分开记录。[B1, §5.3、§13.2]

因此，“不做插件中心”不能被解释为“角色能力全部留在提示词里，不记录、不验证”。

### 2.2 现在建设完整中心的不足

完整中心会额外承担来源审核、安装范围、升级回退、配置冲突、认证凭据、多设备分发、兼容性和生命周期维护。它会成为另一条产品主线，而当前需要先证明的是任务协作和可靠交接。

官方文档已经提供宿主侧的插件发现、安装与管理方式；本项目不应默认重写这些通用能力。[O3] 同时，官方 App Server 文档仍将若干插件管理接口标为开发中，不建议生产客户端调用；不能因为能画出管理页面，就假定存在稳定的宿主控制接口。[O5]

### 2.3 方案取舍

| 方案 | 能解决什么 | 主要缺口或成本 | 当前处理 |
|---|---|---|---|
| 完全交给宿主，项目不记录能力依赖 | 避免重复安装管理 | 难以解释角色为何不可运行，交接缺少环境依据 | 不采用这种完全放空的边界 |
| 角色依赖声明 + 就绪检查 + 运行快照 | 直接支持任务开工、失败解释和接续 | 需要有限的宿主核验及记录能力 | 当前采用的范围方向 |
| 完整插件管理中心 | 统一发现、安装、升级、治理和分发 | 引入另一套产品及长期运维责任 | 暂缓，按真实问题升级 |

这里的选择不是永久否定管理中心，而是不把它设为首个任务闭环的前置条件。

## 3. 对象定义：不要统一塞进一张“插件表”

| 对象 | 本文中的含义 | 本项目关注点 |
|---|---|---|
| Skill | 工作指引及其配套资源，可能包含脚本、参考资料或模板 | 当前角色需要什么工作方法，来自哪里、什么版本 |
| MCP 服务 | 通过接口提供工具、数据和服务端操作 | 连接的是哪个服务、当前身份能调用什么 |
| MCP 工具 | 服务暴露的一项具体操作 | 输入输出要求、读写效果、工具暴露和本次授权 |
| Plugin | 将相关能力组合分发的软件包 | 本项目能力如何打包；包与其中组件的对应关系 |
| Marketplace | 插件发现与分发目录；本文将此前的“market”统一称为 Marketplace | 按需维护有限目录，不负责业务任务执行 |

上述基础区分依据官方插件架构；Plugin 不必同时拥有 Skill 和 MCP。[O1] 官方也描述了仓库级或个人级 JSON 插件目录，可以先只包含一个插件。[O2]

**角色依赖的通常是具体 Skill 或工具，不是“安装了某个包”这一事实本身。**同一个 Plugin 可以包含多个组件；MCP 服务整体可达，也不能证明其中每个工具都已授权或可用。

Hook 可能随插件提供，但不是本模块的首版必需依赖。检查插件来源时应识别其是否附带额外运行行为，不因为安装一个包而默认接受全部行为。

## 4. 首版范围

### 4.1 纳入的能力

| 能力 | 首版做法 | 边界 |
|---|---|---|
| 角色声明能力依赖 | 在现有 RoleProfile 中增加所需 Skill / 工具引用 | 必需项与可选项明确，不自动安装 |
| 来源与版本要求 | 保存来源、指定版本或内容指纹，以及适用范围 | 不只靠显示名称匹配，不宣称指纹证明安全 |
| 就绪检查 | 只核对当前角色、当前计划需要的能力 | 不扫描和管理整个用户环境 |
| 缺失与冲突报告 | 告知缺什么、影响哪一步、需要谁处理 | 不自动修复、替换或降低要求 |
| 运行依赖快照 | 将本次解析结果、观察和证据关联到 Attempt | 不复制一套全局安装状态 |
| 接续时复核 | 对照旧快照与当前环境，说明变化和影响 | 旧快照不是当前可用性的证明 |

### 4.2 按需做，而非立即做

自有 Plugin 的打包、版本说明与轻量 Marketplace 目录，仅在实际分发和复用时进入实施。首版可以先有工作指引、受控工具和检查记录，不为安装体验单独开发后台。

### 4.3 暂不做

不做全生态搜索与收录、评分推荐、公共发布审核平台、自动依赖解析及安装、自动升级回退、跨设备配置同步、集中凭据托管或周期性 LLM 检查。

不以实现本模块为由切换到 App Server、不引入常驻执行器、不进行客户端注入，也不恢复旧动态模型调度与 Hook 草案。[B1, §2.3、§3、§14]

## 5. 职责与唯一事实来源

```text
RoleProfile：角色需要什么
       ↓
Plan / Assignment：本次选择与授权范围
       ↓
按需就绪检查：比对要求、环境观察和证据
       ↓
Team Service：校验业务条件，记录检查结果
       ↓
现有认领与启动流程
       ↓
Attempt：关联实际运行及依赖快照
       ↓
交接：新执行者读取快照并核对自己的环境
```

这是一段现有业务流程，不是新增一个调度服务。

| 所属 | 负责 | 不负责 |
|---|---|---|
| RoleProfile | 声明专业职责、必需与可选能力、输入输出要求 | 授予运行权限、证明本地已经安装 |
| Plan / Assignment | 固定本次角色版本、所选能力及执行范围 | 自动接受目录变化或新工具 |
| Team Service | 校验计划、授权、版本与检查记录；约束自身业务命令 | 凭数据库配置直接限制宿主全部工具或文件权限 |
| Codex / 执行环境 | 实际加载、工具暴露、运行及权限实施 | 替代业务验收 |
| MCP 服务 | 自身认证、访问控制、具体操作执行 | 由“连通成功”推导业务授权 |
| 人类入口 | 决定安装、配置、授权和范围变化 | 通过角色自述或普通评论被冒充 |
| 检查适配逻辑 | 收集当前可观察信息，报告未知与差异 | 假定任意 App 版本都有统一插件控制 API |

Team Service 保存的是**需求、授权和带来源的检查结果**。宿主及服务端保存各自真实配置与权限；本项目不维护与它们竞争的第二份“真实安装状态”。该边界与原交接文档的组件分工一致。[B1, §6、§15.4]

## 6. 最小数据建议

以下是本项目的候选业务字段，不是 Codex、MCP 或插件清单的原生配置键。优先扩展既有角色、计划、证据和 Attempt 记录，不强制新建三套独立数据库表。

### 6.1 角色能力要求

| 候选字段 | 含义 |
|---|---|
| `requirement_id` | 本角色内稳定的要求标识 |
| `kind` | Skill 或 MCP 工具；包与目录信息作为来源元数据 |
| `source_ref` | 仓库、插件来源或服务实例的可识别引用 |
| `component_ref` | 来源中的具体 Skill、服务与工具标识 |
| `revision_constraint` | 指定版本、不可变引用或内容指纹要求；无法核验时明确记录 |
| `necessity` | 对所选工作是必需还是可选 |
| `purpose` | 为什么需要，支持哪个工作步骤 |
| `effect_requirement` | 允许的操作效果及所需限制，例如只读取任务 |

运行时权限仍归 RuntimeProfile、计划授权及真实执行环境管理，不复制一份相互矛盾的权限配置。

### 6.2 就绪检查报告

| 候选字段 | 含义 |
|---|---|
| `report_id` | 检查记录引用 |
| `plan_revision` / `assignment_id` | 检查针对的确切计划与分工 |
| `role_revision` | 被检查的角色定义版本 |
| `environment_ref` | 当前宿主、会话或工作区的非敏感定位信息 |
| `checked_at` | 观察时间，不用时间本身证明持续有效 |
| `checks` | 各项检查结果、来源、方法和证据 |
| `blocking_reasons` | 必需条件未满足或未知的原因 |
| `next_action` | 建议由谁做什么；不是自动执行指令 |

### 6.3 Attempt 依赖快照

Attempt 引用实际采用的角色、计划、组件来源、可观察版本、工具暴露和检查报告。能获取的实际运行信息按原文档的 Requested / Resolved / Observed / Verified 区分；缺失信息不靠模型自报填补。[B1, §13.2]

**快照表示“当时检查和使用了什么”，不表示“外部环境已经被锁死”。**远程服务的接口指纹、版本号或工具清单，也不证明其内部实现此后不会变化。

不得保存访问令牌、密钥、完整认证头或未经授权的全局配置内容。可记录非敏感连接标识、认证状态及证据位置。

## 7. 就绪状态与判定

不要用一个 `installed: true` 代表整个执行前提。需要分开检查：

```text
角色声明需要
≠ 安装或配置存在
≠ 当前环境可加载
≠ 当前会话可获得
≠ 相关身份已认证
≠ 具体工具可调用
≠ 当前任务已授权使用
≠ 实际限制已经验证
```

这些是独立维度，不要求每种组件都经历同一条线性状态机。例如纯 Skill 没有服务认证环节；不需要认证的工具也不能被误报为缺少登录。

### 7.1 候选检查结果

| 结果 | 含义 | 处理原则 |
|---|---|---|
| 满足 | 对指定条件已有可核验依据 | 只证明该项，不代表整个任务完成 |
| 不满足 | 明确缺失、冲突或被拒绝 | 必需项阻止相应执行 |
| 未知 | 无接口、证据不足或未执行核验 | 不等同于满足；必需保证未知时不假装通过 |
| 已失效 | 相关版本、会话、配置或授权发生变化 | 对受影响项重新核对 |
| 不适用 | 此类组件没有该条件 | 记录理由，不填成成功 |

### 7.2 必需与可选项

必需项不满足或无法证明时，阻止依赖它的执行，返回明确原因。

可选项缺失时，仅当当前计划本来就允许不使用它，且不影响验收、权限或必需证据，才可以继续；报告必须说明该项未参与。不得借“可选”之名取消强制评审、数据边界或安全保证。

角色要求与实际环境不匹配时，允许提出变更方案，但不能自行把“必需”改为“可选”、换服务、换模型或授予额外权限。

## 8. 检查流程与触发方式

### 8.1 触发边界

| 入口 | 行为 |
|---|---|
| 人工“检查当前角色能力” | 在明确范围内执行一次检查，展示结果 |
| 已授权任务启动 | 作为现有执行前核对的一部分，不另起常驻 Agent |
| 新会话接续 | 比对旧依赖快照与当前环境；不把旧报告自动沿用为通过 |
| 已知相关版本或配置变化 | 将关联报告标记需复核；不因此安装、升级或自动启动新执行 |

不新增定时 LLM 轮询，也不要求每次工具调用前重新遍历全环境。普通元数据检查优先由代码完成；需要语义判断时使用当前已授权工作流程，不偷偷启动另一个分析 Agent。

### 8.2 一次检查的候选步骤

1. 读取当前任务、计划、角色和分工的精确版本，核对所需能力及授权。
2. 在批准的工作区、来源和宿主范围内解析依赖，不按名称随意匹配另一个组件。
3. 收集当前可观察的加载、工具和认证信息，区分宿主事实、服务回执与人工说明。
4. 核对来源与版本要求、工具效果及所需限制；缺少证据则记录未知。
5. 生成一次检查报告，给出受影响工作与下一责任人，不自动修复。
6. 通过既有业务入口保存报告；启动时重新校验计划和授权未变，再走原有认领流程。
7. 实际运行产生新的观察结果后关联到 Attempt；若发现关键配置不符，不继续开展依赖该配置的工作。

检查外部服务和调用宿主不放进数据库长事务。检查通过也不是外部环境与任务数据库之间的原子保证；具体操作仍依赖宿主、服务端授权和运行时检查。[B1, §13.3、§15]

### 8.3 “检查”并非天然无副作用

读取项目内静态文件与启动一个 MCP 进程、连接远端服务、进行 OAuth、发送测试请求，是不同动作。适配器须说明本次检查是否启动进程、访问网络、发送内容或写入记录。

普通检查不执行任意 Skill 脚本，不安装缺失组件，不读取全部密钥。需要行为探针时使用明确批准的隔离环境与样例；不能为了证明只读就对真实业务资源尝试写入。

人工提供的截图或配置说明可以作为带来源的材料，不能静默提升为宿主实测证据。必要保证无法验证时，提交可行性问题，而不是自动降低保证级别。

## 9. 授权与禁止的隐式行为

### 9.1 操作效果必须分开

| 操作 | 本模块允许的默认效果 | 不附带发生 |
|---|---|---|
| 保存角色能力要求 | 保存角色定义新版本 | 不安装依赖，不改变在途计划 |
| 查看依赖及已有报告 | 读取允许范围内的记录 | 不发起新认证或执行 |
| 发起就绪检查 | 按所见范围核对并记录结果 | 不修改全局配置，不自动启用工具 |
| 发现缺失或冲突 | 展示原因和处理建议 | 不搜索替代后直接使用，不自动降级 |
| 申请安装、升级或配置变更 | 形成明确请求与影响说明 | 不把提出请求等同于执行成功 |
| 执行环境变更 | 仅在另行明确授权后，通过支持的方式处理 | 不属于首版自动修复功能 |
| 启动角色 | 经过既有计划、权限、认领和现场核对 | 不仅凭“插件已安装”就启动 |

### 9.2 必须保留的边界

- 角色关联某项工具，不授予该工具权限；没有关联某项工具，也不证明宿主已经禁止它。
- 安装、启用、认证、Hook 信任和业务授权分别核对；不能用其中一个动作代替全部动作。[O2–O4]
- Team Service 只能强制其控制范围内的业务命令；只读和工具隔离须由真实宿主或服务端实施。
- 自称 Reviewer、传入角色名、填写 `approved_by` 或在评论中写“已授权”，都不是可信身份。
- 能力检查通过不等于人类验收；任务 `done` 仍由原有验收契约决定。[B1, §15]

用户可以预先授权一个明确流程，不必每一步重新询问；但本次整理文档不产生这样的执行授权。

## 10. 来源、版本与变更处理

| 情况 | 首版处理 |
|---|---|
| 同名 Skill 来自不同目录或插件 | 显式选择来源，不只按名称匹配 |
| 角色定义或所选 Skill 内容变化 | 保留旧记录，对受影响任务复核；不得静默改写计划快照 |
| 文件存在，但不能确认当前会话已获得 | 记录对应维度未知，不显示“已完整生效” |
| MCP 已连接，但需要的工具缺失或被禁用 | 按工具报告不满足，不使用其他写工具绕行 |
| 认证对象或服务实例不匹配 | 阻止相关操作，不默认切到另一个账号或服务 |
| 远程工具接口与原快照不同 | 记录差异并核对当前契约；接口相同也不宣称实现完全不变 |
| 用户在宿主侧手动修改配置 | 将其作为实际环境变化处理，不静默覆盖回本项目保存的旧值 |
| 宿主不提供所需管理接口 | 保留未知和人工处理入口，不改用私有协议或注入路线 |

来源可信度、内容完整性和访问权限是不同问题：相同指纹不证明安全；指定版本不证明当前会话已经加载；服务可达不证明读取某个项目已获授权。

## 11. 页面与交接中的呈现

首版不新增独立“插件管理中心”导航。优先在角色详情增加“所需能力”，在任务详情或启动入口增加“就绪检查”，在 Attempt 中展示“本次依赖与验证”。

以下是展示示例，不是实际检查结果：

```text
任务：评审保存视图功能
角色：Reviewer，定义版本 3

必需条件
  项目评审 Skill：来源与内容版本已核对
  当前会话获得该 Skill：未验证
  任务读取工具：当前会话可用
  精确交接版本读取：未验证
  代码只读限制：未证明实际生效

结论
  暂不启动要求硬只读的 Reviewer 执行。
  先核对 Skill 加载、交接读取和实际权限。

允许的下一步
  查看证据 / 重新检查 / 提出配置或方案变更

不会自动发生
  安装插件 / 修改权限 / 替换角色 / 启动其他 Agent
```

交接材料引用本次报告和依赖快照，说明已验证条件与仍未知事项。接手者必须核对自己的环境，不只阅读旧报告。

界面应显示观察时间、适用角色和计划版本、证据来源及下一步责任人。没有必要显示与当前任务无关的全部插件、账号或全局配置。

## 12. 实施切片

这些是后续实施建议，不是本次执行授权。接手者先检查仓库已有内容，不假设当前项目仍只有文档。

| 切片 | 内容 | 完成标准 |
|---|---|---|
| C0：只读核对 | 对照现有 RoleProfile、RuntimeProfile、Assignment、Attempt 和宿主能力 | 给出能复用什么、缺什么、哪些字段不能可靠读取 |
| C1：依赖声明 | 扩展现有角色及计划快照，记录必需／可选项、来源和用途 | 角色编辑不影响在途计划；显示来源与版本要求 |
| C2：按需检查 | 对选定角色提供一次检查和报告，复用现有证据存储 | 缺失、未知、权限不符可区分；不出现自动修复 |
| C3：启动与交接关联 | 报告接入既有认领规则，Attempt 引用运行依赖，新会话重新核对 | 计划变化拒绝沿用旧报告；交接能够解释环境差异 |
| C4：有限分发 | 有实际复用需求时打包自有插件，并按需维护目录 | 在目标宿主验证安装与加载；没有新增通用管理后台 |

C0–C3 不必等待 C4，不要求部署 Todos 或 PowerContext，也不要求先安装一组 Hook。

不预先定义完整安装、升级和回退 API；若仓库已有功能，则按其真实接口与授权模型集成，而不是生成第二套同义服务。

## 13. 验收与测试

验证以实际行为为准，不以界面上有选项、代码里出现字段或模型说“我已加载”作为通过证据。

| ID | 场景 | 预期结果 |
|---|---|---|
| A01 | 角色依赖缺失 | 显示缺失与影响，不安装、不换用替代组件 |
| A02 | 同名组件来自不同来源 | 能区分来源；来源不明确时不随意匹配 |
| A03 | 角色或计划已修订 | 旧报告不能直接放行新版本计划；旧历史保留 |
| A04 | 组件存在但当前会话加载不明 | 显示未知，不等同于完全就绪 |
| A05 | 服务可达但认证失败或工具被禁用 | 分别报告，不把连接成功当作可执行 |
| A06 | 角色未关联某写工具但宿主仍暴露 | 不宣称隔离；按实际暴露与权限要求处理 |
| A07 | 必需权限保证无法验证 | 不启动依赖该保证的任务，不自动降为提示词约定 |
| A08 | 合法可选项缺失 | 仅在计划允许且不影响必需条件时继续，并记录未使用 |
| A09 | 检查报告生成期间计划改变 | 启动入口拒绝使用不匹配的报告 |
| A10 | 新会话接收旧执行快照 | 重新核对实际环境，不把历史成功当作当前成功 |
| A11 | 用户手动修改宿主配置 | 可呈现相关差异，不自动写回覆盖 |
| A12 | 日志、快照及导出包含认证信息 | 敏感值不进入报告、数据库、仓库或交接材料 |
| A13 | 检查需要进程或网络操作 | 展示效果并遵守已授权范围，不隐式触发安装或登录 |
| A14 | 宿主接口不可用 | 显式未知或不支持，不改用未批准的执行路线 |

若为了完成这些测试必须先建设复杂安装器、全局扫描或长期管理服务，应重新缩减切片，而不是认为平台已经成为前置必需品。

## 14. 何时升级为管理中心

升级依据应来自实际使用问题，不采用“以后插件会很多”作为充分理由。

| 可观察到的问题 | 优先扩展 | 仍不自动需要 |
|---|---|---|
| 同一套 Skill 在多个项目重复配置 | 自有插件打包与有限目录 | 公共插件市场 |
| 版本差异反复导致交接失败 | 版本约束、差异展示与升级确认 | 全生态依赖解析器 |
| 多台执行机环境经常不一致 | 环境清单与一致性检查 | 自动批量改机器配置 |
| 多人团队需要统一来源政策 | 团队能力目录和明确审批 | 集中持有所有外部凭据 |
| 必须批量部署、撤销或回退 | 单独评审生命周期管理方案 | 无人值守、无边界的自动修复 |
| 外部开发者向平台发布并供他人发现 | 再讨论真正的 Marketplace 产品 | 自动改变现有产品定位 |

升级前先核对宿主是否已提供可复用能力，并明确新增维护责任、权限、验收和退出方式。目录文件可以长期保持简单，没有必须演进成独立网站或服务的要求。
