## 1. 决策摘要

### 1.1 建议采用的方向

> **Team Service 决定任务、授权和交付；Strands TypeScript SDK 运行 Agent 循环；受控工具及隔离环境执行具体动作。**

建议从 `@strands-agents/sdk` 构建一个有限、明确的执行适配，不直接接受默认 `createHarness()` 的全部行为，不 fork 整个框架，不提前建设多 Provider／多宿主运行平台。

Strands 官方区分底层 SDK 与预组装 Harness：前者提供 Agent 循环及构件，后者组合工具、上下文、会话等默认能力，返回普通 Agent。[S01–S02] 这支持选择底层 SDK，但不证明我们可以省略编码工具设计、权限实施和质量评估。

**本方案优先验证的是一项产品能力：**一个已批准的任务，能按确定的角色、Skill、工具和范围执行，在需要人类决定时停住，故障后不重复写入，并提交可核验成果。

### 1.2 原则不变，执行实现可以重新选择

原整体方案以 Codex App 为主要宿主，并保留 Team Service 的唯一业务权威。[B1, §2–6] 本文提出新的执行候选，因此必须明确区分：

| 层次 | 本次处理 |
|---|---|
| 产品目标 | 保持任务驱动、角色参与、成果可验收、工作可接续 |
| 已确认范围 | 不做通用插件管理中心；能力要求、确定版本和就绪核验继续保留 |
| 已确认约束 | 显式授权、未知执行不重派、单一写入责任、人类验收独立 |
| 新架构建议 | 在隔离切片中验证 Strands 自有执行路线 |
| 尚未发生的决定 | 全面迁移执行宿主、采用具体模型服务、启用 Docker 或其他隔离设施、部署云端 |
| 仍然归档／排除 | 旧自动降档和整组 Codex Hook 草案不恢复；不采用 CodexBoard 路线 |

**使用 Codex App 开发本项目，与成品内部是否使用 Codex App 运行 Agent，是两个决定。**本方案不要求改变开发工具或仓库名。

### 1.3 成功标准

主要看交付质量、授权有效性、可恢复性、人工参与体验和维护负担。耗时与 token 继续记录，但不为节省用量省略核验，也不因成本可接受而允许无限重试或自行扩权。

## 2. 辩证取舍与路线选择

### 2.1 三条路线

| 路线 | 收益 | 主要责任或缺口 | 建议 |
|---|---|---|---|
| A：Codex App 为执行宿主 | 延续已有编码工作方式，减少自建执行责任 | 角色配置、权限、事件与恢复受宿主可用接口影响 | 保留为基线，不破坏既有任务 |
| B：Strands SDK 运行 Agent，Team Service 管业务 | 能直接构造角色与工具、接入审批、采集执行事件 | 自己承担工具安全、编码效果、会话兼容与故障恢复 | **首选验证路线** |
| C：Strands 协调，Codex 执行 | 可能保留 Codex 编码体验并增加上层组织 | 两套规划、审批、会话及重试；上层不自动获得下层全部控制 | 特定需求成立后另评，不作为首版默认 |

以上是项目设计判断，不是框架性能排名。B 是否优于 A，要靠同一任务与验收标准的实际比较，不能只看 API 丰富程度。

### 2.2 为什么值得验证 B

角色可以由确定配置直接构造；权限检查可以位于真实工具边界；运行事实可以在发生时登记，而不是主要依赖历史解析。它可能减少反复适配外部 App 的复杂度，但是否降低总开发成本尚未验证。

### 2.3 为什么不能直接全面迁移

SDK 不等于完整 Coding Agent 产品。仓库理解、文件补丁、错误处理、测试执行、上下文组织和任务收敛仍需验证。相同模型名称不意味着相同编码质量；自建工具也可能比既有 Codex 工作流更不可靠。

标准 OpenAI Provider 文档使用独立 API 凭据；ChatGPT 与 API 分开计费。[S14–S15] 不读取或复用 Codex 的私有登录材料，不假定订阅额度适用于 SDK 调用，不把兼容接口自动视为完全兼容所有工具／流式／取消能力。

### 2.4 不采纳的捷径

不能先启动默认完整 Harness，再仅靠提示词禁止未授权工具；不能让 Strands 与 Codex 同时修改同一工作区来做“对照试验”；不能把正在运行的 Codex 会话直接改写成 SDK 会话并声称无缝迁移。

## 3. 首个验证范围与不做事项

### 3.1 最小范围

单人需求方、一个本地项目、一个活动 Mission、明确的 Provider 与实际模型。先完成一个只读 Reviewer，再扩展为一个实现者与一个独立 Reviewer 串行交付；同一受控写入范围内只有一个活动写入者。

角色目录可以更多，但不为展示团队而全部启动。首次不使用任意自主委派、Graph／Swarm 工作流编辑器或后台子 Agent。

### 3.2 首版必需

任务与计划版本、明确角色和能力锁、一次运行的就绪核验、受控工具、可信审批、运行／操作记录、取消和未知结果对账、成果验证、人类验收。

首次需要的模型调用、会话持久化、日志保存和测试执行分别纳入试点授权。

### 3.3 暂不纳入

通用插件市场、自动依赖安装、模型自动路由、全局 Skill 扫描、自动长期记忆写入、群聊式无限协作、远程无人值守集群、跨设备调度、任意 shell 暴露、生产部署、自动合并或发布。

独立 Runner 是本路线新增的进程职责，不等于建设长期在线的调度平台。首轮由明确的人类动作启动，执行当前已批准计划。

## 4. 整体架构与信任边界

```text
人类用户 ── 任务、计划、具体审批、成果验收
    │
    ▼
React 工作台
    │ 受保护的业务 API
    ▼
Team Service（Fastify）
    ├─ Task / Plan / Assignment / Attempt
    ├─ RoleProfile / RuntimeProfile / CapabilityLock
    ├─ 授权、认领、控制绑定、操作许可、对账
    ├─ Evidence / Handoff / 人类验收
    └─ 业务 SQLite（唯一业务写入者）
    │
    │ 有版本的命令／事件，非模型可自行构造的执行权限
    ▼
Runner（受信任控制进程，按需启动）
    ├─ Strands 执行适配：构造、调用、中断、观察
    ├─ 会话存储：单写者、版本与精确引用
    ├─ 受控 Tool Boundary：最终参数、授权与操作记录
    └─ 明确 Provider 调用：凭据不进入模型上下文或项目进程
    │
    ├─ 受限资料读取：选定 Skill、需求、证据
    ├─ 明确获准的远端 MCP：每项工具独立控制
    └─ 隔离执行环境：文件补丁、项目测试
           └─ 受控工作区、有限挂载、资源与网络限制
```

### 4.1 三种边界不能合并

**业务权限边界：**Team Service 判断当前身份、任务、计划、操作范围和版本。

**执行进程边界：**Runner 管 Agent 生命周期、会话和工具包装；它不执行项目提供的任意代码。

**不受信任代码边界：**仓库测试、脚本、依赖安装等放入已验证的隔离环境，不继承 Runner 的控制凭据或模型密钥。

模型可见工具参数不是权限凭证。任务 ID、角色名、Provider ID、Session ID 即使出现在上下文中，也不能让模型据此操作其他资源。SDK 的 invocation state、Agent state 和工具可写状态不作为授权权威；可信身份与许可在业务服务及工具边界的受保护上下文中核对。

### 4.2 不变的业务权威

SDK Session、Agent 内部 todos、运行日志和模型总结均不是任务状态数据库。`done` 仍仅由可信人类对精确成果的验收产生。[B1, §4–6]

SDK 的 SessionManager 管会话信息，不负责外部副作用或任务授权；Taskboard、MCP 与内部执行均复用同一业务命令，不另存平行任务状态。

## 5. 组件职责与原方案映射

| 组件 | 负责 | 不负责 |
|---|---|---|
| Team Service | 计划、授权、认领、审批决定、控制绑定、证据与验收 | 执行任意项目脚本、推测模型内心状态 |
| Coordinator Agent | 澄清、拆分建议、协作议题、结果整合 | 自批计划、授予权限、代替用户验收 |
| 确定性推进逻辑 | 从已批准有限计划中取可执行项，检查门禁 | 自行扩大角色、流程、预算或目标 |
| Runner | SDK 生命周期、受控工具连接、会话及运行事件 | 改写业务授权、维护第二套任务库 |
| Strands SDK | Agent 循环、工具调用、中断、会话相关构件 | 保证本项目代码质量、实现全部安全与 exactly-once |
| 工具边界 | 最终参数与许可检查、操作记录、真实执行和结果核对 | 从自然语言推定新增权限 |
| 隔离环境 | 已定义范围内的文件和代码执行约束 | 业务验收、外部 MCP 服务的访问控制 |
| Skill／上下文适配 | 已选版本的内容读取、来源与交接引用 | 自动安装、发布或更换内容权威 |

首轮 Coordinator 可以只是用户明确给出的计划加确定性执行逻辑，未必需要再启动一个规划模型。真正需要语义规划时，作为一个独立、获准的 Assignment 运行。

### 5.1 参考项目的关系

Todos、Dashi 继续提供流程与工程参考；SkillBox 为可选资产来源；PowerContext 为可选知识与交接服务；Wake 为外部历史或异常恢复资料入口。[B1–B2] 不把五个参考系统安装成五套底座。

新 Strands 执行优先直接记录事实，Wake 不必参与每次运行。SDK 会话不自动代替长期知识库，SkillBox Profile 不代替任务授权。

## 6. 技术栈与工程组织建议

### 6.1 推荐栈

| 层次 | 建议 | 依据与限制 |
|---|---|---|
| 运行环境 | Node.js 24 LTS，TypeScript strict | 官方 SDK 快速开始要求 Node.js 22+；本次 Node 官方页面列 24 为 LTS。[S13、S16] 补丁版本在本地锁定 |
| 界面 | React + Vite | 沿用原规划，不为本路线重建原生桌面端。[B1] |
| 业务服务 | Fastify | 沿用已有统一命令边界；先读仓库现状 |
| 业务存储 | SQLite + 原数据库访问方式，优先沿用 better-sqlite3 | 单业务写服务、短事务；不在事务中等待 SDK／网络／进程 |
| Agent 内核 | `@strands-agents/sdk` | 固定已验证发布版及对应源码，不默认依赖 `@strands-agents/harness` |
| Provider | 首轮只实现一个明确选择 | OpenAI Provider 若被选择，按官方说明需要相应客户端依赖；不自动连账号或复用 Codex 登录。[S14] |
| 传输契约 | 现有 Zod／类型校验方式 | SDK 类型限制在适配内部；业务 API 不直接暴露 Agent 对象 |
| Runner 通信 | 本机父子进程 IPC 或受保护本地接口，先选一种 | 显式协议版本、命令 ID、事件序号；不引入消息集群 |
| 代码执行 | 通过验证的隔离环境；Docker 是候选 | 需要独立授权和宿主验证，不把进程／worktree 当安全沙箱 |
| 会话 | 所选 TS 版本支持的 SessionManager + 明确本地存储 | 独立于业务 DB；不可自动推定跨版本恢复安全 |
| UI 更新 | 先查询；需要流式体验再用 SSE | 展示连接断开不等于 Agent 停止；传输不替代持久记录 |
| 验证 | 现有 Vitest、真实临时 SQLite、Playwright，加 SDK 契约及故障测试 | 测试脚本先检查副作用，目标业务测试状态仍为 NOT_RUN |

除明确核对的 SDK／Node 约束外，本表是沿用原方案的技术方向，不代表所有包的最新版本已重核或组合已运行。不要复制旧文档中的未来版本数字，也不要仅为文档一致性升级全部依赖。

### 6.2 候选目录职责

```text
web/                         任务、审批、运行、成果界面
server/commands/             唯一业务命令与权限
server/runtime/              运行意图、认领、协议、结果对账
server/capabilities/          能力锁与就绪检查
server/evidence/              产物、核验、技术交接、验收
runner/
  main                       受控启动、通信、资源关闭
  strands/                   SDK/Provider/Session 适配
  tools/                     工具描述、最终门禁与调用包装
  execution/                 隔离环境、工作区及进程观察
shared/                      本项目协议、schema、原因码
migrations/                  业务数据库迁移
roles/ / skills/             固定版本的专业定义和工作指引
tests/                       契约、集成、故障与质量回归
docs/                        ADR、探针、运行说明
```

这些是代码职责，不要求每项单独建服务或表，也不要求为了目录树移动已有文件。可继续一个仓库、一个锁文件，使用不同入口构建 Team Service 和 Runner。

## 7. 身份、执行对象与状态建模

### 7.1 复用业务对象

保留 `Project / Task / Plan / RoleProfile / RuntimeProfile / Assignment / Attempt / Evidence / Decision / Handoff`。只增加原模型缺少的引用和操作记录，不另造任务系统。[B1–B3]

| 概念 | 本文语义 | 重要区别 |
|---|---|---|
| Attempt | 一次获准的具体工作尝试 | 不是每次模型请求，也不是每次 invoke |
| RuntimeInstance | 实際承载执行的 Runner 实例与代次 | 进程重启需重新绑定，不能只看 PID |
| SDK Session / Agent | 一份会话与其 Agent 身份 | 不是永久角色、不是授权凭据 |
| Invocation | 一次 SDK invoke／stream | 审批继续可能产生新 Invocation，但仍属于原 Attempt |
| LogicalOperation | 一次具备明确效果的工具操作 | 内部网络重试可能多次；不等于多个业务 Attempt |
| ExecutionRequest | 对 Team Service 提交的启动／继续／取消等意图 | 命令接收不等于执行完成 |
| ApprovalRequest | 对具体动作的待决请求 | SDK interrupt ID 只是关联信息，不是批准身份 |

### 7.2 何时延续、何时新建

普通 HITL 暂停与回答，在计划、操作、会话和控制权仍有效时可以沿用 Attempt，新增 Invocation 与恢复记录。Attempt 仍活动与 Runner 当前是否正在执行是两个维度；界面应显示“等待批准／运行未决”等真实子状态，不能仅因 Attempt 未终结就显示正在计算。

确认失败／中断后的重新执行，或模型／角色／写入范围发生实质变更，走新 Attempt，关联旧 Attempt 和精确接续基线，不重写历史。

Runner 崩溃后能否恢复同一个 Attempt，是待探针验证的能力。不能证明挂起状态安全持久化时，保留未知并对账；确认旧执行停止后，可通过明确交接建立新 Attempt，而不是伪装成原执行从未断开。

### 7.3 单写者约束

业务认领、SDK 会话写入和工作区写入分别约束。即使两个 Agent 的 SDK session ID 不同，也可能竞争同一目录或外部数据库。

SessionManager 文档明确采用单个会话的单活跃写者假设，且不提供分布式锁。[S06] 本项目首版使用已有业务 CAS、当前控制绑定及本机进程管理，未知旧写者仍占用相关资源。超时或心跳丢失不能自动释放可写资源。

## 8. 执行规格：先固定，再构造 Agent

### 8.1 `ExecutionSpec` 的定位

它是由有效 Plan／Assignment 解析的本项目内部快照，描述本次“被允许尝试什么”，不是新的权限权威，也不是 Strands 原生配置。

建议包含：任务及计划版本、角色及 Skill 精确版本、Provider／模型及参数、工具与中间件清单、输入资料、工作区基线、隔离策略、会话策略、限制和授权引用。

### 8.2 内部示例

```yaml
schema_version: "runtime-spec.proposal.v1"
attempt_id: "<由Team Service认领后生成>"
plan_revision: "<已确认版本>"
assignment_id: "<具体分工>"
role_revision: "<角色版本>"
authorization_ref: "<可信决定引用，不是凭据>"
execution_backend: "strands-ts"
backend_lock_ref: "<SDK/Provider/适配版本锁>"
capability_lock_ref: "<本次确定的Skill和工具清单>"
model:
  provider_ref: "<已配置服务身份>"
  model_id: "<实际支持的模型ID>"
  configuration_ref: "<明确参数及兼容证据>"
  credential_ref: "<非敏感定位信息，不含密钥>"
workspace:
  binding_ref: "<受控工作区身份>"
  baseline_ref: "<代码或只读快照版本>"
  access: "read_only"
execution_policy:
  sandbox_profile_ref: "<已验证隔离策略>"
  tool_set_ref: "<仅本次所需工具及效果>"
  tool_strategy: "sequential"
  interventions_ref: "<经过审阅的控制链>"
  implicit_delegation: false
  automatic_model_switch: false
  automatic_asset_install: false
session_policy_ref: "<存储、版本与单写者策略>"
limits_ref: "<本次与累计限制的明确值>"
context_manifest_ref: "<实际允许交付的内容>"
```

示例不能直接作为 SDK 参数运行。实现时逐字段适配，只使用锁定版本支持的接口；无法映射的必需配置应阻塞，而不是删除字段后继续。

### 8.3 构造后的实际能力必须复核

显式传入 `tools` 不保证最终工具集合等于这份数组：官方 Sandbox 文档说明其后端会自动注册 sandbox 工具；Harness 也可能追加内置工具和插件。[S03、S10]

因此，在构造完成及获准初始化之后，记录实际工具 registry、schema、插件、中间件、上下文策略和 Provider 能力。与锁定清单不匹配时不进入业务执行。不能只检查“我们写进构造参数的列表”。

运行中默认不允许动态注册工具、热更新 Skill、替换模型或加载新插件。已知能力漂移触发复核，不静默重配。

## 9. 启动与交付全流程

| 步骤 | 行为 | 关键门禁 |
|---|---|---|
| 1. 建立计划候选 | 明确范围、分工、验收和能力要求 | 不因提案自动产生执行权 |
| 2. 解析依赖 | 固定所需 Skill／资料／工具来源 | 不取未批准 latest，不安装缺失项 |
| 3. 人类确认计划 | 绑定精确版本、数据范围与允许效果 | 身份由可信入口解析 |
| 4. 静态预检 | Provider 配置、资料、工作区、旧执行、限制 | 主动联网或探针另有明确效果 |
| 5. 认领 | 短事务检查 CAS、控制绑定、依赖和容量 | 建 prepared Attempt 后提交事务 |
| 6. 注册 RuntimeInstance | 启动当前任务专属 Runner 并登记身份 | 不在 DB 事务内启动进程；未知启动不重发 |
| 7. 构造并会话核验 | 解析 SDK 配置、实际工具集合、内容交付和隔离 | 尚不运行未经放行的业务工具 |
| 8. 调用 Agent | 使用指定模型及批准输入 | Provider 与数据出站范围有效 |
| 9. 工具操作 | 通过最终工具边界，必要时暂停等待批准 | 许可检查后执行，记录真实结果 |
| 10. 收尾 | 收集代码、验证、部分结果、停止原因及会话引用 | SDK 正常返回不自动使任务 done |
| 11. 技术交付／交接 | 固定成果及输入基线，必要独立评审 | 过期证据不能通过 |
| 12. 人类验收 | 用户接受精确候选成果 | 不顺带合并／推送／发布 |

两阶段就绪检查沿用能力专项 v0.3：静态预检不冒充会话事实，实际会话核验必须位于相关业务动作之前。[B2, §9] 自有 SDK 路线使这件事更可控制，但不免除测试。

## 10. 工具能力与默认策略

### 10.1 最小编码工具面

以下是本项目建议的能力类别，不是已实现工具名：

| 能力 | 允许效果 | 约束 |
|---|---|---|
| 列目录／搜索代码／分段读文件 | 读取批准的工作区或快照 | 有界输出；不接受任意绝对路径或链接逃逸 |
| 读取指定 Skill／证据 | 读取精确版本 | 每次检查来源和访问范围；无全库隐式召回 |
| 查看 Git／变更 | 观察实际基线和差异 | 不自动 fetch、checkout、reset 或 commit |
| 应用补丁 | 修改批准文件 | 核对预期文件版本；拒绝覆盖不属于本次的改动 |
| 运行已选验证 | 执行批准的项目测试 | 测试是代码执行，必须走隔离与资源／网络策略 |
| 提交评审／结果 | 写业务证据记录 | 只限当前 Assignment；不能调用验收入口 |
| 提出问题或变更 | 保存候选议题／方案 | 不直接启动新角色、安装或发布 |

首轮只读 Reviewer 不获得补丁、shell、依赖安装等能力。其“只读”指代码和业务资源限制，不意味着不能保存获准的评审记录。

### 10.2 默认策略（本项目候选）

采用一个明确模型、确定工具集合、顺序工具执行、有限循环和有限纠偏。关闭隐式委派、后台工具、自动长期记忆写入、全局 Skill 发现和自动模型切换；不使用自然语言风险分类器作为授权依据。

官方 TS 配置默认同轮工具并发。[S07] 本项目应显式选择顺序策略，并检查实际策略；单 Agent 不等于单个并发写动作。

完整 Harness 默认包括 shell／文件、网络、子 Agent 等工具、记忆与后台策略，Intervention 默认为无。[S03] 本方案不依赖这些默认值；如以后复用其中一个构件，应单独审阅其附带工具、模型调用、联网和持久化。

### 10.3 工具描述不等于强制约束

工具 schema、`readOnlyHint`、用途文字、模型承诺都不能替代调用路径的真实授权和隔离。自定义工具可以拥有宿主进程权限，必须逐项审计。[S17]

只隐藏工具名称也不够：检查它是否能通过通用 shell、程序化工具调用、嵌套 Agent 或宽泛 MCP 工具绕行。首版不开放这些通用旁路。

## 11. 显式授权、Intervention 与最终执行门禁

### 11.1 使用 SDK 控制语义，但不外包授权

官方 Intervention 提供 Proceed、Deny、Guide、Confirm、Transform 等结果。[S04] 建议映射如下：

| 语义 | 本项目用途 |
|---|---|
| 继续 | 已在当前明确授权内，进入最终操作核对 |
| 拒绝 | 禁止效果、越权资源或不可满足的限制；不能换工具绕过 |
| 等待确认 | 有明确候选动作，但现有授权不覆盖 |
| 纠正反馈 | 参数／格式等可在原范围内修正的问题；受纠偏次数限制 |
| 转换 | 已声明的参数规范化／脱敏；关键参数改变要重新绑定批准 |

权限组件异常按拒绝或阻塞处理，不按允许处理。辅助调试日志可以尽力记录；必需操作许可、证据或结果记录失效，则停止新的相关副作用，不能假装已保存。

### 11.2 审批对象必须是“具体动作”

ApprovalRequest 至少绑定：可信请求来源、Task、计划和角色版本、Attempt／RuntimeInstance、逻辑操作 ID、SDK interrupt 关联、工具版本、最终参数摘要、资源范围、代码基线、有效期与状态。

摘要只证明内容匹配，不证明身份。密钥不写入摘要输入的公开副本、模型消息或普通日志；使用非敏感引用。

官方 Confirm 的默认响应判断只是解释返回值，还可预填响应而不暂停。[S04] 因此，`true`／`yes` 或一段 Agent 自述不能成为我们的批准依据。

### 11.3 推荐批准链

```text
工具请求
  → 在受信代码中解析、规范化，形成最终动作
  → Team Service 校验当前计划和权限
  → 已覆盖：准备本次操作许可
  → 未覆盖：持久化 ApprovalRequest，SDK 中断
        → 人类入口展示作用对象、差异、风险与范围
        → 记录具体决定
        → Runner 读取决定，重新验证版本与最终参数
  → 将许可绑定到一次 LogicalOperation
  → 在实际工具调用边界再次校验
  → 执行并登记结果
```

审批既可以覆盖一个事先明确的有限流程，也可以覆盖单次动作；不要求每次读取都弹窗。流程授权必须列明工具效果、资源、次数／停止条件，不使用“信任这个 Agent 的一切操作”。

### 11.4 防止参数在批准后被改变

Hook／中间件可能转换参数。最终执行包装必须看到真正送入工具的参数，在所有允许转换之后验证匹配；若仍有更下层代码可以改变目标或效果，则这条链路尚未完成授权保证。

权限检查失败不能当作普通可重试错误。改变路径、账号、MCP 服务、工具实现、工作区基线等相关内容后，旧许可不复用；如仍在明确流程授权内可重新生成匹配许可，否则请求新决定。

### 11.5 批准只消费一次，但不能承诺所有副作用 exactly-once

许可保留 `pending / approved / rejected / expired / revoked` 等决策状态；执行消费另与 LogicalOperation 关联。同一 SDK 回调重入应查询同一操作，不重复消费许可或重新发起写入。

数据库可以原子地把批准绑定到本次操作，但外部工具调用与该事务并不原子。结果未知时按 §14 对账，而不是再次使用批准直接重试。

## 12. Runner 通信、业务幂等与事件可靠性

### 12.1 选定一种本地传输

首版建议 Team Service 按需创建 Runner 子进程，使用受保护的 IPC 传递有限命令和事件；若现有仓库已经有合适本地 HTTP，则沿用并验证身份。两者不同时搭建成框架。

Runner 不能直接写业务 SQLite。其身份和范围由服务端绑定，业务消息不信任自报 `actor`；项目测试容器不得访问该 IPC、服务凭据或业务 DB。

### 12.2 内部协议示意

```json
{
  "protocol_version": "runtime.v1-proposal",
  "command_id": "<stable-command-id>",
  "kind": "start",
  "attempt_id": "<prepared-attempt-id>",
  "control_generation": "<current-generation>",
  "execution_spec_digest": "<immutable-spec-digest>"
}
```

这是本项目协议，不是 Strands API。`start / answer_approval / request_cancel / query_observation` 等意图按最小切片实现即可；不提供任意 JSON-RPC 或任意执行参数透传。

### 12.3 三段状态分开

```text
命令已登记／已接收
    ≠ Runtime 已启动／已登记
    ≠ 工具效果完成／业务成果已接受
```

重复的同键同内容请求返回原记录；同键不同内容报冲突。发送启动后失去响应，先查询／对账，不创建第二 Runner。旧控制代的事件可作为历史材料保留，但不得更新当前权威状态。

### 12.4 事件与持久化

事件带本项目执行引用、RuntimeInstance 代次、序号、来源和观察时间。事件消费者处理重复、乱序和缺口，不因序号间断自动重放业务工具。

关键许可及操作意图须持久化后才发出副作用。执行完成但无法登记时保留未知／待对账，停止新的相关写入。纯 UI 文本流可丢弃或重读，不与关键控制回执共用无界缓冲。

服务失联时停止新的工具副作用和新的模型循环；已在途动作尽力取消并核对。断开浏览器的展示流不直接等同于取消任务，是否继续由原计划的运行边界决定。

## 13. 会话、中断、停止与检查点

### 13.1 保留三层状态

| 层次 | 候选记录 |
|---|---|
| 业务 Task | 沿用 backlog／todo／in_progress／in_review／blocked／done／canceled |
| Attempt 观察 | 沿用 prepared／running／succeeded／failed／interrupted／unknown |
| 本次运行细节 | waiting_approval、cancel_requested、限制原因、SDK 原始 stopReason、会话可恢复性 |

细节字段不必塞入 Task 枚举。一次正常结束可能只完成部分工作；状态归类必须绑定约定的 Assignment 输出，不从 SDK 字符串直接跳到 done。

### 13.2 停止原因的处理

| 观察 | 本项目处理 |
|---|---|
| 正常返回／stop sequence | 登记输出，检查成果与验证，可能仍为 partial |
| interrupt | 保留待决请求与会话关联，不标失败或已完成 |
| 达到循环／token 限制 | 保存部分工作和剩余项，不自动增加上限 |
| cancelled | 停止循环的观察；继续检查工具、进程和外部操作 |
| 模型输出截断、错误、过滤 | 保留原始原因；不能假装有效成果，不绕过安全限制 |
| 不认识的 SDK 原因 | 保存原值与版本，标记未解释；不默认成功 |

这是归类建议，具体 TS 字段与异常／返回路径以所锁版本为准。SDK 文档说明取消在若干检查点被观察，工具回调内的取消需要工具配合。[S12]

### 13.3 中断回调会重入

官方 Interrupts 文档说明，回答后相关 Hook／工具会再次进入；同轮已完成结果与剩余工具有各自恢复规则。[S05] 因此：

- 审批请求创建必须幂等；不能每次重入产生新批准卡片。
- 中断之前不要执行未记录的外部写入。
- 恢复先检查 LogicalOperation；已经成功返回原结果，未知则对账。
- 不能只靠 SDK 内存去重解决 Runner 崩溃后的重复写入。

### 13.4 四类恢复材料

```text
循环检查点：循环暂停在何处
SDK 会话：消息、Agent 状态及相关恢复信息
业务检查点：任务、计划、授权、能力锁和操作记录
工作现场：代码、未提交改动、测试、在途进程与外部副作用
```

官方 TS 的 checkpointing 标为实验性，检查点不包含会话状态。[S07] 首版不把它当作可靠恢复前提。可先完成普通结束／HITL 边界的会话接续；任意循环中崩溃后的透明恢复需独立验证。

Session 存储保留 SDK／序列化格式及适配版本、所属 Attempt 与 Agent 身份、最近成功写入观察和完整性材料。不得因为目录存在就显示“恢复可用”。

## 14. 取消、崩溃与未知副作用对账

### 14.1 取消流程

```text
记录取消意图并禁止新派发
  → 传播取消信号到 Agent 和工具
  → 核对本地工具、测试子进程、容器与远端请求
  → 区分已停止／仍在运行／无法确认
  → 核对代码及外部副作用
  → 确认安全后释放资源，形成可接续基线
```

关闭 Runner 不证明它发起的外部任务停止。PID 单独不足以证明进程身份，容器终止也不撤销已经发出的远端写操作。不得通过“新建 worktree”忽略共享数据库或外部 API 冲突。

### 14.2 LogicalOperation 的最小记录

候选字段：operation ID、Attempt／Invocation、实际工具及版本、最终参数摘要、授权引用、效果类别、资源、操作前基线、已发出观察、实际结果／产物、状态、核对依据。

推荐状态语义为 `prepared / dispatched / succeeded / failed / unknown`。状态名称可以复用现有 IntegrationOperation；关键是保留“是否可能已经产生副作用”。

### 14.3 失败窗口处理

| 窗口 | 处理 |
|---|---|
| 已建 prepared，能证明未发出启动 | 关闭或修复准备记录，再依据当前授权决定新启动 |
| 启动发出但回执丢失 | 查询原 RuntimeInstance／执行来源；无法确认则 unknown |
| 批准已保存但回复未送达 | 重新读取同一决定并核对，不重新请求无限批准 |
| 工具已成功但结果登记失败 | 按输出产物、预期文件摘要或远端 operation ID 对账 |
| 工具失败且能证明无副作用 | 可在既有明确策略内重试；保留每次尝试 |
| 写请求是否到达未知 | 不因 HTTP 超时／SDK 异常直接重试 |
| Session 保存成功但业务结果未登记 | 对照操作日志和工作区核对；会话文本不是授权依据 |
| 业务结果已登记但 Session 不完整 | 保留结果；必要时以正式交接新建会话，不倒退任务事实 |
| 旧控制者迟到提交 | 存为历史或候选证据，由当前控制者核对接纳，不覆盖当前结果 |

TS SDK 的实例防重入不能替代业务幂等；官方所读文档将 TypeScript 的重叠调用拒绝与 Python 的幂等 token 能力分开。[S12] 跨进程的命令与操作去重由本项目负责，不宣称通用 exactly-once。

## 15. 限制、纠偏、重试与资源边界

### 15.1 限制按层管理

| 层次 | 需要明确的量 |
|---|---|
| 模型单次请求 | Provider 支持的输出限制、网络超时、允许的重试 |
| SDK Invocation | 循环轮次、可观察 token 预算 |
| Attempt | Invocation 总数、纠偏次数、工具实际尝试、墙钟时间、待审批时限 |
| Mission／计划 | 已授权角色、评审／修复轮次、最大活动写入者、整体停止条件 |
| 具体进程／容器 | CPU、内存、磁盘、输出、运行时间、进程数、网络 |

SDK 的 invocation limits 在循环边界检查且每次调用重新计数；单次响应可能超过 token 软上限。[S08] 不能将它作为整个 Mission 的精确硬额度，也不能通过不断 resume／新 invoke 绕过本项目累计限制。

业务侧的写操作次数、资源和授权上限在每次实际工具动作前检查，不等待 SDK 下一个循环边界。未知结果也占用相应操作记录；不能把超时当作未使用配额，再自动发起一次相同写入。

### 15.2 不设伪精确的统一阈值

具体值由试点任务和用户接受范围确定，不恢复旧 20%／30% 余额阈值。任一限制用尽，明确返回部分成果和下一步决定，不自动提高预算、换更强模型或重开新 Agent。

### 15.3 重试分类

Provider 网络重试、模型纠偏、工具重试、任务重新派发分别计数。读取重试可能只影响费用；写重试可能重复副作用，不能使用相同策略。

Intervention 的 Guide 不作为无限继续机制；同一问题连续出现或达到计划轮次后停止并提交可处理原因。修正参数不允许悄悄变更目标资源、账号或权限。

超时监测、资源观测和 UI 刷新可以由普通代码执行，不是定时调用分析 Agent。其行为仍需在产品配置中可见。

## 16. 执行隔离与秘密管理

### 16.1 隔离不是单个 `sandbox` 字段

官方 TS API 说明省略 sandbox 时目前可落到 Node 主机执行；不是所有自定义工具都会自动遵循沙箱。[S07、S17] 必须逐项证明文件、命令和网络操作发生在哪里。

DockerSandbox 文档说明它对已有容器执行操作，不创建容器，并会自动注册相关工具。[S10] 因此“传入 DockerSandbox”不能直接视为完成容器生命周期、安全配置或 Reviewer 工具限制。

### 16.2 首轮推荐边界

只读阶段使用确定的代码快照和有限读工具，不提供通用命令执行；验证程序由受信任测试驱动在获准范围运行。

实现阶段如果需要执行项目测试，进入专门批准的隔离环境。Docker 为首选试验候选之一，但必须核对本机支持、安装及资源副作用；不在本文生成可直接以高权限启动的脚本。

候选隔离要求：仅挂载选定项目／产物目录，不挂宿主 HOME、SSH、云凭据、Codex 配置、业务 DB、Runner IPC 或 Docker socket；以非特权用户运行；默认无网络；需要依赖下载时另用明确联网阶段；限制资源并保留进程树观察。

这些是本项目目标控制，不声称容器天然构成绝对安全边界。任何必须开放的例外要记录原因和影响。

### 16.3 测试与评审的特殊约束

测试代码可创建、删除文件或发起连接。只允许一个命令名，并不能使其内容安全；计划应绑定测试目标和代码基线，在隔离环境执行。

Reviewer 阅读固定成果。需要运行验证时，使用只读源快照加可写临时／构建目录，或独立测试副本，不让评审过程修改被评审的候选代码。测试若会修改源文件，显式报告并另行设计执行范围。

### 16.4 凭据与出站内容

模型凭据只交给可信 Provider 客户端；业务控制凭据只属于可信 Runner／服务连接，不能进入工具参数、Skill、会话、导出或项目代码进程。外部 MCP 使用最小范围的独立身份，不共享管理员 Token。

允许调用模型也包含数据出站决定：需求、源码片段、工具输出发给哪个 Provider，是否允许缓存或遥测，分别明确。不因为“本地执行”就声称所有数据留在本地。

## 17. 角色协作与编码质量

### 17.1 固定流程优先

首个完整用例采用：确认需求／计划 → 实现者 → 验证 → 独立 Reviewer → 获准窄修复 → 人类验收。

每段使用独立 Assignment 与明确输入成果，不共享一个无限增长的角色群聊。需要咨询时创建具体议题；消息送达不自动唤醒其他 Agent。协调者建议和确定性派发规则继续分开。

### 17.2 独立评审的含义

Reviewer 使用不同的 Agent 实例和上下文，读取固定候选版本及验收标准，不继承实现者未经验证的“已经正确”结论。模型可以相同，但独立性应来自输入、实例、权限和评审任务，而不是只换一个角色名称。

Reviewer 无权自行验收或开始修复。产品应分开“只读评审”和“评审后按批准范围修复”；允许一轮修复不等于允许无限循环。

### 17.3 结构化输出的边界

要求结果说明：状态、修改／产物引用、执行过的验证、失败／跳过项、未解决问题、下一步和实际运行引用。Schema 通过只证明结构合法，测试和内容判断仍需证据。

不把模型自报百分比当进度，不要求访问完整内部推理来证明角色遵循指令。主要通过可观察动作、成果、拒绝结果和回归测试评价。

### 17.4 对照评估

Codex 基线与 Strands 候选使用相同初始代码、需求和验收，分开的工作副本，不同时修改同一项目现场。选择小型修复、跨文件功能和中断续办三类真实样例，重复试验并记录人工介入。

无法使用相同模型或工具时记录差异，不将结果全归因于 SDK。优先比较成果正确性、回归、越权、重复写入、接续质量，再看时间和用量；不预填提升百分比。

## 18. Skill、会话、长期记忆与历史资料的整合

### 18.1 CapabilityLock 保留

角色声明需求，Plan 固定 Skill 精确版本及配套资源，Runner 验证实际交付。稳定 URI、Bundle 或文件名不是内容锁；来自 SkillBox 的历史版本与当前 ACL 分别检查。[B2]

Strands 的 SDK 插件不是 Codex 的分发插件；SDK 中的 tools 也不是外部 MCP 服务的授权策略。不要将它们统一塞进一个“插件安装状态”。

### 18.2 四类内容各自负责

| 内容 | 主责 |
|---|---|
| 当前对话与 SDK 状态 | 已选择的 SessionManager 和会话存储 |
| 当前任务／授权／交付 | Team Service |
| 跨任务经验与正式交接 | 选定上下文机制，可选 PowerContext |
| 既有 Codex 日志与外部历史 | 获准来源／快照／证据接纳流程，可参考 Wake |

首轮不自动写长期记忆。若以后启用召回、提取、摘要或 offloading，分别明确数据范围、模型调用、存储位置、内容指纹和失败处理；不能借“上下文管理”恢复隐式来源变化。

当前 Harness 的长期记忆包括逐轮召回和后台提取，后台任务也有默认策略。[S18–S19] 本方案不默认采用它们；停用长期记忆不表示可以忽略长任务上下文容量，仍需明确的窗口、摘要或阶段交接策略。

### 18.3 关键基线不要只放在模型历史里

当前授权、能力清单、验收要求、待决问题与成果版本，保存在业务记录；在获准上下文组装时加入必要部分。压缩后的模型摘要不能改写这些权威记录。

SDK 会话格式不能直接替代 Continuation Package。跨 Provider、跨 SDK 版本或从 Codex 切换到 Strands 时，使用精确交接及现场核对，不导入隐藏状态并宣称语义完全等价。

### 18.4 历史模块不成为迁移前置

新执行直接采集运行事件；原 Codex 历史只在异常恢复或接手时按需取用。不必在 Strands 试点前建设全库搜索，也不因读取旧日志自动生成记忆、Skill 或新执行。

## 19. 观测、存储与正式证据

### 19.1 记录可观察事实，不推测内部过程

保留 Requested／Resolved／Observed／Verified 四类信息。[B1–B3] 运行配置明确由哪一层解析；Provider 不返回的实际模型内部信息保留未知。

逻辑工具动作与实际调用尝试分开。中间件设计文档说明：缓存短路仍可触发外围 Hook，内部重试多次可能只产生一组外围事件。[S11] 因此，实际发出次数应在真实调用包装处记录，不能仅数 Hook。

如果 Provider 内部重试不可见，报告观测缺口，必要时关闭相应自动重试或采用可观察方式；不捏造每次网络请求。

### 19.2 推荐事件字段

本项目执行引用、操作 ID、来源层、事件序号、SDK／适配版本、开始结束观察、请求摘要、是否实际发出、是否缓存／转换、结果状态、产物引用、用量来源和未知项。

原始返回与交给模型的裁剪／脱敏视图区分。截断、解析失败和丢事件必须到 UI 与交接仍可见。不得把失败结果转换成“成功摘要”后丢失原证据。

### 19.3 分开存储与保留

业务 DB 保存有界元数据、授权与证据引用；会话和较大产物在独立受保护存储。运行日志、会话内容和正式证据有不同保留及访问策略，不默认全量上报第三方遥测。

不自动保存完整提示词、秘密或不必要的内部推理内容。来源快照只证明保存了哪些字节，不能单独证明来源真实性或现场仍有效。[B1, §4、§8]

文件产物提交和 DB 登记不是一个事务：先写获准暂存、校验、形成确定产物，再登记；中断窗口保留未链接状态，按精确引用对账，不能静默删除唯一结果。

| 切片 | 交付 | 通过证据 | 不带入的工作 |
|---|---|---|---|
| R0：现状和依赖核对 | 仓库事实、版本锁、许可／默认行为审查、Provider 与隔离选择 | 差异表、源码／包身份、授权与探针计划 | 不假设空仓库，不安装全部参考系统 |
| R1：只读 Reviewer | 一个固定角色与 Skill、有限读工具、结构化评审 | 实际 registry、越界拒绝、正确位置引用、无代码写入 | 无 shell、自动子 Agent、长期记忆 |
| R2：审批与受控工具 | 可信批准、最终参数门禁、幂等操作记录 | 参数变化、重复批准、回调重入均不绕过 | 不依赖自然语言风险评分 |
| R3：隔离实现闭环 | 一个实现者、获准验证、独立评审、有限修复、人类验收 | 真实成果、测试、权限拒绝、工作区单写证据 | 不自动合并／发布，不并行写同一工作区 |
| R4：故障与接续 | 审批时重启、工具未知结果、取消、会话恢复／明确交接 | 原执行处置、精确会话与操作核对、无重复副作用 | 不承诺任意时刻无缝恢复 |
| R5：对照与采纳决定 | 与 Codex 基线比较，明确 Go／No-Go | 质量与控制均达到事先确认门槛 | 不以功能数量代替质量 |

R2 的最小待批写操作只作用于隔离 fixture。R3 之前必须完成隔离选择和主动探针；故障测试使用合成数据或明确获准的项目副本。

每个阶段先明确安装、联网、模型使用、凭据、落盘和清理范围。R0 文档核对不自动授权 R1–R5。依赖或关键能力不满足时停止对应阶段，不自行切换宿主或扩大权限。

## 21. 验收矩阵与 Go／No-Go

### 21.1 候选行为测试

全部状态初始为 **NOT_RUN**。这是本项目验收目标，不是 Strands 官方测试结果。

| ID | 场景 | 通过条件 |
|---|---|---|
| RT01 | SDK／Provider 配置不受支持 | 明确失败，不忽略必需字段或自动换模型 |

| RT03 | 同轮出现多个工具调用 | 顺序策略实际生效；独立执行间仍遵守写锁 |

| RT05 | Skill／工具正文试图请求扩权 | 外部内容不改变授权，实际动作被拒绝 |
| RT06 | 授权服务异常 | 不放行新的相关副作用 |
| RT07 | 模型返回 yes／伪造批准人 | 不被接受为可信批准 |
| RT08 | 批准后路径、参数、代码或计划变化 | 不沿用旧许可 |
| RT09 | 中间件转换最终参数 | 最内侧门禁检查真实参数；无绕行路径 |
| RT10 | 同一批准被重复消费／回调重入 | 对应同一逻辑操作，结果可复用或对账，不重复写入 |
| RT11 | 两次点击启动同一工作项 | 一个有效认领，无重复 Runner 或半条 Attempt |
| RT12 | 两个 Runner 写同一 Session／工作区 | 实际拒绝冲突，不靠 SDK 实例锁假装跨进程安全 |
| RT13 | 启动成功但响应丢失 | 查询原执行，未知时不重派 |
| RT14 | 工具写入成功、结果登记失败 | 能按确定产物／操作标识对账，不盲目重试 |
| RT15 | 工具超时且远端是否执行未知 | 保留 unknown 与待处理资源 |
| RT16 | 等待审批时 Runner 重启 | 恢复同一待决关联并重验授权，或明确不支持并安全交接 |
| RT17 | Session 与业务记录不一致 | 检测差异；不以对话文本覆盖业务事实 |
| RT18 | 取消时工具不响应信号 | 不显示全部停止，保留活动工具及资源占用 |
| RT19 | 服务／浏览器断线 | 区分展示断线与控制失联；不重复启动或自动批准 |
| RT20 | token／轮次限制达到 | 部分结果可见，无自动加预算／新 invoke 绕过 |
| RT21 | 连续 Guide 或修复往返 | 达到有限边界后停止，不无限循环 |
| RT22 | 重试／缓存／转换 | 逻辑记录与可观察真实调用可区分，观测缺口不伪填 |
| RT23 | 容器试读宿主秘密／访问控制接口 | 受控拒绝，凭据和业务 DB 不可访问 |
| RT24 | 项目测试尝试越界写或联网 | 符合所声明的实际隔离策略，拒绝结果可核验 |
| RT25 | Reviewer 试图改代码或验收 | 对应工具／服务端拒绝；评审记录仍可合法提交 |
| RT26 | SDK 正常返回但无有效测试／成果 | 不自动 done；部分／未验证状态保真 |
| RT27 | 旧控制代迟到结果 | 不覆盖当前计划，可经当前控制方显式接纳 |
| RT28 | SDK／Provider 升级后恢复旧状态 | 兼容性有测试；不兼容时拒绝或明确新交接 |
| RT29 | 日志、Session、快照及导出 | 无令牌／未批准内容泄露，访问与保留有效 |
| RT30 | 从 Codex 转交到 Strands | 先处理旧执行，按精确交接与新 Attempt 继续，不冒充原会话 |
| RT31 | 同一真实任务与 Codex 基线比较 | 记录正确性、回归、人工干预及不可比条件 |
| RT32 | 决定退出 Strands 路线 | 停止新派发、处置旧执行、保留成果、可人工续办 |

### 21.2 判定规则

安全与一致性硬门槛不能被平均质量分抵消：出现越权、假验收、未知写入重放或凭据泄露时，不采纳为主执行路线，先修复并复验。

质量门槛在试验前确定：功能通过、回归可接受、接续不遗漏关键约束、人工操作负担可接受。结果须有重复样例，不承诺一次成功就代表通用编码质量。

若控制链成立但编码效果不足，可保留只读评审／研究用途，不全量切换；若关键安全边界无法实现，保持原路线或提出新方案，不用降级承诺掩盖。

## 23. 与既有规划的修订及退出方式

### 23.1 明确需要修改的旧边界

| 原规划 | 本路线成立后的变化 | 不变部分 |
|---|---|---|
| Codex App 为主要执行宿主 | Strands 成为新任务的一种显式运行后端，验证通过后才考虑默认 | Codex App 可继续作开发工具和旧任务宿主 |
| 首版无自有 Agent Runner | 增加本地受控 Runner | 不扩大为远程无人值守集群 |
| 暂不把 Docker 作为首版前提 | 执行不受信代码前必须选择实际隔离；Docker 是候选 | 不盲目安装，不用容器名称代替验证 |
| 从宿主回执／历史读取运行信息 | 新路线优先直接采集实际运行；历史作补充 | 未观察信息仍 unknown |
| 角色配置需证明外部宿主接收 | 可由受信构造过程产生，但仍核验 registry、权限和实际行为 | 能力锁、两阶段核验、结果验证保留 |
| 原 Codex Hook 草案归档 | SDK 内部控制机制是新的明确实现选择 | 不恢复旧自动调度、降档或全量扫描 |

这些修改需要架构采纳决定；不能靠本文日期较新自动覆盖原文件。

### 23.2 在途任务不热迁移

先暂停原任务新派发、处置旧运行和副作用，形成精确交接；用户明确采用新后端后创建关联新 Attempt。保留原宿主、运行 ID、成果和验收记录。

### 23.3 退出或回退

Strands 不达标时停止该后端新派发，处理仍在运行的工具，保留代码、证据、会话来源和失败原因。通过明确交接回到人工流程或已选宿主，不直接重放最后一条写命令。

不把“可替换”实现成首版通用后端插件系统。初期只保留稳定业务协议和一个小适配模块；真正出现第二个自有实现时再抽象共同部分。

### 23.4 建议文档关系

本文作为独立运行路线提案，与 `integrated-implementation-plan.md`、`role-capability-readiness-design.md` 并列。采纳后在主方案增加清晰引用及 ADR：哪些原则继承，哪些执行边界改变，哪些测试已通过。

原 SkillBox／Wake 源码审阅结果属于历史材料，本轮未重跑，也不证明 Strands 集成成功。
